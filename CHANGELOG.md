# Changelog

Chronological record of notable changes and the reasoning behind them — not a full diff log. See `CLAUDE.md` for the current architecture and standing rules; this file is for *why* and *when*, kept as an incident/decision log the way a similar sibling project's changelog proved genuinely useful for exactly that purpose.

## Initial build — core sync engine

SpareBank1 OAuth2+BankID authentication, transaction fetch, transform to YNAB's shape, bulk create with `import_id`-based deduplication, MQTT/Home Assistant status and control, Docker image + GitHub Actions CI to `ghcr.io`.

Two API details were unverified from documentation alone and resolved via live scripts before being trusted:
- SpareBank1's `/transactions` endpoint's real query params and field names — resolved via `scripts/probe_transactions.py` against a real account.
- Whether YNAB's resource path is `/budgets` or `/plans` (one AI-summarized spec fetch suggested the latter) — confirmed live as `/budgets` via `scripts/verify_ynab.py`, which also proved the `import_id` dedup guarantee directly (submitting the same transaction twice: created once, reported as a duplicate the second time).

Follow-up fixes found only once real data was in hand: SpareBank1 dates are Unix epoch milliseconds, not ISO strings (was crashing every fetch, uncaught); payee names improved by preferring `remoteAccountName` over raw `description` when present.

A real end-to-end cycle against a live account confirmed the design: 34 fetched → 31 imported on the first run, 0 new imports on an immediate second run.

## Credit cards, multi-budget mapping, pending→booked reconciliation

Extended to support:
- **Credit card accounts** — confirmed to need zero fetching changes vs. regular accounts (same endpoint, params, response shape); only improvement needed was preferring `cleanedDescription` over raw `description` for payee names, since card purchases have no `remoteAccountName`.
- **Multiple YNAB budgets** — `config.yaml`'s `ynab.budgets` (human-readable alias → real budget UUID) plus each account's `ynab_budget` field, with a fail-fast pydantic validator catching unresolvable aliases and duplicate account keys at startup.
- **SQLite state store** (`sync/state_db.py`), replacing the previous JSON-based cursor store, adding a `tracked_transactions` table to support:
- **Pending→booked reconciliation** — a not-yet-settled transaction imports immediately as `uncleared`; once SpareBank1 reports it booked, the *same* YNAB transaction is updated in place (`cleared` + `amount`) instead of creating a second one.

Live verification of the new YNAB update call (`update_transactions`, bulk PATCH) found a real wrong assumption: a guessed `GET .../transactions/import_id/{import_id}` lookup endpoint returned a genuine 404 — it doesn't exist in the YNAB API. Replaced with `find_transaction_by_import_id()`, which lists `GET .../accounts/{account_id}/transactions` (a well-established endpoint) and scans client-side for a matching `import_id`.

## Comparison-research-driven hardening

Compared against a sibling project (`../ynab-auto-bank`, ~23,000 lines, similar purpose via a different bank aggregator) for lessons. Confirmed two of our architectural choices already avoid real bug classes that project hit in production (a multi-thread sync-dispatch race; a content-hash dedup-key collision), and that our headless/MQTT-only scope deliberately avoids its much larger web-UI/config-management surface. Two real gaps found and fixed:
- `scheduler.py`'s MQTT command handler had no exception guard — a single bad command could silently kill `sync_now`/`pause` handling for the rest of the connection's lifetime, with no error surfaced. Fixed.
- `tenacity` had been a declared dependency since the original design but was never actually wired in. Added a shared retry decorator (`http_retry.py`) for read-only GET calls only (3 attempts, backoff, on connection errors/429/5xx) — writes are deliberately not retried at the HTTP layer, since they're already safe to retry next cycle via `import_id` dedup and idempotent PATCH semantics.

## Tracking-key bug: duplicate transactions from an unstable SpareBank1 `id`

**Root cause**: SpareBank1's `id` field — used since the initial build as the transaction identity for `import_id` derivation and local tracking — was discovered live to change on *every single poll* of a still-pending credit-card transaction. Two fetches of the same real charge, hours apart, returned completely different `id` strings while every other field (`nonUniqueId`, `description`, `amount`, `date`, `accountKey`) stayed identical. Every poll cycle was therefore treating the same pending transaction as brand-new, creating a fresh YNAB transaction each time — a live, active duplication bug.

**Fix**: `transform.get_tracking_key(sb1_tx, account_key)` replaces `id` as the tracking/dedup key everywhere. It prefers `creditCardIdentifiers.nonUniqueId` when present (booked credit-card transactions expose this structured field) and falls back to the raw top-level `nonUniqueId` otherwise (pending credit-card transactions, and all regular bank-transfer transactions, which never have `creditCardIdentifiers`), scoped by account key. A regression test reproduces the exact bug scenario (same `nonUniqueId`, two different `id` values across two sync cycles) and proves only one transaction is created.

**Still open**: whether the pending reservation's `nonUniqueId` becomes `creditCardIdentifiers.nonUniqueId`'s value once the *same* transaction settles is a well-supported hypothesis (structural match: booked `nonUniqueId` is literally `"{partitionKey}-{that value}"`) but not yet confirmed against an exact same-transaction pending→booked pair. See `CLAUDE.md`'s "Known open risk" for the accepted contingency if it turns out false.

## Deleted-transaction resolution and manual re-add backend

While live-testing the tracking-key fix, the fixed pending transaction still didn't appear in YNAB. Root cause, found by cross-referencing the local state DB against YNAB directly: **YNAB permanently reserves a transaction's `import_id` even after that transaction is deleted**, and its plain (non-delta) transaction list silently excludes deleted transactions — so the existing resilience lookup (`find_transaction_by_import_id`) found nothing, even though YNAB's "duplicate" response was correct. The deletion itself was accidental: earlier guidance to "check the budget for duplicates from the migration window and clean them up" wasn't precise enough, and the cleanup caught a legitimate, freshly-tracked transaction (not just stale pre-fix duplicates) alongside real ones — see `CLAUDE.md`'s new "Operational gotchas" entry.

**Fix**: a second, heavier lookup (`find_transaction_including_deleted`, budget-wide with `last_knowledge_of_server=0`, since YNAB has no simpler way to see deleted transactions) distinguishes "really lost local state" from "this was intentionally deleted." A confirmed deletion is recorded as permanently resolved (`booking_status='DELETED'`) so it's never retried or re-errored — logged in human-readable terms (payee/date/amount, no ids) and surfaced as a new `resolved_deleted_last_run` MQTT sensor, so a resolution is noticeable without being noisy.

**New capability**: since a resolved-deleted transaction might have been deleted by mistake (as happened here), `tracked_transactions` now persists full reconstruction data (payee, memo, date, YNAB account, cleared status) for every row, and `SyncEngine.readd_deleted_transaction()` can re-create one from that data with a fresh import_id (the original stays permanently burned). No MQTT command or GUI triggers this yet by design — `scripts/readd_deleted_transaction.py` (list candidates, or re-add one by id) is the only current entry point; a proper command receiver is planned for later.

## Frontend SPA (React + Vite + Tailwind)

Added `frontend/` — a TypeScript SPA giving the previously script-only admin tasks (checking status, re-adding a deleted transaction, importing a spreadsheet) a proper UI, built against a FastAPI JSON API contract designed concurrently by other work. Three tabs, no router (local-state nav only — sits behind an external reverse proxy with its own auth): Dashboard (polls `/api/status` every 15s, color-coded healthy/paused/auth-required/error state, per-run and all-time counters), Deleted Transactions (list + one-click re-add with per-row success/error feedback), Import (drag-and-drop `.xlsx` upload → dry-run preview with classified rows and summary counts → confirm commit; 422 responses from the backend are shown verbatim in a styled callout since the backend deliberately writes personality into those specific error messages).

Kept dependency-minimal as specified (react, react-dom, vite, @vitejs/plugin-react, typescript, tailwindcss, postcss, autoprefixer) with one necessary addition not in the original list: `@types/react` + `@types/react-dom` as devDependencies — TypeScript's JSX type-checking fails outright without them (`tsc` reported hundreds of "JSX element implicitly has type 'any'" errors until added), it isn't optional tooling.

`npm install && npm run build` verified clean (Node v24.15.0 / npm 11.12.1) — no TypeScript or build errors. `npm audit` flags a moderate `esbuild`/dev-server-only advisory inherited from the pinned Vite 5 line (fix requires an intentional major-version bump to Vite 8); left as-is since it only affects the dev server's CORS handling, not the production build this deliverable is judged against.

## Sync Now button, and the payee-duplication bug

**Sync Now button**: the GUI's status page was read-only. The backend (`POST /api/sync-now`) and the frontend API wrapper (`syncNow()`) already existed, unused — only `Dashboard.tsx` needed a button wired to them. Since `/api/status` has no "sync in progress" field, the button's loading/"requested" feedback is local optimistic UI, not backend-driven.

**Payee-duplication bug**: reported behavior — renaming or merging a payee inside YNAB doesn't stick; the next sync of the same merchant recreates the old name as a fresh payee. Root cause, found by reading the code: every create path always submitted `payee_name` (a string YNAB matches by exact case-sensitive equality) and never `payee_id`; nothing in the codebase looked up or cached an existing payee before creating.

Confirmed live via `scripts/verify_ynab_payee_id.py` before trusting the fix (per the project's live-verify standing rule): `create_transactions`'s response includes a resolved `payee_id` per created transaction (previously unread); renaming a payee via `PATCH /budgets/{id}/payees/{payee_id}` and then creating a new transaction with that same `payee_id` correctly attaches to the renamed payee; and, as a control, resubmitting the stale original `payee_name` after the rename reproduced the bug exactly — a second, separate payee.

**Fix**: a new `StateDB.payee_mappings` table caches the `payee_id` YNAB assigns the first time a given raw `(budget, payee_name)` pair is created (`INSERT OR IGNORE` — first-write-wins, since the cached id is meant to be a permanent anchor to whatever the user renames it to). `engine.py::_classify()` looks up the cache before every create and, when present, submits `payee_id` instead of `payee_name` (`ynab_payload.build_create_payload()` now treats the two as mutually exclusive, matching YNAB's own behavior); `_record_created()` populates the cache from the create response, carefully excluding a matched transfer's primary leg (whose `payee_id` is YNAB's own transfer payee, not a merchant - see invariant 8) from ever being cached under a raw merchant name. See `CLAUDE.md` invariant 12 for the full mechanism. Known gap, left unconfirmed: behavior when a cached `payee_id` refers to a payee since deleted/merged in YNAB - the live API used for verification has no way to delete or merge payees, so this case couldn't be exercised.

Also fixed, while verifying subagent configuration this session: two of the three custom `.claude/agents/*.md` files used a YAML-array `tools: [...]` format that likely doesn't parse, and `explorer.md`'s `name: explorer` collided with the built-in `Explore` agent (probably why none of the three were showing up as available agent types) - renamed to `code-scout` and switched all three to the documented comma-separated `tools:` format; also added `Bash` to `patcher`'s tool list, since its own system prompt instructs it to run lint/checks after an edit but it had no way to.

**File import**: a second, independent dedup domain (`sync/file_import/`) for importing bank export spreadsheets, parallel to the live SpareBank1-poll path. Named generically (`file_import`, not `xlsx`) since xlsx is only the first supported format — a `TransformerBase` OCP registry (ported from the sibling `../ynab-converter` project's plugin pattern) means a second format is a new file, not a change to the engine or dedup logic. The dedup key (`sync/file_import/dedup.py`) is a sha256 hash of *content* fields (date, amount, casefolded payee, casefolded memo) — modeled on another sibling project's (`../ynab-auto-bank`) `compute_dedup_key` — since a spreadsheet row has no bank-assigned id to key off at all, unlike SpareBank1's `nonUniqueId`. Uses a distinct `"FILE:"` import_id prefix from `transform.py`'s `"SB1:"` so the two dedup domains can never collide even for the same real-world transaction observed by both paths. `SyncEngine.import_file_rows()` reuses `_record_created`/`_backfill_duplicates` **verbatim** from the live-poll path — only the fetch+classify stage differs per source, not the submit-and-reconcile-duplicates logic. The one registered transformer (`NorwegianBankTransformer`) was built against the real header/column layout confirmed live from `../ynab-converter`'s own sample export, not guessed.

**FastAPI backend + GUI wiring**: `src/ynab_auto_sync/webapp/` exposes `/api/status`, `/api/deleted-transactions` (+ readd), and `/api/import` — the latter always re-parses the uploaded file from scratch on every call (dry-run and commit alike), so the frontend's preview→confirm flow needs no server-side session. Account resolution for an import is: explicit override (always honored) → else exactly one config match via the new `AccountMapping.import_source_name` field → else rejected with a deliberately witty message (`webapp/import_messages.py` — an explicit product requirement, not a joke to skip). `__main__.py` now runs the scheduler and uvicorn concurrently via `asyncio.gather` on one event loop.

**SQLite concurrency hardening**: the GUI turns what was rare, manual concurrent DB access (a script run by hand) into routine concurrent access (a webapp route firing while a scheduled cycle runs). Fixed with three mechanisms together: `PRAGMA journal_mode=WAL` + `PRAGMA busy_timeout=5000` (replacing `scripts/readd_deleted_transaction.py`'s old "if locked, just retry" folklore with an actual wait-and-retry mechanism) plus an `asyncio.Lock` around every mutating `StateDB` method (every such method is now `async`, guarding against two coroutines on the shared event loop interleaving mid-transaction — see `_backfill_duplicates`' awaited network call between a read and a write on the same key). `check_same_thread=False` was also needed, not for concurrency safety but because Starlette's `TestClient` dispatches into a different OS thread than the one `StateDB` was constructed on even for a fully async app — discovered via `sqlite3.ProgrammingError` while writing `tests/unit/test_webapp.py`, not a theoretical concern.

**Cron scheduling**: replaced the fixed `poll_interval_seconds` loop with a single `croniter` expression (`sync.cron_expression`, default `"0 6,8,10,12,16,20 * * *"` — no fetching overnight). The scheduler's existing `wait_stop`/`wait_sync_now`/`FIRST_COMPLETED` race (which keeps `sync_now`/shutdown responsive) was untouched — only the wait's timeout source changed, from a fixed interval to `croniter(...).get_next(datetime)`.

**`tracked_transactions` retention**: implemented the policy `CLAUDE.md` had specified but left unbuilt — `StateDB.prune_booked_transactions()` (BOOKED rows only, past `retention_days`, never PENDING regardless of age) and `maybe_vacuum()` (rate-limited VACUUM, since DELETEs alone don't shrink the file), called non-fatally at the end of every sync cycle. `retention_days`' config validator enforces it stays past the fetch horizon (`initial_backfill_days + lookback_overlap_hours`) so pruning can never resurrect-as-new a transaction still inside a cycle's normal re-fetch window.

Full test suite (127 tests) and `ruff check` clean throughout. Added a project-wide `ignore = ["B008"]` to `pyproject.toml`'s ruff config — a documented, deliberate exception for FastAPI's `Depends()`/`File()`/`Form()` parameter-default pattern, which ruff's default rule set otherwise flags as a bug.

## Import dropdown, payee/memo sanitization, multi-account fetch, real linked transfers

Four more additions on top of the file-import/GUI/cron/retention work above.

**Import account picker → dropdown**: the GUI's Import tab's free-text account-override field (users had to type an exact internal key by hand) became a `<select>` populated from `/api/status`'s existing `accounts` list, with an explicit "Auto-detect from file format" default option representing "no override" (a real, valid choice, not an error state).

**Payee/memo sanitization**: new `sync/sanitize.py::clean_bank_text()`, ported and trimmed from sibling project `../ynab-auto-bank`'s `description_processing.py` — strips a leading run of `=`, replaces `*` word-separators with spaces (SpareBank1 and the Norwegian Bank xlsx export are both confirmed to use `*` this way, e.g. `"Zettle_*Micro Kaffi AS"`, `"PAYPAL *JAGEX LTD"`, `"Vipps*Odeon kino Stavange"`), removes a parenthesized account number, collapses whitespace. Applied on both the live-poll (`transform.py`) and file-import (`file_import/transformers/norwegian_bank.py`) paths so formatting is consistent regardless of source. Deliberately did NOT port the sibling project's "strip standalone CRV marker" rule — that's specific to its own bank aggregator (Enable Banking) and has never been observed in any SpareBank1 payload; porting an unconfirmed pattern risked silently mangling a legitimate merchant name for no real benefit.

**Multi-account SpareBank1 fetch**: `sb1_client.get_transactions()` now takes a list of account keys and fetches every configured account in ONE request instead of one-call-per-account. Confirmed live via new `scripts/probe_multi_account_transactions.py` (following this project's standing live-verification practice) that SpareBank1's API accepts a **repeated** `accountKey` query param and returns the genuine union (a two-account probe returned exactly the sum of each account's individually-fetched count, correctly split via each transaction's own `accountKey` field) - a comma-joined single value is explicitly rejected with 400. `run_cycle()` now computes each account's own fetch window first, fetches all accounts at the earliest shared `since`, then re-applies each account's own (possibly later) window as a client-side filter - unchanged correctness, fewer HTTP calls, and incidentally exactly the "collect everything before creating anything" shape the transfer feature below needed anyway.

**Real, YNAB-native linked transfers** (the big one): previously, a transfer between two of the user's own SpareBank1 accounts would import as two ordinary, unlinked transactions. Sibling-project research first (`../ynab-converter` has nothing on this; `../ynab-auto-bank` only does cosmetic payee relabeling via a `KnownAccount` table + description-text account-number matching, explicitly never using YNAB's native `transfer_account_id`/transfer-payee mechanism - confirmed via grep, zero matches in that entire codebase) showed neither project had solved the real problem, so this was new design work, live-verified before being built (per this project's standing practice) via a new `scripts/verify_ynab_transfer.py` that created one real test transaction against the user's live budget:

- Creating a transaction with `payee_id` set to the destination account's auto-generated `"Transfer : <name>"` payee makes YNAB **auto-create the linked paired transaction on the other account itself** - the caller must never submit both sides.
- The auto-created side gets **`import_id: null`** - YNAB assigns it none at all.
- Transfers only work **within one YNAB budget** - confirmed by testing two accounts in the same budget.
- A transfer-creating submission's response lists the **same transaction id twice** in `transaction_ids` - would have silently inflated `CycleResult.created` if not caught by this verification step.
- YNAB defaults the auto-created side's `cleared` to `"uncleared"` regardless of what the primary was created with.

Built as: `sync/transfers.py` (pure-function `find_transfer_pairs` - opposite-sign, equal-amount, different-account matching within a configurable date window, ambiguity-safe on both sides, no I/O, independently unit-tested), a new `_match_transfers()` pass in `engine.py` inserted between classify and submit (scoped per-budget for free, since `creates_by_budget` was already grouped that way), and `_record_transfer_secondary()` which writes the auto-created leg's `tracked_transactions` row using a clearly-marked local-only synthetic import_id (`"LOCAL:XFER:..."`, never sent to YNAB) plus an immediate corrective PATCH if SpareBank1 already reports that leg as booked. `CycleResult.created` now comes from `_record_created`'s own return value (rows actually written) rather than trusting `response["transaction_ids"]`'s length, fixing the double-counting bug found above for both the transfer and non-transfer paths.

The date-matching window (`sync.transfer_match_window_days`, default 4) exists because credit-card payments can take until the "next working day" to become visible on the card account - confirmed by the user this can exceed 1 calendar day across a weekend, so a same-day-only match would miss real transfers.

**Known, documented residual risk** (not fully solved): if the process crashes in the narrow window between recording a transfer's primary and secondary legs (two back-to-back local SQLite writes, no network call between them), the secondary could be left untracked, and a later cycle would then submit it independently as a genuine duplicate (no import_id on YNAB's side for it to collide with). Fixing this fully would need wrapping both upserts in one atomic DB transaction - a larger `StateDB` change, deliberately deferred rather than blocking this feature on it.

All new/changed behavior covered by tests (149 passing) and `ruff check` clean.

## Multi-provider refactor: provider seam, notification seam, DB-backed mappings, drag-drop UI

The sync core was welded to SpareBank1 and to MQTT. `engine.py` imported `sparebank1.client`/`auth.TokenStore` directly, read the raw SB1 field `sb1_tx["accountKey"]` inline, and hardcoded SB1's `PENDING`/`BOOKED` vocabulary; `scheduler.py` imported `aiomqtt` and owned the broker connection inline, with no way to run without a broker; account mappings lived in static `config.yaml`, so nothing could be remapped at runtime. This change introduces seams on both sides and delivers the mapping UI. **YNAB remains deliberately hardcoded** — it is the only target, and abstracting it would buy nothing.

**Input seam.** New `providers/` package: `TransactionProvider` (`type_name`/`list_accounts`/`fetch`), `NormalizedTransaction`, `ProviderAccount`, `BookingStatus`, `ProviderAuthRequiredError`, plus a registry mirroring the existing `file_import` one. `sparebank1/` and `sync/transform.py` moved under `providers/sparebank1/` and a `SpareBank1Provider` now owns what used to be inline in `run_cycle`: the batched multi-`accountKey` fetch, the `accountKey` bucketing, and the three per-row `MissingFieldError` skip-and-log branches. `AuthRequiredError` subclasses `ProviderAuthRequiredError`, so the scheduler no longer imports anything bank-specific. `engine.py` now has **zero** code references to SpareBank1.

**The dedup keys had to survive byte-identical**, since `tracked_transactions` is primary-keyed on them and YNAB permanently burns every `import_id` it has seen (invariant 6) — a one-character drift would silently re-import an entire history as duplicates. Guarded three ways: the provider calls the existing `transform.py` derivations rather than reimplementing them; a regression test pins the resulting `tracking_key`/`import_id` to **hardcoded literals** (not recomputed from the code under test, which would pass even if both sides drifted together); and a differential check ran identical payloads through both the old inline path and the new provider, confirming equality on key, date, amount, payee, memo and cleared status. `sync/import_ids.py` now centralizes the hashing while each source keeps its prefix as a **frozen literal** — `"SB1:"` must never be computed from `type_name()`.

**Output seam.** `NotificationSink` (`notifications/`) with `MqttSink` wrapping the existing `mqtt/` package verbatim and `NullSink` for headless operation; `mqtt.enabled` added and `AppConfig.mqtt` made optional. `scheduler.py` no longer imports `aiomqtt` at all, and the reconnect-with-backoff loop moved into `MqttSink.commands()`. One deliberate behaviour change: publishes are now best-effort rather than propagating. Previously a publish failure aborted the cycle, so **a dead broker would stop bank syncing entirely** — now sync continues and MQTT reconnects independently. MQTT is observability, never a correctness dependency.

**Mappings moved to SQLite** (`account_mappings`), so the GUI can edit them at runtime — this deliberately overturns the old "no config editing" non-goal, *for mappings only*; secrets stay in YAML. `config.yaml`'s `accounts:` list is now read once, on first startup, purely to migrate an existing install, and ignored thereafter. The seed copies `sparebank1_account_key` into `provider_account_id` **byte-for-byte**, with an adversarial byte-equality test, because that string prefixes every tracking key already written. Config's fail-fast duplicate checks moved to write-time validation in `create_mapping`/`update_mapping` (`MappingValidationError` → HTTP 422) — a startup-only check would be trivially bypassed by the GUI.

**Config reshaped** to a `providers:` map discriminated on `type`, so several connections of the same type can coexist (the SpareBank1 alliance is many separate banks). Tokens moved from a single `state/tokens.json` to per-provider `state/tokens/<name>.json`, **with an automatic migration** — without it an existing install would look unauthenticated and force a pointless BankID re-login.

### Bugs found and fixed along the way

- **`_backfill_duplicates` could crash an entire sync cycle.** `_match_transfers` pops `payee_name` off a transfer primary's payload (replacing it with `payee_id`), but `_backfill_duplicates` read it back with `[]` instead of `.get()`. A transfer leg returned in `duplicate_import_ids` — which happens on a retry after partial failure, or with overlapping cycles — raised `KeyError` and took down the cycle. Both the pop and the unguarded read were on normal paths; they just had to coincide. The regression test was verified to genuinely reproduce it (`KeyError: 'payee_name'`) before the fix was applied. `payee_name` now rides on `_PendingCreate` independently of the payload dict, making it structurally impossible.
- **`readd_deleted_transaction` crossed dedup domains.** It always minted an `SB1:`-prefixed id, even re-adding a file-imported row. Since the id is always brand-new this was a mislabel rather than a live collision, but it violated invariant 7's separation; it now re-derives inside the original row's own domain via `import_ids.prefix_of`.
- **File-import error counts always rendered blank.** The backend sent `summary["error"]` while the frontend typed `errors`. Aligned on `errors`.
- **Transfer matching could miss real pairs across providers.** `TransferCandidate.account_key` was an unqualified account id; two providers legitimately using the same id string would look like one account and suppress the match. Now scoped as `{provider_type}:{provider_account_id}`.

### Testing gaps closed

Nothing proved the seam worked with more than one provider, because there had only ever been one — every engine test would still have passed if the engine silently consulted only the first. Added `test_engine_multi_provider.py` with two fake providers, covering multi-provider fetch, two providers sharing an account id, an unconfigured provider being skipped rather than fatal, disabled mappings, and the engine (not the provider) owning the per-account date cutoff. Also added the previously-untested unrecognized-`accountKey` branch, and token-migration tests including the clobber-protection case. A shared `tests/conftest.py` replaced the duplicated helpers in `test_engine.py`/`test_webapp.py`.

149 → 215 tests, `ruff` clean throughout.

## Follow-up: mapping creation was broken by a frontend/backend field mismatch

First real use of the new Mappings tab failed on every drop with a 422: `{"type":"missing","loc":["body","provider"]}`. Root cause was a contract mismatch between two halves built in parallel — `/api/providers` returned the field as `type`, while `frontend/src/api/client.ts`'s `ProviderInfo` declared `type_name`. The frontend read `undefined`, `JSON.stringify` dropped the key entirely, and the backend correctly rejected a body with no `provider`.

Fixed by naming the thing correctly on both sides rather than just picking one spelling: the endpoint now returns **`name`** (the provider's config key — exactly what `account_mappings.provider` stores, and what a client must send back) alongside **`type`** (the implementation type, display only). They are genuinely different: two SpareBank1-alliance banks share a `type` but must never be conflated, so `type` was never a usable identifier. The existing multi-provider test was keying its assertions by `type` and would have collapsed two entries into one — updated to key by `name` and to assert both fakes share a type.

**Why nothing caught it**: the backend tests asserted whatever the backend happened to produce, and the frontend has no tests, so the contract only existed in prose. Also asserts the `mapped` flag flips after mapping, since the UI greys out accounts with it.

## SpareBank1 no longer imports PENDING transactions

**Root cause**: the user confirmed against real data that SpareBank1's `amount` field can be wrong while a transaction is still `PENDING` (a preauth/hold amount that differs from what it actually settles at — normal bank behavior, not a parsing bug). Previously, `_classify()`'s pending→booked "transitioned" branch was relied on to correct the amount once the transaction booked — but that branch only fires if the tracking key (`nonUniqueId`/`creditCardIdentifiers.nonUniqueId`) survives the transition unchanged, which is exactly the unproven hypothesis in `CLAUDE.md`'s "Known open risk." A wrong pending amount could therefore persist indefinitely if the hypothesis is false for a given transaction.

**Fix**: `providers/sparebank1/provider.py`'s `fetch()` now skips `PENDING` rows entirely (logged at debug level) rather than normalizing and returning them — a transaction is only imported once SpareBank1 reports it `BOOKED`, with its real, final amount. This is the "accepted contingency" `CLAUDE.md` already documented for the dedup-key-stability risk, now adopted for a more direct reason, and it matches how the sibling project `../ynab-auto-bank` sidesteps the same hazard. `engine.py`'s "transitioned" branch is unchanged and still needed — it's what correctly resolves any `tracked_transactions` row that was already `PENDING` from before this change once its real-world transaction books. Three existing tests incidentally exercised `PENDING` transactions as an implementation detail of scenarios not actually about pending state (a delete-resolution test, the `id`-instability regression test) and were switched to `BOOKED` fixtures instead, since that's what those code paths actually see in production now; a fourth was rewritten to assert the new skip behavior directly.

## Cycle-failure retry with exponential backoff

**Trigger**: after restarting for the PENDING-import fix above, the user hit a real SpareBank1 500 error - unrelated to that change - and it exposed a real gap: a failed cycle just sat there as one recorded failure until the next cron fire, hours later, with no attempt to recover sooner.

**Design**: `scheduler.py`'s `_attempt_cycle()` now retries a failed cycle with exponential backoff (`sync.retry_backoff_base_seconds * 2**attempt`, capped at `sync.retry_backoff_max_seconds` - new tunable `SyncConfig` fields, defaults 60s/1800s), but only up until the next scheduled cron fire - once a computed retry delay would land at or after that fire, retrying is abandoned (that fire attempts a fresh cycle anyway, so a race would be redundant) rather than continuing indefinitely. The retry wake-up folds into `_run_loop`'s existing `asyncio.wait(timeout=...)` (`_seconds_until_next_wake()` = min of the cron-fire timeout and any pending retry deadline), so a retry wait is interruptible by `stop`/`sync_now` exactly like the normal cron wait already was - no new event-loop machinery needed.

**The "keep data in memory" requirement drove a real engine refactor**: a failed *provider fetch* has nothing worth caching, but a failed *YNAB write* does - retrying that should only re-hit YNAB, never re-poll the provider (SpareBank1) just because YNAB is what's down. `sync/engine.py`'s `run_cycle()` was split into `fetch_and_classify()` (provider reads + local classification, returning a new `ClassifiedCycle`) and `submit()` (the YNAB writes), with `run_cycle()` kept as a thin composition of the two for every other caller. `scheduler.py` calls the two phases directly: a fetch-phase failure retries from scratch; a submit-phase failure caches the `ClassifiedCycle` and retries only `submit()`. This is safe without extra bookkeeping because `submit()` was already idempotent on retry by construction - YNAB's `import_id` dedup (invariant 1) and `update_transactions`' idempotent PATCH payloads mean resubmitting an already-succeeded budget's creates alongside a still-failing budget's is harmless (reported back as `duplicate_import_ids`, not double-created) - confirmed by tracing the exact code path rather than assumed.

**Explicit exclusion**: `ProviderAuthRequiredError` does not get backoff-retried - a revoked OAuth token needs a human BankID re-login, so retrying on a timer against the same broken credentials achieves nothing and just adds log noise. Unchanged from before this feature: an auth failure waits for the next natural cron fire, same as always.

**Clearing on success**: any successful cycle - cron-fired, a backoff retry, or a manually-triggered "sync now" - clears all retry state (attempt count, retry deadline, cached `ClassifiedCycle`) via `_clear_retry_state()`. A user hitting "sync now" is exactly how someone breaks out of an ongoing backoff loop after fixing whatever was wrong - this was an explicit requirement, not just a nice-to-have.

**File import gets none of this, on purpose**: `POST /api/import` is a single user-initiated request, not a background loop - retrying it with backoff would just hang the HTTP request. `webapp/routes/file_import.py` now catches `httpx.HTTPStatusError`/`TransportError` from the commit call and reports a 503 with a new sarcastic-but-clear message pool (`import_messages.ynab_unavailable()`, matching the existing tone of `unrecognized_format()`/`no_account_resolved()`), telling the user to retry the upload manually later.

**Known, accepted tradeoff, documented rather than silently accepted**: cached classified data can be resubmitted for as long as the retry loop runs before the next cron fire (up to several hours with large cron gaps and the 30-minute backoff cap), so any genuinely new bank transactions during an extended YNAB outage won't be picked up until the next cron-fired fetch. This directly matches what was asked for (avoid hammering the provider's API during a YNAB-side outage) and was judged an acceptable staleness window, not a bug.

235 tests passing (7 new scheduler retry/backoff tests, 1 new file-import-503 test), `ruff` clean.

## Docker image: fixed hardcoded `uid 1000` breaking Unraid deployments

**Found via a real first-deployment attempt on Unraid**, root-caused live rather than guessed: the container kept crashing at startup with `sqlite3.OperationalError: unable to open database file` from `StateDB.__init__`, even though `config.yaml` parsed fine and the volume mounts (confirmed via `docker inspect`) were exactly right. ## Transfer-matching false positive, fixed via account-number cross-reference (found from real production data)

**Root cause, found by fetching live data, not by inspecting code**: `sync/transfers.py::find_transfer_pairs()`'s existing rule - opposite-sign, equal-amount, different-account, within a 4-day window - is exactly what the module's own docstring already flagged as an accepted false-positive risk, and it fired for real: a 158.48 kr salary deposit got linked as a "transfer" to an unrelated 158.48 kr REMA 1000 grocery purchase on a different account, 4 days later (right at the window edge). Since a matched transfer's secondary leg is never submitted to YNAB at all (it's replaced by YNAB's own auto-created linked transaction), this wasn't just "linked wrong" - the real grocery transaction's own description/payee/memo would have been silently lost.

**First design tried and abandoned**: a hand-curated allowlist of SpareBank1 `typeCode` values that read as "transfer" (e.g. `R_260` "Overførsel mellom egne kontoer"). This correctly rejected the 158.48 false positive and matched a genuine 39722.10 kr bank-to-bank transfer (confirmed live - both legs carry explicit transfer-labeled type codes) - but failed a third real case, a credit-card bill payment (18289.30 kr), found by looking up one specific transaction id at the user's request. Neither leg of a real credit-card payment carries a typeCode that reads as "transfer" at all (`PAYCTDOMOUPKID` "Betaling med KID" on the checking side, `K_0047` generic "Transaksjon" on the card side) - a structural gap in the taxonomy, not a fixable oversight, since SpareBank1 apparently doesn't model card payments as an "internal transfer" transaction type the way it does for plain bank-to-bank moves.

**Fix, based on a stronger signal found in the same live data**: every SpareBank1 transaction carries a real account-number cross-reference - `accountNumber.value` (the owning account's own number, nested, present on every transaction including credit cards) and `remoteAccountNumber` (the counterparty's real number when known, with a `"-1"` sentinel meaning "not applicable" - confirmed on every card purchase). `find_transfer_pairs` now additionally requires `c.remote_account_number == other.account_number` **or** `other.remote_account_number == c.account_number` - deliberately OR, not AND, between the two directions. The genuine 39722.10 kr transfer has both directions resolve correctly; the genuine 18289.30 kr credit-card payment only has ONE direction resolve (the checking leg names the card issuer's own internal clearing account, "Sparebank 1 Kreditt AS", rather than the card itself - but the card's own transaction feed, description "Innbetaling", correctly names the checking account back) - which is exactly why OR was required, not AND, and exactly the case the typeCode design couldn't have covered no matter which codes were added to its allowlist. The 158.48 false positive is independently rejected by this signal too - neither leg names the other's real account number.

Threaded provider-agnostically per this project's existing pattern (`NormalizedTransaction` → `_PendingCreate` → `TransferCandidate`, mirroring how `booking_status`/`payee_name` already flow through the same chain): new `NormalizedTransaction.account_number`/`remote_account_number` (both `str | None = None`, so any provider/test that doesn't populate them simply never participates in transfer-matching - a safe default, not a regression, since SpareBank1 is the only provider today), populated by new `transform.get_account_number()`/`get_remote_account_number()` getters (neither raises `MissingFieldError` - no signal means "just import normally," never a skipped row). A Plan-agent design review (before the credit-card case was found) validated the overall approach and specifically recommended keeping `sync/transfers.py` unmodified in favor of pre-filtering in `engine.py` - that recommendation applied to the (now-abandoned) typeCode design, where a simple per-candidate boolean allowed pre-filtering; the account-number check is inherently pairwise (it compares one candidate's fields against another's), so `sync/transfers.py`'s `TransferCandidate`/`partners_of()` had to change after all once the design pivoted.

**Method note**: root-caused entirely from real data, not guessed - a one-off diagnostic script (never committed, deleted after use along with its transaction-data dump) fetched the user's own live SpareBank1 transactions using a freshly re-authenticated local token (the original local token had gone stale, rejected with `invalid_grant`, most likely because refresh tokens rotate on every use and the NAS deployment's own copy had since rotated forward - re-running `scripts/auth_setup.py` locally produced an independent token pair, avoiding any risk to the NAS's live sync). This matches the project's standing "live-verify any new or changed assumption" rule about as literally as it gets.

284 tests passing (13 new/updated: `test_transform.py`'s new getters, `test_sparebank1_provider.py`'s field-wiring test, `test_transfers.py`'s cross-reference cases including the asymmetric one-direction case, `test_engine.py`'s updated transfer fixture plus a new direct regression test for the 158.48 scenario), `ruff` clean.

## Audit Log tab: account column, account filter, sortable headers

Follow-up to the Audit Log feature above, requested after using it: the table had no way to tell which of several accounts a row belonged to, or to sort/filter by anything other than category.

**`audit_events` gained an `account_key` column** — the same provider-account identifier `tracked_transactions.account_key` already uses, stamped at every existing write site (`_record_created`/`_record_transfer_secondary`/the update loop/`_backfill_duplicates`'s three sub-cases/`fetch_and_classify()`'s two skip branches/`import_file_rows()`'s duplicate hook). `_PendingUpdate` gained an `account_key` field alongside its existing `provider_type` to make this possible for the `updated` case. For a malformed-row skip, the account is known to the provider even though the row itself never became a `NormalizedTransaction` — it now flows up through the existing `SkipCallback`'s `context` dict (`{"account_key": ..., "raw": ...}`, already present since the initial audit-log build, just not consumed until now).

**Sorting is server-side, not client-side** — `list_audit_events()` gained `sort_by`/`sort_dir` parameters, both validated against an explicit allowlist (`StateDB.AUDIT_EVENT_SORT_COLUMNS`) before being interpolated into the `ORDER BY` clause, since this is the one place in the codebase where a column name (not just a value) reaches raw SQL. Client-side sorting wasn't an option: the table is paginated via `offset`, so only one page is ever loaded in the browser at a time - sorting what's in memory would just reorder that one page, not the underlying dataset. The GUI's column headers are now clickable, toggling direction on a repeat click of the same column.

**Account filter reuses `GET /api/status`'s existing `accounts` list** rather than adding a new endpoint - the same list `Import.tsx`'s account-override dropdown already fetches, so `AuditLog.tsx` follows that exact precedent (fetch on mount, `<select>` with `display_name` as the label, raw `account_key` as the value) instead of inventing a new pattern.

**Incidental fix along the way**: `providers/sparebank1/provider.py` had memo extraction disabled (`memo=None` where `_extract_memo(sb1_tx)` used to be) from unrelated prior work, which meant `NormalizedTransaction`'s required `memo` argument was missing entirely and crashed every real fetch. Completed the change without reverting the memo-skip itself - passed `memo=None` explicitly rather than restoring extraction, since that wasn't this task's concern.

323 tests passing (8 new/updated: `StateDB`'s `account_key` filter + sort-column/sort-direction validation including the SQL-injection-shaped rejection case, the webapp route's equivalents, and `account_key` assertions added to five existing engine-level audit tests covering create/transfer/unmapped-account/stale-window/malformed-row scenarios), `ruff` clean, `tsc && vite build` clean. Live-verified via a two-account throwaway server and a real browser check: the account filter correctly narrows to one account, and clicking the Payee header sorts ascending then descending with the arrow indicator following correctly.
