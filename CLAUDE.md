# CLAUDE.md

Guidance for Claude Code sessions working on this repo. Keep this file up to date as the project evolves — it's meant to save a future session from re-deriving hard-won context, not to duplicate what's already clear from reading the code.

## What this project is

A long-running Python service that pulls bank transactions from one or more **providers** and imports them into YNAB, with zero duplicate transactions guaranteed. SpareBank1 (accounts + credit cards) is the only provider implemented today, but it sits behind a seam (`providers/`) rather than being wired into the core. Also: status/control over MQTT for Home Assistant (optional — it can run with no broker at all), a bundled admin GUI, and a spreadsheet-import path for historical bank exports. Every source — live poll or file import — shares **one** dedup/tracking/classify core, so no two of them can double-book the same real-world transaction. Runs on a cron schedule (default: six times a day, nothing overnight) rather than continuous polling.

Two things are deliberately NOT abstracted: **YNAB** is the one and only target, hardcoded on purpose; and the **dedup guarantee** is centralized rather than delegated to each source.

## Architecture map

- `src/ynab_auto_sync/config.py` — pydantic v2 config model, loaded from `config/config.yaml` (gitignored, real secrets — never read or print its contents). `providers` is a `dict[str, ProviderConfig]` discriminated on `type`, keyed by a **user-chosen name** — that key is what `account_mappings.provider` stores and what names the provider's token file, so renaming it orphans that provider's mappings until they're re-pointed (deliberate: silently re-matching by type could re-route real money to the wrong account). Several entries of the same `type` are supported and expected (the SpareBank1 alliance is many separate banks). The remaining `model_validator` only checks what config.yaml alone can still get wrong: unresolvable YNAB budget aliases on the legacy `accounts:` seed list, an invalid `sync.cron_expression`, and a `sync.retention_days` below the still-reachable fetch horizon. **Duplicate-account and duplicate-`import_source_name` checks deliberately no longer live here** — mappings are runtime-mutable now, so a startup-only check would be trivially bypassed by the GUI; they moved to write-time validation in `StateDB` (see invariant 10). `AccountMapping`/`accounts` survives ONLY as the one-time seed source for `account_mappings`; nothing reads it after the first startup. `notifications: NotificationsConfig | None = None` holds discrete-event-notification provider config (`NotificationsConfig.ntfy: NtfyConfig | None`) — nested rather than a flat top-level `ntfy:` field so a future second provider slots in without another `AppConfig` field each time. This is unrelated to `mqtt`/`gui` above: those drive the *state* sink (`notifications/`), this drives the *event* notifier (`alerts/`) — see that package's architecture-map entry and "Discrete event notifications" below. `api_response_logging: ApiResponseLoggingConfig = Field(default_factory=ApiResponseLoggingConfig)` — always-present-with-default like `logging` above (not `Optional[...] = None` like `mqtt`/`notifications`), since it's a debug toggle with its own `enabled: bool = False`, not "absent means off." No cross-field validation needed (unlike `sync.retention_days`) — see `api_response_logging.py`'s own architecture-map entry. `SyncConfig.manual_match_window_days: int = 0` (opt-in, disabled by default) and `SyncConfig.match_window_unit: Literal["calendar_days", "working_days"] = "calendar_days"` (shared with `transfer_match_window_days`) drive the manual-transaction-matching feature — see "Manual-transaction matching (opt-in)" below.
- `src/ynab_auto_sync/providers/sparebank1/auth.py` — OAuth2 + BankID token lifecycle; `AuthRequiredError` subclasses the provider-neutral `ProviderAuthRequiredError` so `scheduler.py` never imports a bank-specific exception. `client.py` — accounts/transactions fetch, decorated with `http_retry.retry_get`. `get_transactions()` takes a **list** of account keys and fetches all of them in ONE request (confirmed live via `scripts/probe_multi_account_transactions.py` that SpareBank1 accepts a repeated `accountKey` query param and returns the genuine union, each row tagged with its own `accountKey` field — a comma-joined single value is explicitly rejected with 400).
- `src/ynab_auto_sync/ynab/client.py` — YNAB API calls: `create_transactions` (bulk POST), `update_transactions` (bulk PATCH — confirmed live it silently IGNORES an `import_id` key, see "Manual-transaction matching" below), `delete_transaction` (single DELETE — deleting an already-deleted transaction returns 404, not idempotent success, confirmed live), `find_transaction_by_import_id` (resilience lookup), `list_unimported_transactions` (an account's own no-`import_id`, not-deleted transactions — the manual-transaction-matching feature's candidate pool), `get_budgets`, `get_payees` + `find_transfer_payee_id` (used by `engine.py`'s transfer-matching — see invariant 8). `YnabAccountsCache` wraps `get_accounts()` behind a per-budget, 5-minute TTL cache (`ACCOUNTS_CACHE_TTL`, mirroring `providers/sparebank1/provider.py`'s own `_ACCOUNTS_CACHE_TTL`/`list_accounts()` cache for the identical reason — a Mappings-tab visit shouldn't re-hit YNAB's live `/accounts` endpoint every time); instance-level, no lock, same "one asyncio event loop per process" reasoning as `StateDB`'s own concurrency notes. Constructed once per process in `webapp/app.py`'s `create_app()` and served via `webapp/routes/providers.py`'s `GET /api/ynab/accounts?force_refresh=`.
- `src/ynab_auto_sync/sync/sanitize.py` — `clean_bank_text()`, a small ported-and-trimmed subset of sibling project `../ynab-auto-bank`'s description-cleaning rules (strip leading `=`, replace `*` word-separators with spaces, remove parenthesized account numbers, collapse whitespace). Applied to payee/memo on both the live-poll (`transform.py`) and file-import (`file_import/transformers/norwegian_bank.py`) paths, so formatting is consistent regardless of source. Deliberately does NOT port that project's "strip standalone CRV marker" rule — unconfirmed for SpareBank1 data, see the module's own comment.
- `src/ynab_auto_sync/sync/ynab_payload.py` — bank-agnostic construction of the YNAB create-transaction dict (`{"account_id", "date", "amount", "payee_name" or "payee_id", "memo", "cleared", "approved", "import_id"}`) via `build_create_payload()`, plus the two YNAB field-length caps `YNAB_PAYEE_NAME_MAX_LEN`/`YNAB_MEMO_MAX_LEN` (moved out of `transform.py`, which re-exports both for backward compatibility). Extracted specifically so `engine.py`'s file-import path no longer had to reach into the SpareBank1-specific `transform.py` just to get YNAB's own length caps — that was an open/closed violation blocking a multi-provider refactor. `build_create_payload()` takes only already-normalized values (a `date`, int milliunits, plain strings) and never a raw source dict; its `import_id` parameter is a pure passthrough — it must never derive, hash, or re-prefix it (see invariant 6, YNAB permanently burns an import_id). Its optional `payee_id` parameter, when given, is emitted INSTEAD of `payee_name` (YNAB treats them as mutually exclusive on create — see invariant 12). Used by both `transform.transform_transaction()` (live-poll path) and `engine.import_file_rows()` (file-import path); `sync/file_import/transformers/norwegian_bank.py` still has its own separate copy of the two length constants, not yet consolidated onto this module.
- `src/ynab_auto_sync/providers/` — **the input seam** (mirrors the older `sync/file_import/` registry pattern). `base.py`: `TransactionProvider` ABC (`type_name()`/`list_accounts(force_refresh=False)`/`fetch(since_by_account, on_skip=None)`), `NormalizedTransaction`, `ProviderAccount` (`account_type` has no fixed vocabulary across providers — SpareBank1 confirmed live to send `"USER"`/`"SAVING"`/`"CREDITCARD"`, not the `"checking"`/`"credit_card"` an earlier, never-verified version of this docstring guessed), `BookingStatus`, `ProviderAuthRequiredError`. Its docstrings carry the load-bearing knowledge a new provider's author needs — read them before adding one. `fetch()` takes a **per-account** window map and may over-fetch (a provider batching several accounts into one upstream call uses `min(...)`); the ENGINE applies the authoritative per-account cutoff, and a provider must never drop a row for being too old. Per-row robustness is the provider's job: one malformed row is logged and skipped, never raised. `SkipCallback` + `report_skip()` (mirrors `engine.py`'s `ProgressCallback`/`_report()` shape exactly) is the optional, default-`None`, best-effort hook a provider calls once per genuinely malformed row it drops — backs the GUI's Audit Log "skipped" category (see `state_db.py`'s `audit_events` entry below); a provider must NOT call it for routine, expected per-cycle skips (e.g. SpareBank1's PENDING-row skip), only for structurally-malformed data — see `fetch()`'s docstring for the exact line. `registry.py`: `REGISTRY`/`register`/`get_provider_class`. `sparebank1/provider.py`: `SpareBank1Provider`, which owns what used to be inline in `run_cycle()` — the batched fetch, `accountKey` bucketing, and the three per-row `MissingFieldError` skip-and-log branches, each of which also calls `report_skip()` alongside its existing `logger.error()`. `fetch()` also skips every `PENDING` row outright (logged at debug level, `report_skip()` deliberately NOT called) rather than normalizing and returning it — SpareBank1's `amount` is not reliable until a transaction books, confirmed against real data; see "Resolved: SpareBank1 PENDING transactions are no longer imported at all" below. `list_accounts()` is TTL-cached (`_ACCOUNTS_CACHE_TTL`, 5 minutes; instance-level, no lock needed — long-lived per-process singleton on one event loop, same reasoning as `StateDB`'s own concurrency notes) so a Mappings-tab visit doesn't re-hit the live `/accounts` endpoint every time; `force_refresh=True` (wired from the GUI's "Refresh" button through `GET /api/providers?force_refresh=true`) bypasses it. It also runs each account's raw `name` through `_friendly_account_name()` — confirmed live (`GET /personal/banking/accounts?includeCreditCardAccounts=true`) that a regular checking/savings account's `name` is already a real personal nickname (never touched), but a credit card's `name` is a masked card number (e.g. `"**** **** **** 3431"`) while its `description` holds the real product name (e.g. `"Mastercard Ung"`) — the masked case is replaced with `f"{description or type_label} •{last4}"`. A name that doesn't match the masked-number regex is returned completely untouched, so this can only improve on today's floor, never regress it. This is separate from — and doesn't touch — `account_mappings.display_name`, which is set once at mapping-creation time and only reflects the fix for accounts mapped *after* it shipped; `Mappings.tsx`'s existing-mappings table has its own click-to-edit rename (`doRename`/`updateMapping(id, {display_name})`, no backend change needed since `display_name` was already in `StateDB._MAPPING_UPDATABLE_FIELDS`) for anything mapped before.
- `src/ynab_auto_sync/providers/sparebank1/transform.py` — SpareBank1 transaction dict → YNAB transaction payload (payee/memo run through `sanitize.clean_bank_text` before truncation, final dict assembled via `ynab_payload.build_create_payload()`). Owns the tracking-key and dedup-id derivation for the *live-poll* path — see "Core invariants" below, this is the most correctness-sensitive file in the project. The `"SpareBank1 transaction"` fallback payee string is bank-specific and deliberately stays here rather than in `ynab_payload.py`. `get_account_number()`/`get_remote_account_number()` extract the transfer-matching cross-reference fields (see invariant 8) — neither raises `MissingFieldError` like the other getters here do, since a transaction with no recognizable account number should just never participate in transfer-matching, not be skipped/logged as malformed. `PAYEE_NAME_CANDIDATES` (payee) vs. `MEMO_FIELD_CANDIDATES` (memo) are deliberately DIFFERENT tuples, not the same list reused — confirmed live against 25 real booked transactions that memo never once carried information payee didn't already say (either byte-identical, or differing only by a payment-processor prefix like `"Vipps*"`/`"Zettle_*"` that `cleanedDescription` already strips for payee). `MEMO_FIELD_CANDIDATES` prefers `cleanedDescription` too (fixing that prefix case) but deliberately EXCLUDES `remoteAccountName` — including it would make memo mathematically guaranteed to always equal payee whenever a named counterparty exists (same field, same first-hit), permanently defeating the suppress-when-identical check below instead of just correctly applying it. Both `provider.py`'s `_extract_memo(sb1_tx, payee_name)` and this file's `transform_transaction()` compute payee first, then suppress memo to `None` whenever it's identical to payee after cleaning (case-insensitive, whitespace-normalized) — `transform_transaction()` is confirmed dead in the live `fetch()` path (`provider.py` reimplements everything locally per its own docstring) but is kept behaviourally in sync since its own tests still exercise it.
- `src/ynab_auto_sync/sync/file_import/` — the analogous dedup/transform layer for the *file-import* path (a different source, same no-duplicates guarantee, deliberately generic naming since xlsx is only today's first format — see invariant 7): `base.py` (`TransformerBase` OCP contract: `can_handle(headers)`/`name()`/`transform(rows)`, `ImportedTransactionRow`, `RowTransformError`), `registry.py` (`REGISTRY`/`register`/`detect_transformer`), `parsing.py` (`parse_file(filename, data)` — dispatches on extension, `.xlsx` today via openpyxl, a future `.csv` branch slots in without touching transformers), `dedup.py` (`compute_dedup_key`/`get_tracking_key`/`derive_import_id`, prefix `"FILE:"`), `transformers/norwegian_bank.py` (the one registered transformer so far, payee/memo also run through `sanitize.clean_bank_text`).
- `src/ynab_auto_sync/sync/transfers.py` — pure-function matching only (`TransferCandidate`, `find_transfer_pairs`), no I/O, deliberately decoupled from `engine.py`'s internal types so it's independently testable. `TransferCandidate.account_number`/`remote_account_number` (both `str | None`) carry SpareBank1's real account-number cross-reference — see invariant 8 for the full matching rule, why it's OR not AND between the two directions, and the false positive that motivated it. `find_transfer_pairs`' date-window check goes through `sync/date_window.py`'s `days_between()` (a new `unit` parameter, default `"calendar_days"` so no existing call site's behavior changes) rather than a raw `abs((...).days)` — see "Manual-transaction matching (opt-in)" below for why this became shared, configurable behavior instead of transfer-matching-only.
- `src/ynab_auto_sync/sync/date_window.py` — `days_between(d1, d2, unit)`, shared by `transfers.py`'s transfer-matching (invariant 8) and `engine.py`'s manual-transaction-matching (below). `unit="working_days"` counts business days via `workalendar.europe.Norway()` (a module-level, stateless, reusable instance) — confirmed live that `get_working_days_delta()` is already order-independent and correctly excludes both weekends and Norwegian public holidays (e.g. Good Friday → the following Tuesday is 1 working day, not 4 calendar days).
- `src/ynab_auto_sync/sync/engine.py` — **provider-agnostic**: it knows only the `TransactionProvider` contract and consumes `NormalizedTransaction`s. It has zero code references to SpareBank1 (keep it that way). Constructed as `SyncEngine(config, http_client, db, providers)`. `run_cycle()` is a convenience composition of two phases now exposed separately so `scheduler.py` can retry just one of them (see "Cycle-failure retry with backoff" below): `fetch_and_classify()` — read enabled mappings from the DB → `_compute_fetch_windows()` (cursor + overlap, widened by any still-pending transaction — generic, stays in the engine) → `provider.fetch()` per provider → `_classify()` → **match transfer pairs** (`_match_transfers`, invariant 8) → returns a `ClassifiedCycle` — then `submit(classified)`: batch create/update per YNAB budget → persist tracking. `submit()` is safe to call more than once with the same `ClassifiedCycle`, including after a prior partial failure — every write it makes is naturally idempotent on retry (YNAB's `import_id` dedup, invariant 1, and `update_transactions`' idempotent PATCH payloads), which is exactly what makes the retry design below safe without extra bookkeeping. Both phases take an optional `on_progress: Callable[[str, dict], Awaitable[None]] | None = None` (default `None` everywhere, so every existing caller is unaffected) — called once per provider before `fetch()` and once per budget before each YNAB write, wrapped in a best-effort `_report()` helper that swallows and logs any callback exception so a broadcast bug can never affect the cycle itself (see "Live GUI push updates" below). `SyncEngine` still has no `NotificationSink` import of its own — the callback is a plain function, not the sink interface, so the engine stays notification-agnostic. `import_file_rows()` normalizes each parsed row into the SAME `NormalizedTransaction` shape and runs it through the SAME `_classify()`, which is what makes "a file import can't double-book what a live poll already imported" structural rather than two code paths agreeing by convention. A mapping naming an unconfigured provider is logged and skipped, never fatal. `readd_deleted_transaction(tracking_key)` is source-agnostic and re-derives the new `import_id` inside the ORIGINAL row's dedup domain via `import_ids.prefix_of` (invariant 7). Has no MQTT side effects of its own (see docstring in the file). `_classify()`'s "new" branch also looks up `db.get_payee_id(ynab_budget_id, ntx.payee_name)` and threads it through to `build_create_payload` (invariant 12); `_record_created()` writes the mapping back from the create response's `payee_id`, but only when the submitted payload had no `payee_id` of its own — a transfer primary's rewritten `payee_id` (see `_match_transfers`, invariant 8) must never be cached under a raw merchant name. `reconcile_payee_mappings()` is the separate maintenance-pass half of the same invariant — see "Payee-mapping reconcile pass" below. **Audit trail**: every `created`/`updated`/`duplicate`/`skipped` outcome writes a row to `db.audit_events` (see `state_db.py` below) immediately alongside the corresponding `tracked_transactions` write, stamped with the provider's own `account_key` (`_PendingCreate.provider_account_id`/`_PendingUpdate.account_key`, or `ntx.provider_account_id` at the two `fetch_and_classify()` skip sites — `_PendingUpdate` gained this field alongside `provider_type` specifically to make this possible, populated in `_classify()`'s `"transitioned"` branch from the same `ntx` already in scope) — `_record_created()`/`_record_transfer_secondary()` write `created` (the latter tagged `"transfer secondary leg..."` in `detail`; the primary leg is tagged `"transfer primary leg"`), `submit()`'s update loop writes `updated` right after `mark_booked()`, all three `_backfill_duplicates()` sub-cases write `duplicate` (distinguished only via `detail`, not a finer `event_type`), and `fetch_and_classify()`'s two defensive skip branches (unmapped account, stale/out-of-window) write `skipped` directly. A malformed-row skip's `account_key` instead flows up through the `on_skip` callback's `context` dict (see `providers/` below) — the provider still knows which account it was fetching for even when the row itself is too broken to become a `NormalizedTransaction`. `import_file_rows()` shares the same `created`/duplicate machinery via `_record_created()`/`_backfill_duplicates()`, plus its own small hook for the file-only "already tracked" duplicate case (`_classify()`'s `"unchanged"` outcome never reaches `_backfill_duplicates()` on this path, since it's filtered out before `pending_creates` is built) — fired only when `not dry_run`, since a preview never actually writes anything. Deliberately NOT audit-logged, to avoid flooding: `_classify()`'s plain `"unchanged"` outcome on the live-poll path, and the provider's routine PENDING-row skip — both are expected, high-frequency, non-diagnostic events, not "something went wrong." **Manual-transaction matching** (opt-in, see the dedicated section below): `_classify()`'s "new" branch, given a per-account `manual_candidates` list, may instead return a `"matched_manual"` outcome (`_PendingManualMatch`); `fetch_and_classify()` populates that list lazily per `ynab_account_id` (only when `manual_match_window_days > 0`, so the disabled case costs zero extra API calls) and routes the outcome into `ClassifiedCycle.matches_by_budget`; `submit()`'s `_record_matched()` creates the replacement transaction FIRST and only deletes the original manual transaction after that succeeds — never the other order — and never indexes the create response positionally (YNAB's own native transaction-matching can echo the still-live original back in the same response; the replacement is found by its own submitted `import_id`, same pattern `_record_created()` already uses for the unrelated transfer-response quirk). `import_file_rows()` deliberately never wires this in (omits `manual_candidates`, defaulting to `None`) — a bulk historical file import isn't the scenario this was built for.
- `src/ynab_auto_sync/sync/state_db.py` — SQLite state: `account_cursors`, `run_metadata`, `tracked_transactions`, `account_mappings`, `payee_mappings`, `audit_events`. Disposable/recoverable by design (see invariants). `audit_events` is a genuinely **append-only** log (autoincrement PK, never mutated once written) — the one table here that's NOT a current-state upsert; it backs the GUI's Audit Log tab and is purely observational, never read by any dedup/classify/submit logic. `insert_audit_event(...)` is one generic write method (mirrors `upsert_tracked`'s single-signature-many-call-sites style) with `event_type` one of `created`/`updated`/`duplicate`/`skipped`, an `account_key` (the provider's own account identifier, same value `tracked_transactions.account_key` uses — mirrors `DeletedTransactions.tsx`'s existing "Account" column convention), and a free-text `detail` for the specific reason — see `engine.py`'s entry above for exactly which outcome writes which event/detail/account_key. `list_audit_events(event_type=None, account_key=None, include_skipped=False, sort_by="occurred_at", sort_dir="desc", limit=50, offset=0)` returns `(rows, total)`; an explicit `event_type` always wins over `include_skipped` (so `?event_type=skipped` works regardless). `sort_by` is checked against `AUDIT_EVENT_SORT_COLUMNS`, a fixed allowlist — never interpolate a caller-supplied column name into the `ORDER BY` clause directly, even though the only caller (`routes/audit.py`) already constrains it via a `Literal` type; `sort_dir` is checked against `("asc", "desc")`. Both raise `ValueError` on an invalid value rather than silently falling back. `count_audit_events_by_type()` is a cheap zero-filled `GROUP BY`, backing the GUI's summary strip — deliberately unaffected by the current `event_type`/`account_key`/`include_skipped` filter, so the strip always shows true totals as a nudge toward categories the current filter is hiding. `prune_audit_events(cutoff_date)` reuses `config.sync.retention_days` (no new config knob) and compares on `date(occurred_at)` rather than the raw datetime string, so "today" is never pruned regardless of what time it currently is. `run_metadata`'s `*_last_run` counters (`fetched_last_run`, `imported_last_run`, `updated_last_run`, `duplicates_last_run`, `resolved_deleted_last_run`) are all set together in `record_success()` and zeroed together in `record_failure()` — `fetched_last_run` is the raw pre-dedup/classification count (`CycleResult.fetched`, sourced from `ClassifiedCycle.fetched_count`), added via the same migration mechanism as `resolved_deleted_last_run` before it (see "Discrete event notifications" below). `run_metadata.log_level` (`set_log_level(level)`) is a fourth kind of thing this table holds alongside cursors/counters/`paused`: a GUI-settable runtime override for the process's log level, `NULL` until ever set (meaning "no override, fall back to `config.logging.level`") — see "Runtime-configurable log level" below. `delete_all_mappings()` is the bulk "clear all" the Mappings tab's clear-all button calls — a single `DELETE FROM account_mappings` with no `WHERE`, returning the row count deleted; only removes the mapping rows, `tracked_transactions`/burned `import_id`s are untouched (invariant 11 still applies — nothing is re-imported on remap). `payee_mappings` (`get_payee_id`/`upsert_payee_mapping`) caches, per `(ynab_budget_id, raw_payee_name)`, the YNAB `payee_id` first assigned to that raw text — see invariant 12; `upsert_payee_mapping` is `INSERT OR IGNORE`, deliberately first-write-wins. `delete_payee_mappings_for_ids(ynab_budget_id, ynab_payee_ids)` is the healing half of invariant 12's reconcile pass (see `SyncEngine.reconcile_payee_mappings()` and "Payee-mapping reconcile pass" below) — deletes cached rows whose `ynab_payee_id` YNAB's own payee list now reports `deleted: true`. A no-op (returns 0, no query run) for an empty `ynab_payee_ids` — deliberately never triggered by an id merely being *absent* from a fetch, since YNAB confirmed keeps deleted/merged payees present in the list with the flag set (unlike guessing from absence, which a transient or incomplete fetch could make dangerously wrong — see that method's own docstring). `tracked_transactions` also persists full reconstruction data (`payee_name`, `memo`, `transaction_date`, `ynab_account_id`, `cleared`, `readd_count`) on every row, not just deleted ones. Every mutating method is `async` and guarded by an internal `asyncio.Lock` (see invariant 9); the connection is opened with `PRAGMA journal_mode=WAL`, `PRAGMA busy_timeout=5000`, and `check_same_thread=False`. `prune_booked_transactions(cutoff_date)` / `maybe_vacuum(min_interval_days)` implement the retention policy (see below — no longer just "recommended"). `account_mappings` (`list_mappings`/`get_mapping`/`create_mapping`/`update_mapping`/`delete_mapping`/`seed_mappings_from_config`/`count_tracked_for_account`) is now **authoritative** for which accounts sync where: `engine.run_cycle()` reads `list_mappings(enabled_only=True)`, and `webapp/routes/mappings.py` lets the GUI edit them. A disabled mapping is skipped at fetch time entirely, and its existing PENDING tracked rows are left untouched rather than pruned, so re-enabling resumes reconciliation instead of orphaning them. `create_mapping`/`update_mapping` re-implement `config.py`'s startup dedup checks as write-time validation (raising `MappingValidationError`) since a mutable table can no longer rely on a one-time fail-fast load-time check; budget-alias validity is still the caller's concern, not validated here. `seed_mappings_from_config(rows)` is seed-once-only (no-op if the table already has any row) and its `provider_account_id` must be copied byte-for-byte from the old `sparebank1_account_key` — see invariant 2/7, a single character of drift breaks every existing `tracked_transactions` match and the burned YNAB `import_id`s that depend on it.
- `src/ynab_auto_sync/state.py` — atomic-write JSON store, used only for the rotating OAuth tokens (deliberately kept separate from the SQLite DB, a different risk profile). Tokens are **per provider** at `state/tokens/<provider-name>.json`; `provider_setup.token_store_path()` owns that path and transparently migrates a pre-existing single `state/tokens.json` on first use, guarded so it can never clobber newer tokens. Without that migration an existing install would look unauthenticated and force a pointless interactive BankID re-login.
- `src/ynab_auto_sync/provider_setup.py` — shared by the service and every `scripts/` tool so they cannot disagree on where tokens live (a script writing to a different path than the service reads would make a successful login look ignored). Also `resolve_sparebank1_provider(config, name)`, which refuses to guess when several are configured rather than risking an interactive login against the wrong bank.
- `src/ynab_auto_sync/sync/import_ids.py` — the shared hash/truncation half of `import_id` derivation (`derive_import_id(prefix, seed)`, `prefix_of`). The **prefix is deliberately NOT decided here** — each source owns its own frozen literal (see invariant 7). Exists so `engine.py` can re-derive an id for a source it knows nothing about (`readd_deleted_transaction`) without importing a provider module.

## Core invariants — do not violate these without re-deriving why they exist

1. **YNAB's `import_id` is the authoritative no-duplicates guarantee, always.** Local SQLite state (`tracked_transactions`) is a performance/tracking layer only — it may be lost or reset without ever causing a real duplicate in YNAB, because `engine.py`'s `_backfill_duplicates` resilience path recovers via `find_transaction_by_import_id()` whenever YNAB reports a submission as a pre-existing duplicate. Never build a design that relies on local state being the source of truth for dedup.

2. **Never derive the tracking/dedup key from SpareBank1's own `id` field.** This was a real, live production bug: `id` was proven to change on *every single poll* of a still-pending credit-card transaction (two fetches of the same real charge, hours apart, returned completely different `id` strings — same `nonUniqueId`, same everything else). The correct key comes from `transform.get_tracking_key(sb1_tx, account_key)`:
   - Prefers `creditCardIdentifiers.nonUniqueId` when present (booked credit-card transactions — a structured, specific field).
   - Falls back to the raw top-level `nonUniqueId` (pending credit-card transactions, and all regular bank-transfer transactions, which never have `creditCardIdentifiers`).
   - Scoped by `account_key` (SpareBank1's own field is literally named "nonUniqueId" — it warns you it isn't globally unique).
   - `get_transaction_id()` (reading `id`) still exists for logging/display only — it must never feed `derive_import_id()` or any `tracked_transactions` key again.

   **Generalized for the provider seam:** every provider must derive `NormalizedTransaction.tracking_key` from a field *proven stable across polls of the same real-world transaction*, verified live against that provider's own API — never from something that might be a per-response id. The warning is restated in `providers/base.py`'s docstring so a future provider's author meets it there rather than rediscovering this bug with a different bank. Also note **`provider_account_id` is load-bearing, not cosmetic**: it prefixes every SpareBank1 tracking key, so it must survive any migration or rename byte-for-byte (see the `account_mappings` seed).

3. **`tracked_transactions` rows are written immediately as each YNAB call succeeds — not deferred to end-of-cycle** — while `account_cursors`/`run_metadata` are only persisted by the *caller* (`scheduler.py`) after the whole cycle succeeds. This split is deliberate: cursor advancement is all-or-nothing per cycle (a failure means next cycle's overlap window retries everything), but transaction tracking reflects real external state the moment it's true, so a later-budget's failure in the same cycle can't cause a retry to re-attempt creating an already-created transaction.

4. **Amounts are float NOK from SpareBank1, converted to YNAB milliunits via `round(amount * 1000)`.** Confirmed live, not a minor-units API.

5. **Dates from SpareBank1 are Unix epoch milliseconds** (`get_transaction_date()` handles this) — a real bug (`ValueError`, not caught) before it was found and fixed. Occasionally an ISO string appears too; both are handled.

6. **YNAB permanently reserves an `import_id` once used, even after the transaction using it is deleted — and its plain (non-delta) transaction list silently excludes deleted transactions.** Confirmed live: a transaction resolved as a "duplicate" that can't be found via `find_transaction_by_import_id()` (account-scoped, plain list) may still exist, just deleted — check with `find_transaction_including_deleted()` (budget-wide, `last_knowledge_of_server=0`) before concluding local state is genuinely broken. When a deletion is confirmed, `_backfill_duplicates` marks the row `booking_status='DELETED'` **permanently** — never retried automatically, by design (an intentional deletion, e.g. a real duplicate cleaned up by hand, must not be silently resurrected). If a deletion turns out to have been a mistake, `SyncEngine.readd_deleted_transaction()` (invoked via `scripts/readd_deleted_transaction.py` or the GUI's DeletedTransactions tab) re-creates it from the persisted payee/memo/date/amount/cleared data with a fresh, derived import_id (the original stays burned forever). **Related, separately confirmed live**: `PATCH .../transactions` silently IGNORES an `import_id` key in an update payload — 200 response, but the field reads back `null` immediately after (`scripts/verify_ynab_import_id_patch.py`). There is no API-level way to retroactively grant an existing transaction real import_id-dedup protection; the only way is to delete it and create a fresh transaction with the import_id set from the start — see "Manual-transaction matching (opt-in)" below for where this mattered.

7. **File-import dedup keys are derived from stable *content* fields (date + amount + casefolded payee + casefolded memo), hashed — never from any row-assigned or file-provided id.** A bank export file has no equivalent of SpareBank1's `nonUniqueId` at all, so this isn't just the safer option, it's the only one — same underlying invariant as #2, applied to a source that never had a candidate id to misuse in the first place. `sync/file_import/dedup.py`'s `IMPORT_ID_PREFIX = "FILE:"` is deliberately distinct from `transform.py`'s `"SB1:"`: the two dedup domains (live-poll vs. file-import) must never collide even if the same real-world transaction is later observed by both paths, since `derive_import_id` hashes only the raw pre-prefix string as its entropy source — a shared prefix would silently and permanently merge two unrelated dedup domains in YNAB. `tracked_transactions.sb1_transaction_id` (the PK column) now holds either a live-poll tracking key (`{account_key}:{raw_id}`) or a file-import one (`file:{ynab_account_id}:{dedup_hash}`) — the column name is a pre-existing misnomer, not a bug; it was already "just the tracking key string" before file-import existed.

   **Prefix rules, now that there can be many sources:** a source's prefix is a **frozen literal** it owns — `"SB1:"` must never be computed from `provider.type_name()` or anything else that could change, because YNAB permanently burns every `import_id` it has seen (invariant 6) and a changed prefix would silently re-import that source's whole history as duplicates. Two sources must never share a prefix. `sync/import_ids.py` centralizes only the hashing/truncation; the prefix stays with the source deliberately. `readd_deleted_transaction` re-derives inside the ORIGINAL row's domain (via `import_ids.prefix_of`) — it used to always mint an `SB1:` id even for file-imported rows, which was a real (if benign, since the id was always fresh) domain crossing.

8. **Account-to-account transfers use YNAB's real, native linked-transfer mechanism — never both sides as independent transactions once matched.** Confirmed live via `scripts/verify_ynab_transfer.py` before this was designed (per the standing rule below), not assumed: creating a transaction with `payee_id` set to the destination account's auto-generated `"Transfer : <name>"` payee (found via `ynab_client.get_payees()`/`find_transfer_payee_id()`) makes YNAB **auto-create the paired transaction on the other account itself** — the caller must never submit both sides. Two load-bearing facts this depends on, both confirmed the same way:
   - **The auto-created side gets `import_id: null`** — YNAB assigns it none. `engine.py`'s `_record_transfer_secondary()` therefore writes a locally-synthesized, clearly-marked `"LOCAL:XFER:..."` import_id for that row's `tracked_transactions` entry — this value was never sent to or recognized by YNAB and must never be reused to attempt a real API call against it.
   - **Transfers only work within one YNAB budget.** `engine.py`'s `_match_transfers()` therefore only ever looks for pairs within one budget's own newly-classified transactions (`creates_by_budget`'s existing per-budget grouping already provides this scoping for free) — a transfer where the two accounts map to different budgets always imports as two ordinary, independent transactions, unchanged from before this feature existed.

   Matching itself (`sync/transfers.py::find_transfer_pairs`) requires opposite-sign, equal-amount, different-account, within `config.sync.transfer_match_window_days` (default 4 — credit-card payments can take until the "next working day" to become visible, confirmed by the user to sometimes exceed 1 calendar day) of each other, **AND** at least one leg's real account-number cross-references the other (see below) — among **only transactions being freshly created this same cycle** — an already-tracked transaction is never retroactively converted into a transfer leg. Ambiguous matches (more than one plausible partner, checked symmetrically on both sides) are skipped entirely, never guessed, matching `_backfill_duplicates`' existing "don't guess" stance elsewhere.

   **Account-number cross-reference, added after a real false positive found via live data**: the sign/amount/account/window rule alone linked a real 158.48 kr salary deposit to an unrelated 158.48 kr grocery purchase on a different account, 4 days later — same amount, opposite sign, nothing else in common, right at the edge of the window. Fetching real transaction data (`GET .../transactions`) turned up two more fields, `accountNumber.value` (the owning account's own real account number, nested, present on every transaction including credit cards) and `remoteAccountNumber` (the counterparty's real account number when known, with `"-1"` as SpareBank1's own sentinel for "not applicable" — confirmed on every card purchase seen). `NormalizedTransaction.account_number`/`remote_account_number` (`providers/base.py`, both `str | None = None`, populated by `providers/sparebank1/transform.py`'s `get_account_number()`/`get_remote_account_number()`) carry these through `_PendingCreate` into `TransferCandidate` (`sync/transfers.py`), which now requires `c.remote_account_number == other.account_number` **or** `other.remote_account_number == c.account_number` — deliberately OR, not AND. A genuine bank-to-bank transfer (confirmed live, 39722.10 kr) has **both** directions resolve correctly. A genuine credit-card bill payment (confirmed live, 18289.30 kr) only has **one** direction resolve: the checking-account leg's `remoteAccountNumber` names the card issuer's own internal clearing account (e.g. "Sparebank 1 Kreditt AS"), not the card itself, but the card's own transaction feed (`typeCode: "K_0047"`, description "Innbetaling") correctly names the checking account back — so requiring both directions would have silently broken all credit-card-payment linking, which is exactly why a hand-curated `typeCode` allowlist (the first design tried) was abandoned in favor of this direct identity check: no SpareBank1 `typeCode` reliably identifies a credit-card payment as "transfer-shaped." A provider/test that never populates `account_number`/`remote_account_number` simply never participates in transfer-matching at all (safe default — two ordinary transactions, not a crash), so this is additive for SpareBank1 only, not a behavior change for a future provider that doesn't implement it.

   **Known residual risk, documented rather than silently accepted**: if the process crashes in the narrow window between `_record_created` writing the primary leg's `tracked_transactions` row and writing the secondary's (two back-to-back local SQLite writes, no network call between them), the secondary could be left permanently untracked. A later cycle would then see it as a fresh "new" transaction from its own account's own fetch and submit it independently — and since YNAB's auto-created secondary has no import_id for that submission to collide with, this specific narrow case would create a genuine duplicate. Not fully solved (would need wrapping both upserts in one atomic DB transaction, a larger `StateDB` change) — deliberately left as a known gap rather than pretending it can't happen.

   Also confirmed live and worth knowing: a transfer-creating submission's `create_transactions` response lists the **same transaction id twice** in `transaction_ids` — `total_created`/`CycleResult.created` is therefore computed from `_record_created`'s own return value (rows actually written locally), never from `len(response["transaction_ids"])`. And YNAB defaults the auto-created secondary's `cleared` to `"uncleared"` regardless of what the primary was created with — if SpareBank1's own data says that leg is already `BOOKED`, `_record_transfer_secondary` immediately issues a follow-up `update_transactions` PATCH to correct it, rather than waiting for a future poll's normal pending→booked transition.

9. **`StateDB` is safe under the concurrency the GUI introduces (a webapp route and a scheduler cycle now routinely overlap on one process, not just rarely via a manual script), via three mechanisms together, not one:** `PRAGMA journal_mode=WAL` (readers don't block on a writer), `PRAGMA busy_timeout=5000` (a writer that finds the DB locked by another *process* waits and retries instead of raising immediately — this is what replaces `scripts/readd_deleted_transaction.py`'s old "if locked, just retry" folklore with an actual mechanism), and an `asyncio.Lock` around every mutating method (serializes writes *within* this process, since the scheduler and the webapp share one event loop per `__main__.py`'s `asyncio.gather`, not separate OS threads). All three matter: WAL/busy_timeout alone wouldn't stop two of this process's own coroutines interleaving mid-transaction (see `_backfill_duplicates`'s awaited network call between a read and a write on the same key); the lock alone wouldn't help a genuinely separate process (e.g. the CLI script run manually) or make concurrent reads fast. `check_same_thread=False` is also required on the connection — not for real concurrency safety (the lock/WAL provide that), but because some ASGI test/runtime paths (confirmed with Starlette's `TestClient`) dispatch into a different OS thread than the one `StateDB` was constructed on even for a fully `async` app.

10. **Mapping invariants are enforced on every WRITE, not at startup — because mappings are now mutable at runtime.** `config.py`'s `model_validator` used to guarantee, once and fail-fast, that no two accounts shared a key and no two shared an `import_source_name`. Moving mappings into the GUI-editable `account_mappings` table destroys that guarantee unless it is re-derived, so `StateDB.create_mapping`/`update_mapping` raise `MappingValidationError` (surfaced as HTTP 422) for a duplicate `(provider, provider_account_id)` — backstopped by a real `UNIQUE` constraint, with `sqlite3.IntegrityError` caught and re-raised rather than leaking a raw sqlite error to an API caller — and for a duplicate non-empty `import_source_name` (checked explicitly; no UNIQUE index is possible since blanks must repeat freely). `webapp/routes/mappings.py` additionally validates `ynab_budget_id` against `config.ynab.budgets.values()` on every write, the third thing the old startup validator covered. If you add a new mapping invariant, it goes in the write path — a startup-only check is now decorative.

11. **Re-pointing an already-synced account at a different YNAB account does NOT move or re-import its history**, because `tracking_key` is scoped by `provider_account_id`, not by the mapping row, and the old `import_id`s are permanently burned in YNAB (invariant 6). This is a genuine, irreversible user-facing consequence, not an implementation detail: `StateDB.count_tracked_for_account()` exists so the GUI can warn before it happens, and `Mappings.tsx` blocks such a change behind a confirmation that says so concretely. Don't "fix" this by re-keying tracked rows on remap — that would re-import everything as duplicates.

12. **A transaction's `payee_name` is only ever an exact-match lookup in YNAB — creating with the same raw text after the user renames/merges that payee in YNAB does NOT reuse the rename, it creates a brand-new payee under the old name.** This was a real reported bug, root-caused by reading the code (every create path always sent `payee_name`, never `payee_id`) and then confirmed live via `scripts/verify_ynab_payee_id.py`: after renaming a payee via the API, resubmitting the original `payee_name` created a second, separate payee, while submitting the same `payee_id` correctly attached to the renamed one. The fix: `StateDB.payee_mappings` (see architecture map) caches the `payee_id` YNAB assigns the FIRST time a given raw `(ynab_budget_id, raw_payee_name)` pair is created; `engine.py`'s `_classify()` looks it up before every create and passes it to `build_create_payload(payee_id=...)`, which then omits `payee_name` entirely (YNAB rejects/ignores neither being informative — the two are mutually exclusive on create, confirmed the same way). `_record_created()` populates the cache from the create response's own `payee_id`, but only for a create that used `payee_name` (i.e. `payee_id` wasn't already set on the outgoing payload) — this excludes a transfer primary leg, whose `payee_id` is YNAB's own transfer payee (invariant 8) and must never be cached under a merchant name. First-write-wins (`INSERT OR IGNORE`) is deliberate: the cached id is a permanent anchor to whatever the user has renamed the payee to, so a later create must never silently overwrite it. **Gap closed**: `SyncEngine.reconcile_payee_mappings()`, called non-fatally from `scheduler.py`'s `_reconcile_payee_mappings()` at the end of every `_do_cycle()`, re-fetches each configured budget's payee list every cycle and deletes any `payee_mappings` row whose cached `ynab_payee_id` YNAB now reports `deleted: true` — never based on absence from the list (see `StateDB.delete_payee_mappings_for_ids`'s docstring). Deliberately does NOT guess what the deleted payee was merged into (YNAB's payee list gives no such linkage, confirmed against sibling project `../ynab-auto-bank`'s identical stance); the next create for that raw payee text simply re-learns a fresh `payee_id` through the normal `_classify()`/`_record_created()` path. See "Payee-mapping reconcile pass" below for the full design and the live-verification of the `deleted` field (`scripts/verify_ynab_payee_deletion.py`).

## Cycle-failure retry with backoff

Added after a real SpareBank1 500 error was observed to just sit as a single recorded failure until the next cron fire, hours later, with no attempt to recover sooner. `scheduler.py` now retries a failed cycle with exponential backoff, entirely on its own (the engine has no retry logic beyond the pre-existing per-GET `http_retry.retry_get`):

- **Backoff schedule**: `sync.retry_backoff_base_seconds * 2**attempt`, capped at `sync.retry_backoff_max_seconds` (defaults 60s / 1800s). Tunable in `config.yaml` without a code change.
- **Bounded by the next cron fire, not open-ended**: before scheduling a retry, `_schedule_retry()` checks whether `now + delay` would land before the next scheduled cron fire (`_next_cron_fire_at()`). If yes, an earlier wake-up is scheduled (`_retry_deadline`, folded into `_run_loop`'s existing wait via `_seconds_until_next_wake()` — the same `asyncio.wait(timeout=...)` that already listens for `stop`/`sync_now`, so a retry wait is interruptible exactly like the normal cron wait). If the delay would land at or after that fire, retrying is pointless — that fire will attempt a fresh cycle anyway — so `_schedule_retry()` gives up instead: clears all retry state and lets the normal cron-triggered attempt happen.
- **Two failure categories, handled differently** (`_attempt_cycle()`): a failure during `engine.fetch_and_classify()` (the provider-hitting phase) has nothing worth caching — the next retry re-fetches from scratch. A failure during `engine.submit()` (the YNAB-writing phase) is different: the already-classified data (a `ClassifiedCycle`) is cached on the scheduler (`_cached_classified`) and reused on the next retry, so a YNAB outage is retried by re-hitting *only YNAB*, never re-polling the provider — this was an explicit requirement, not an incidental optimization. Safe to do because `submit()` is idempotent on retry (see the engine.py architecture-map entry above) — resubmitting an already-created budget's transactions alongside a still-failing budget's is harmless, just reported back as `duplicate_import_ids` YNAB-side.
- **`ProviderAuthRequiredError` is explicitly excluded from backoff retry** — a revoked/expired OAuth token needs a human BankID re-login; retrying against the same broken credentials on a timer achieves nothing and just adds noise. This is unchanged from pre-retry behavior: `auth_required` failures still just wait for the next natural cron fire.
- **Any successful cycle clears all retry state** (`_clear_retry_state()`) — attempt count, retry deadline, and any cached `ClassifiedCycle` — regardless of whether that success came from the normal cron fire, a scheduled backoff retry, or a manually-triggered "sync now" (`POST /api/sync-now` / MQTT `sync_now`). A user manually forcing a sync is exactly how someone breaks out of an ongoing backoff loop after fixing whatever was wrong.
- **Known, accepted tradeoff**: cached classified data can be resubmitted for as long as the retry loop keeps going before the next cron fire (up to several hours with large cron gaps and the 30-minute backoff cap) — meaning any *new* bank transactions that occurred during an extended YNAB outage won't be picked up until the next cron-fired fetch. This matches the explicit request behind this feature (avoid hitting the provider's API repeatedly during a YNAB-side outage) and is judged an acceptable staleness window, not a bug.
- **File import (`POST /api/import`) deliberately has NO retry/backoff at all** — see `routes/file_import.py`'s architecture-map entry above. It's a single user-initiated request, not a background loop; a YNAB failure during the commit is reported straight back as a 503 with a clear message, and the user re-uploads to retry manually.

## Live GUI push updates

The dashboard used to only poll `GET /api/status` every 15s. It now also gets pushed updates over `GET /api/ws` (a new websocket route), with polling kept as an automatic fallback rather than removed:

- **Message envelope**: `{"type": "...", "data": {...}}`. `status_snapshot` (the full `GET /api/status` shape, sent once immediately after a client connects, via a `build_status_payload(config, db)` helper factored out of `routes/status.py` so the REST route and the websocket route can never drift apart), `status` (partial — just `{"run_metadata": {...}}`, mirroring `publish_status`'s existing call sites 1:1), `sync_state` (`{"value": "running" | "idle"}` — `"idle"` is new, see below), `cycle_progress` (`{"phase": "fetching" | "submitting", ...context}`, e.g. `{"phase": "fetching", "provider": "sparebank1", "accounts": 3}`).
- **In-cycle progress is opt-in instrumentation, not a new correctness dependency**: `engine.py`'s `fetch_and_classify()`/`submit()` take an optional `on_progress` callback (default `None`), called once per provider (before `provider.fetch()`) and once per budget (before each YNAB write) — coarse phase boundaries "for free" from where the engine already loops, no new state. Every call is wrapped in `_report()`, which catches and logs any callback exception rather than letting it propagate — a broadcast bug must never turn into a failed (or worse, half-completed) sync cycle. `scheduler.py`'s `_attempt_cycle()` passes a `_report_progress` adapter into both engine calls; `SyncEngine` itself still has zero knowledge of `NotificationSink` or websockets.
- **`sync_state="idle"`** is a new value `_do_cycle()` publishes (after `publish_status`, in the same `finally` block) once an attempt — success or failure — is over. Previously only `"running"` was ever published; MQTT/Home Assistant didn't need the opposite signal, but the dashboard's progress panel does (to know when to hide itself), so this is additive rather than a behavior change for existing MQTT consumers.
- **`CompositeSink` exists because MQTT and the GUI websocket are two independent, both-optional broadcast concerns** (`config.mqtt.enabled` vs `config.gui.enabled`) and `Scheduler` only ever holds one `sink`. `__main__.py`'s `_build_sink()` returns `NullSink()` if neither is active, the single sink directly if exactly one is, or a `CompositeSink` fanning out to both — see the `notifications/` architecture-map entry above for the isolation guarantees. This is the same reason `ConnectionManager` is built once in `main()` and threaded into both `_build_sink()` and `create_app()`: one shared instance, not two.
- **No new auth surface**: `/api/ws` inherits the GUI's existing no-app-level-auth trust model, same as every REST route — the reverse proxy in front of this app is the only boundary.
- **Real bug found and fixed while building this**: FastAPI does not resolve `Depends(...)` functions typed for an HTTP `Request` when used on a `@router.websocket(...)` route — it raises a `TypeError: missing 1 required positional argument: 'request'` at connection time (confirmed live, not from docs). `routes/ws.py` reads `websocket.app.state.*` directly instead of reusing `deps.py`'s `get_config`/`get_db`/`get_ws_manager`.
- **Reverse-proxy dependency, not verifiable from this repo alone**: a websocket connection needs `Upgrade`/`Connection` headers forwarded by the reverse proxy, which `deploy/swag/ynab.subdomain.conf` now sets — but `$connection_upgrade` needs a `map $http_upgrade $connection_upgrade {...}` directive in nginx's `http{}` scope (SWAG's own `nginx.conf`, outside this repo). If missing, the websocket handshake fails **silently from the user's point of view** — the frontend's automatic polling fallback (below) means the dashboard keeps working, just without live updates, so there's nothing that visibly breaks to prompt someone to go check the proxy config.
- **Frontend resilience** (`frontend/src/contexts/SyncStatusContext.tsx`): reconnect with exponential backoff (1s → doubling → capped at 15s, same ceiling `notifications/mqtt_sink.py` uses server-side, reset on a successful connect), and the dashboard's old 15s poll moved into this provider as an automatic fallback — running whenever `connectionState !== "open"`, starting immediately on mount/disconnect and stopping the instant the socket opens, so there's never a gap with no data flowing and never double-fetching once the socket is live. The connection-state indicator (`Dashboard.tsx`'s footer) is a deliberately visible amber badge ("Reconnecting… showing data every 15s") when disconnected, not a quiet footer note — precisely because the proxy-misconfiguration failure mode above is otherwise silent.
- **Server-side heartbeat, not a reverse-proxy timeout override**: `routes/ws.py` sends a `ping` message every 20s of inbound silence (`HEARTBEAT_INTERVAL_SECONDS`), keeping the connection non-idle from the proxy's point of view without requiring the user to also raise a `proxy_read_timeout`-style setting — more portable across whatever reverse-proxy product someone actually has in front of this app, not just SWAG.

## Discrete event notifications (`alerts/`) vs continuous state (`notifications/`)

Two separate output-side seams exist on purpose, both optional, neither aware of the other:

- **`notifications/`** pushes continuous **state** — `sync_state`, `run_metadata` counters, in-cycle progress — to a dashboard (GUI websocket) or Home Assistant (MQTT). This is what existed before this feature and is **unchanged** by it.
- **`alerts/`** pushes discrete **events** — one message per finished cycle, categorized as plain success / success-with-changes / error — to something like a phone (ntfy.sh today). Each of the three is independently toggleable via `NtfyConfig.notify_on_success`/`notify_on_success_with_changes`/`notify_on_error`.

`Scheduler` holds both (`self._sink: NotificationSink`, `self._notifier: EventNotifier`) and calls into each independently from `_attempt_cycle()`; neither seam imports or references the other.

- **Success classification**: `result.created > 0 or result.updated > 0` → `notify_success_with_changes`, else `notify_success`. `duplicates`/`resolved_deleted` alone do NOT count as "changes" — they're not new financial data worth a push notification, unlike a created/updated transaction.
- **Error-notification dedup, an explicit requirement**: the pre-existing retry/backoff mechanism (see above) can retry a failing cycle every 60s–30min for hours during a real outage — without dedup, that would push a notification on every single retry. `Scheduler._maybe_notify_error()` tracks the exact message string of the last error actually pushed (`_last_notified_error`); a repeat of the same message is silently skipped, a different message (or the first failure of a fresh outage) pushes again. Deliberately **not** folded into `_clear_retry_state()`/`_schedule_retry()` — this dedup state must survive "give up retrying, wait for next cron fire" the same way the underlying unresolved error does, and only resets to `None` on an actual success. **Known, accepted limitation**: dedup is by exact message text, so a message that varies slightly between retries (e.g. embeds a timestamp) would defeat it and notify every time — not solved, call it out if ever observed in practice.
- **`fetched_last_run` metric**: added alongside this feature (not strictly part of it) — the raw pre-dedup/classification fetch count already existed as `ClassifiedCycle.fetched_count`/`CycleResult.fetched` but was previously only ever logged. Now persisted (`run_metadata.fetched_last_run`, via the same migration mechanism as `resolved_deleted_last_run` before it), published (new MQTT discovery sensor, forwarded automatically over the GUI websocket/`GET /api/status` since both already forward `read_run_metadata()`'s dict verbatim), shown on the dashboard, and included in ntfy message bodies.
- **Why a new package instead of extending `NotificationSink`**: the two concerns have genuinely different shapes (continuous state with a connection lifecycle + command stream, vs. discrete fire-and-forget events with none) and different failure/config independence requirements (MQTT/GUI vs. ntfy/future providers) — forcing them through one interface would mean either sinks growing unrelated methods or the abstraction leaking one concern's assumptions into the other. Follows the same seam pattern already established twice in this codebase (`providers/`, `notifications/`): an ABC, a `Null*` no-op, a `Composite*` fan-out with per-child isolation, a `_build_*()` constructor in `__main__.py`.

## Runtime-configurable log level

`config.logging.level` used to be the only way to change the log level — hand-edit `config.yaml`, restart the process. The GUI's Dashboard now has a "Log level" dropdown that changes it live, no restart:

- **State, not config — same shape as the account-mappings exception**: `run_metadata.log_level` (`StateDB.set_log_level()`/`read_run_metadata()["log_level"]`) is `NULL` until the GUI control is ever touched, meaning "no override — use `config.logging.level`." `config.yaml`'s value is the seed/fallback a fresh process (or a fresh `state/sync_state.db`) starts with, exactly the same relationship `accounts:` has to `account_mappings` — see the amended non-goals entry above.
- **Applies immediately, not just on next restart**: `webapp/routes/settings.py`'s `PATCH /api/settings` both persists (`db.set_log_level()`) AND calls `logging_setup.configure_logging()` again on the spot. `configure_logging()` was already idempotent (clears and re-adds the one stdout handler, resets the root logger's level) so this needed zero changes to that function — reusing it here is what makes "live" trivial rather than needing a separate "just call `setLevel()`" code path.
- **`__main__.py` reordered on purpose**: `StateDB` is now constructed BEFORE `configure_logging()` is called at startup (previously the reverse), so startup can read any persisted override before deciding what level to configure. Confirmed safe by inspection — `StateDB.__init__` performs no logging of its own, so nothing is lost by delaying `configure_logging()` a few lines.
- **No MQTT/HA integration for this** — deliberately out of scope. Home Assistant's MQTT discovery only has entity types for numeric/binary/switch state (see `mqtt/discovery.py`'s `EntityDescriptor`), not a `select` with an enum of options; adding that machinery for one config knob wasn't judged worth it. The GUI is the only surface for this.

## Manual-transaction matching (opt-in)

Investigated a real report: a Telia bill showed as two independent transactions in YNAB — one manually typed in by the user (no `import_id`) and one from this sync (a real `import_id`). Root cause, confirmed by reading the code: this project's whole no-duplicates guarantee (invariant 1) is scoped to *this tool's own* `import_id`s; `_classify()` never looked at anything a human typed into YNAB by hand. Also confirmed live that the budget had zero YNAB Scheduled Transactions, so YNAB's own native matching (which only fires for a scheduled transaction's own firing, or a Direct-Import-linked account) had nothing to hook into either.

**Two live-verification detours, both worth knowing before touching this code again:**

- **PATCH-ing `import_id` onto an existing transaction is a silent no-op.** Confirmed live (`scripts/verify_ynab_import_id_patch.py`): 200 response, but the field reads back `null` right after. See invariant 6's addendum. This ruled out the obvious first design (attach `import_id` to the pre-existing manual transaction in place).
- **`create_transactions` has its own native, undocumented transaction-matching.** Submitting a transaction with an `import_id` near an existing same-account/same-amount transaction can make YNAB echo that pre-existing transaction back in the SAME response (its `approved` flipped to `false`, `matched_transaction_id` set on both sides) alongside the genuinely new row — confirmed via `scripts/verify_ynab_delete_recreate.py`, fires regardless of payee text similarity. Its exact triggering window is NOT reliably characterized (tested gaps of 5/10/20/40 days: 20 failed to match while 40 succeeded, non-monotonic) — do not depend on it for correctness. Its concrete implication for this codebase: **never index a `create_transactions` response positionally** (`transactions[0]`/`transaction_ids[0]`) whenever a pre-existing similar transaction might still be live at submission time — it can be the OTHER transaction. Always look up by your own submitted `import_id`, the same defense `_record_created()` already needed for the unrelated transfer-response quirk (see invariant 8).

**Design, chosen after weighing the tradeoff with the user**: delete-and-recreate, not patch-in-place, since patch-in-place doesn't work at all (see above).

- `SyncConfig.manual_match_window_days: int = 0` — opt-in, disabled by default. `0` means "no behavior/API-call change from before this feature existed."
- `engine.py::_classify()`'s "new" branch (only reached when nothing is locally tracked for this transaction) checks a per-account, lazily-fetched candidate list (`ynab_client.list_unimported_transactions()` — no `import_id`, not deleted, never a split/`subtransactions`) for exactly one same-amount, in-window (`manual_match_window_days`, counted via `match_window_unit` — see `sync/date_window.py` above) candidate. Zero or more-than-one candidates are NOT guessed — both fall through to an ordinary create, same "don't guess" stance as `_match_transfers`' ambiguous-pair handling (invariant 8).
- A match becomes a `_PendingManualMatch`. `submit()`'s `_record_matched()` creates the replacement FIRST — real bank date/amount, a fresh `import_id`, but the ORIGINAL manual transaction's own `payee_id`/`category_id`/`approved`/`memo`/`flag_color` (so none of the user's categorization is lost) — and only deletes the original AFTER that create succeeds. Deliberately never the other order: a failed create leaves the original completely untouched (safe); a failed delete after a successful create leaves both visible in YNAB (a manually-resolvable duplicate, not lost data) — the safer of the two possible failure modes. Confirmed live that deleting an already-deleted transaction returns 404, not idempotent success — `_record_matched()`'s retry path catches that specifically as "already done," not an error.
- Folded into `CycleResult.created` rather than a new field — a matched-and-replaced transaction is, from every consumer's point of view (run_metadata, MQTT discovery, the dashboard, ntfy), indistinguishable from an ordinary new transaction. Distinguished in the audit log instead (`detail="matched & replaced pre-existing manual transaction {id}"`).
- **Known, accepted risk**: unlike transfer-matching (invariant 8's account-number cross-check), there's no equivalent strong signal for a manual entry — a genuinely unrelated transaction sharing the same amount within the window on the same account would be wrongly claimed. Mitigated by defaulting the feature off, not by trying to eliminate the risk.
- **Deliberately not wired into `import_file_rows()`** — a bulk historical file import isn't the scenario this was built for, and would need its own candidate-cache plumbing for a case that hasn't come up.

## Operational gotchas

- **The running service does not hot-reload — restart it after any code change.** Python loads `engine.py`/`transform.py`/etc. once at process start; editing them on disk has zero effect on an already-running process until it's restarted. This caused real, time-consuming confusion during the tracking-key bug investigation (the fix was correctly on disk but the live process was still running pre-fix code) — always check `ps aux | grep ynab_auto_sync` and compare its start time against the relevant file's mtime before concluding a fix "isn't working." The frontend has the same problem via a different mechanism: editing `frontend/src/*` has zero effect until `npm run build` regenerates `frontend/dist`, which the backend serves as static files — a stale `dist/` looks identical to a real bug.
- **Be precise, not just directionally correct, when advising manual cleanup of financial data.** Advising "check budget X for duplicates from the migration window and clean them up" (without exact identifying criteria — specific import_ids, dates, amounts) led to a legitimate still-pending transaction being deleted by mistake alongside real duplicates. When recommending the user manually delete YNAB transactions based on a hypothesis about what's stale vs. current, give the exact distinguishing fields, not a general heuristic.
- **`ruff`'s default rule set (this repo pins no explicit `select`) includes `B008` (no function calls in argument defaults), which is a false positive for FastAPI's own idiomatic dependency-injection pattern** (`Depends(...)`/`File(...)`/`Form(...)` as a parameter default). `pyproject.toml`'s `[tool.ruff.lint] ignore = ["B008"]` is a deliberate, project-wide exception for this, not an oversight — don't "fix" webapp route signatures to avoid it.
- **The Docker image runs as a fixed, non-root `99:100`** (confirmed via search: Unraid's own default for Docker containers is `nobody:users`, uid 99 / gid 100 — this project deliberately targets that rather than an arbitrary uid, since Unraid/appdata deployments are the primary real-world target). Set via `USER 99:100` in the `Dockerfile`'s runtime stage, numerically rather than via `useradd`/`groupadd` — `python:3.12-slim`'s base Debian image already reserves gid 100 for its own `users` group, so creating a *named* account at that gid would collide; Docker's `USER`/`--chown` accept a raw uid:gid with no `/etc/passwd` entry required, and this app has no home-directory-dependent behavior, so there was no reason to fight that collision instead of just sidestepping it. **Real bug this caused, found via a live Unraid deployment**: the image used to hardcode `uid 1000` (`appuser`), which doesn't match Unraid's default appdata directory ownership — `sqlite3.OperationalError: unable to open database file` at startup (`StateDB.__init__`'s `sqlite3.connect()`) because the mounted `state/` directory wasn't writable by that uid, even though `state/tokens/<name>.json` inside it was already readable (readable-but-not-writable is the tell: `mkdir(parents=True, exist_ok=True)` had already succeeded, so the failure was specifically at creating the new `sync_state.db` file, not at reaching the directory at all). Fixed by switching to `99:100` and documented in README's "Deploying to your docker host" section — a host directory still needs to actually be `chown`ed to `99:100` (or already is, if created by a prior Unraid docker container using the same default) for this to work; the image can't fix host-side ownership itself.

## Standing rules for future work

- **Live-verify any new or changed assumption about SpareBank1/YNAB API behavior before trusting it in the real sync path.** This project's single most effective practice: every non-obvious API detail here (SpareBank1's OAuth host, the transactions endpoint's real field names, YNAB's `/budgets` vs `/plans` resource path, the bulk PATCH update shape, whether a "get by import_id" endpoint exists) got confirmed or refuted by writing a small throwaway script under `scripts/verify_*.py` and running it against a real account/test budget — never by trusting docs or trained-knowledge guesses alone. Docs have been directly wrong or misleading more than once (SpareBank1's own portal has an internal `expires_in` inconsistency; a guessed YNAB lookup endpoint returned a real 404). Keep doing this for anything new.
- **Quality gate**: `pytest -q` (all passing) and `ruff check src scripts tests` (clean) before considering any change done. No type checker, no coverage threshold — deliberately kept simple.
- **Financially-sensitive logic** (anything touching `sync/engine.py`'s classify/create/update logic, `transform.py`'s key derivation, or the dedup guarantee) deserves direct, careful attention rather than autonomous delegation — independent, well-isolated modules (a new client function, a config schema change, a self-contained store) are good candidates for parallel subagent dispatch; the cross-cutting correctness-critical wiring is not.
- **Git: `commit`, `tag`, and `push` are always-ask operations** — never run any of the three without the user explicitly requesting that specific action in that turn (a prior approval doesn't carry forward to the next one). This repo has version control but no automated commit policy.
- **Do housekeeping proactively, as part of finishing the work — don't wait to be asked.** Whenever something happens that a future session would need to know (a bug root-caused, a design decision made, a new invariant discovered, a risk resolved or newly identified, an assumption confirmed or refuted), update `CLAUDE.md` and `CHANGELOG.md` in the same turn as the change itself, and write/update cross-session memory when the fact is durable enough to matter outside this one conversation (a lesson about how to work with this user, a standing project fact). This is an explicit, standing instruction from the user — not optional politeness. `CHANGELOG.md` doubles as an incident/decision log for future sessions, not just a feature list; keep entries focused on *why* and *root cause*, not a diff summary.
- **Config and state are separate for a reason**: `config/config.yaml` (mostly-static secrets, hand-managed) vs. `state/tokens/<provider>.json` (rotating OAuth tokens, written every ~9 min, one file per provider) vs. `state/sync_state.db` (SQLite, disposable). Never merge these concerns.

## Resolved: SpareBank1 PENDING transactions are no longer imported at all

**What used to be here**: this section previously described an open risk — whether a pending reservation's `nonUniqueId` survives becoming `creditCardIdentifiers.nonUniqueId` once the same transaction books, which the pending→booked "transitioned" update path (`engine.py::_classify`) depends on to correct a `PENDING` transaction's amount in place once it settles. That hypothesis was never confirmed either way.

**Superseded by a more direct finding**: the user confirmed against real data that SpareBank1's `amount` field can simply be wrong while `PENDING` (a preauth/hold amount differing from the final settled amount — ordinary bank behavior). Relying on the transitioned-update path to fix this later was therefore never safe regardless of the `nonUniqueId` hypothesis's answer, since a wrong amount could persist indefinitely if the tracking key *doesn't* survive the transition.

**Implemented fix**: `providers/sparebank1/provider.py`'s `fetch()` now skips every `PENDING` row entirely (logged at debug level, not an error — this is expected, not malformed data) — a transaction is only ever normalized and returned once SpareBank1 reports it `BOOKED`, with its real, final amount. This was already the documented "accepted contingency" for the dedup-key-stability risk above; it's now the actual behavior, for a more direct reason. It matches how sibling project `../ynab-auto-bank` sidesteps the identical hazard, and CLAUDE.md's earlier note not to attempt fuzzy date/amount matching as an alternative still stands.

**What this does NOT change**: `engine.py`'s "transitioned" branch (`_classify()`, `tracked["booking_status"] == PENDING and ntx.booking_status == BOOKED`) is untouched and still load-bearing — it's what correctly resolves any `tracked_transactions` row that was already `PENDING` from *before* this change, once its real-world transaction books. No new `PENDING` row will ever reach it going forward, since the provider never returns one to classify in the first place. The original `nonUniqueId`-stability question is now moot for all future transactions (they're simply never created while pending), but remains a live concern for reconciling any pre-existing `PENDING` tracked rows.

## Confirmed live: YNAB's accounts endpoint

`GET /v1/budgets/{id}/accounts` (used for the mapping UI's drop targets) was confirmed against a real budget via `scripts/verify_ynab_accounts.py`: returns 200, wraps the list under `data.accounts`, and every field `get_accounts` and the UI depend on is genuinely present (`id`, `name`, `type`, `on_budget`, `closed`, `deleted`). Real `type` values seen include `checking` and `creditCard`. No further verification needed here.

## Verifying a refactor didn't drift a dedup key

Worth reusing whenever key-derivation code is touched, because it's the failure mode that silently re-imports someone's whole financial history:

1. Pin expected `tracking_key`/`import_id` values as **hardcoded literals** in a test — never `assert derive(x) == derive(x)`, which passes happily when both sides drift together.
2. Run identical fixtures through the old and new code paths and diff every field, not just the key.
3. After the change is live, the first real cycle must import **0 new transactions**. A non-zero count means stop immediately and investigate before it writes duplicates.

## `tracked_transactions` retention policy (implemented)

Was a low-urgency hygiene concern with nothing pruning the table; now implemented via `StateDB.prune_booked_transactions(cutoff_date)` + `StateDB.maybe_vacuum(min_interval_days)`, called from `Scheduler._prune_tracked_transactions()` at the end of every `_do_cycle()` (non-fatal — a pruning failure is logged and never affects the cycle's own recorded success/failure).

- **Only `BOOKED` rows are pruned**, and only once past `config.sync.retention_days` (default 270 days) — enforced at config-load time to stay past the fetch horizon (`initial_backfill_days` + `lookback_overlap_hours`) via a `model_validator` in `config.py`, so a normal cycle's overlap window can never re-fetch a transaction that's already been pruned and misclassify it as new.
- **`PENDING` rows are never pruned by age**, regardless of `transaction_date` — their whole purpose is to be found again later so a pending→booked transition can be detected; pruning one would recreate the "one duplicate at the transition" risk described above, self-inflicted. `prune_booked_transactions`'s `WHERE` clause hard-codes `booking_status = 'BOOKED'` for exactly this reason.
- `maybe_vacuum` rate-limits `VACUUM` (tracked via a migrated `run_metadata.last_vacuum_at` column) since `DELETE`s alone don't shrink the on-disk file and `VACUUM` is too expensive to run every cycle.

## Payee-mapping reconcile pass (implemented)

Closes invariant 12's previously-documented gap: what happens when a cached `payee_mappings` row's `ynab_payee_id` is later deleted or merged away in YNAB by the user. Directly inspired by exploring sibling project `../ynab-auto-bank`'s `YnabPayee` local cache + link-repair pass (`app/ynab_payees.py`) — this project deliberately does NOT port that sibling's much heavier `PayeeAlias`/`PayeeAliasCandidate` learned-alias-with-conflict-tracking system, since that solves a different problem (learning a renamed payee's *display name* via a deferred, human-approval-gated reconciliation pass) that this project never has: `payee_mappings` already anchors on `payee_id` synchronously at create time (invariant 12), so it never needs to "learn" an id after the fact — only to notice when an already-learned id has gone stale.

`SyncEngine.reconcile_payee_mappings()` fetches `ynab_client.get_payees()` for every budget in `config.ynab.budgets`, builds the set of ids YNAB reports `deleted: true`, and deletes any `payee_mappings` row anchored to one via `StateDB.delete_payee_mappings_for_ids()`. Called every cycle from `Scheduler._reconcile_payee_mappings()` (not rate-limited like `maybe_vacuum` — a `get_payees()` GET per budget is cheap enough, unlike `VACUUM`, that adding rate-limit state wasn't judged worth it; revisit only if a real deployment configures many budgets). Per-budget fetch failures are isolated (logged, that budget skipped, others still processed), and the whole step is itself non-fatal to the cycle's own recorded success/failure — same shape as `_prune_tracked_transactions()`, but in its own separate try/except since this step makes a live YNAB HTTP call per budget, a genuinely different failure mode than pruning's pure local SQLite work.

**Deliberately keys off explicit `deleted: true`, never absence from the fetch** — YNAB keeps deleted/merged payees present in the list with the flag set rather than removing them, confirmed via `scripts/verify_ynab_payee_deletion.py` (a two-phase live-verification script: an automatic phase reporting the real deleted/active split in a budget's payee list, then a manual phase that creates a throwaway test payee, asks you to delete or merge it by hand in the YNAB UI, and confirms it re-appears with `deleted: true` rather than vanishing). Treating "absent" as evidence of deletion would be both unnecessary and unsafe — a transient/incomplete fetch could otherwise mass-invalidate a whole budget's cache; this exact property (`test_reconcile_payee_mappings_does_not_delete_when_id_merely_absent` in `tests/unit/test_engine.py`) is the single most important test in the whole feature.

**No guessing what a deleted payee merged into** — YNAB's payee list has no such linkage. A later create for the same raw text just re-learns a fresh `payee_id` through the normal `_classify()`/`_record_created()` path, exactly like a brand-new merchant.

**Not written to `audit_events`** — a healed row has no `tracking_key`/`import_id`/real transaction outcome to attach to; it's an internal cache correction, not a transaction-level event. `logger.info(...)` on a nonzero healed count follows the same log-only precedent as `prune_booked_transactions`/`prune_audit_events`/`maybe_vacuum`.

## Deliberate non-goals (don't reintroduce this scope without discussing first)

- **No general web UI beyond the four admin tasks MQTT/HA genuinely can't do.** MQTT/Home Assistant remains the primary operational surface (status, sync-now, pause). The `frontend/` SPA (see architecture map) exists specifically for status visibility, deleted-transaction re-add, spreadsheet import, and account mapping — tasks needing a file upload, a tabular preview, or drag-and-drop, which HA's dashboard can't provide. Still no OAuth connection management and no general manual reconciliation UI — don't expand it without discussing first.
- **"No config editing" was deliberately overturned twice now — account mappings, and `logging.level`.** Mappings moved from `config.yaml` into the `account_mappings` SQLite table so the GUI can edit them by drag-and-drop; that was the explicit goal of the multi-provider work. `logging.level` got the same treatment for the same underlying reason (see "Runtime-configurable log level" below): `run_metadata.log_level` is state, not config, `config.logging.level` remains the fallback/default a fresh process starts with, and nothing about it is a secret or safety-sensitive. Both exceptions follow the exact same shape: state-DB-backed override, config value as the seed/fallback, never the other way around. Everything else in `config.yaml` — credentials, budgets, cron, retention, GUI/MQTT/notifications settings — remains hand-edited, static, and never written by the app. Don't extend GUI editing to those without discussing first (as happened for both of these); secrets in particular stay in the file.
- **No config export/import, no DB backup tooling.** Both solve problems specific to a fully DB-backed *mutable* config model (the sibling project's). This project's config is still a static YAML file — portable and backup-able by being a plain file. Note the mappings table is now the one exception, and it is *state*, not config: it lives in `state/sync_state.db`, which the invariants already treat as disposable and reconstructible.
- **No currency-mismatch handling.** SpareBank1's data so far shows domestic transactions' `amount`/`currencyAmount` matching exactly, suggesting pre-conversion rather than pass-through — revisit only if a real foreign-currency transaction is observed to behave differently.
