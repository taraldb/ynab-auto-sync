Guidance for Claude Code sessions working on this repo. Keep this file up to date as the project evolves — it's meant to save a future session from re-deriving hard-won context, not to duplicate what's already clear from reading the code.

## What this project is

A long-running Python service that pulls bank transactions from one or more **providers** and imports them into YNAB, with zero duplicate transactions guaranteed. SpareBank1 (accounts + credit cards) is the only provider implemented today, but it sits behind a seam (`providers/`) rather than being wired into the core. Also: status/control over MQTT for Home Assistant (optional — it can run with no broker at all), a bundled admin GUI, and a spreadsheet-import path for historical bank exports. Every source — live poll or file import — shares **one** dedup/tracking/classify core, so no two of them can double-book the same real-world transaction. Runs on a cron schedule (default: six times a day, nothing overnight) rather than continuous polling.

Two things are deliberately NOT abstracted: **YNAB** is the one and only target, hardcoded on purpose; and the **dedup guarantee** is centralized rather than delegated to each source.

## Architecture map

- `src/ynab_auto_sync/config.py` — pydantic v2 config model, loaded from `config/config.yaml` (gitignored, real secrets — never read or print its contents). `providers` is a `dict[str, ProviderConfig]` discriminated on `type`, keyed by a **user-chosen name** — that key is what `account_mappings.provider` stores and what names the provider's token file, so renaming it orphans that provider's mappings until they're re-pointed (deliberate: silently re-matching by type could re-route real money to the wrong account). Several entries of the same `type` are supported and expected (the SpareBank1 alliance is many separate banks). The remaining `model_validator` only checks what config.yaml alone can still get wrong: unresolvable YNAB budget aliases on the legacy `accounts:` seed list, an invalid `sync.cron_expression`, an unrecognized `sync.timezone` IANA name, a `sync.retention_days` below the still-reachable fetch horizon, and a `sync.dedup_lookback_days` below the widest match window plus overlap (see next). `SyncConfig.timezone: str = "Europe/Oslo"` — the IANA zone `cron_expression`'s hour digits are evaluated in (see `cron.py` below and "Resolved: cron ran in UTC, not local time"); was previously implicit UTC with no way to express local time at all, silently offsetting every fire by 1-2h depending on DST. **Duplicate-account and duplicate-`import_source_name` checks deliberately no longer live here** — mappings are runtime-mutable now, so a startup-only check would be trivially bypassed by the GUI; they moved to write-time validation in `StateDB` (see invariant 10). `AccountMapping`/`accounts` survives ONLY as the one-time seed source for `account_mappings`; nothing reads it after the first startup. `notifications: NotificationsConfig | None = None` holds discrete-event-notification provider config (`NotificationsConfig.ntfy: NtfyConfig | None`) — nested rather than a flat top-level `ntfy:` field so a future second provider slots in without another `AppConfig` field each time. This is unrelated to `mqtt`/`gui` above: those drive the *state* sink (`notifications/`), this drives the *event* notifier (`alerts/`) — see that package's architecture-map entry and "Discrete event notifications" below. `api_response_logging: ApiResponseLoggingConfig = Field(default_factory=ApiResponseLoggingConfig)` — always-present-with-default like `logging` above (not `Optional[...] = None` like `mqtt`/`notifications`), since it's a debug toggle with its own `enabled: bool = False`, not "absent means off." No cross-field validation needed (unlike `sync.retention_days`) — see `api_response_logging.py`'s own architecture-map entry. `SyncConfig.manual_match_window_days: int = 0` (opt-in, disabled by default) and `SyncConfig.match_window_unit: Literal["calendar_days", "working_days"] = "calendar_days"` (shared with `transfer_match_window_days`) drive the manual-transaction-matching feature — see "Manual-transaction matching (opt-in)" below. `SyncConfig.currency_decimal_places: int = 2` and `SyncConfig.pending_import_amount_tolerance_kroner: Decimal = Decimal("2.0")` (retyped from `float`) are the two amount-related knobs — see "Currency amounts: Decimal, not float" below and `sync/money.py`'s own entry. `SyncConfig.dedup_lookback_days: int = 90` is the `since_date` floor for every dedup-RESILIENCE YNAB lookup (`since_date_bound()`'s five call sites in `engine.py`) — its OWN knob, deliberately not `initial_backfill_days` (a cursorless-first-run backfill horizon that is legitimately tiny on some deployments); overloading the two silently shrank these lookups and caused real duplicates (see "Resolved: manual-matched PENDING placeholder..." below).

Constructed once per process in `webapp/app.py`'s `create_app()` and served via `webapp/routes/providers.py`'s `GET /api/ynab/accounts?force_refresh=`.

Applied to payee/memo on both the live-poll (`transform.py`) and file-import (`file_import/transformers/norwegian_bank.py`) paths, so formatting is consistent regardless of source. Deliberately does NOT port that project's "strip standalone CRV marker" rule — unconfirmed for SpareBank1 data, see the module's own comment. Also `normalize_payee_for_fuzzy_match()`/`payees_plausibly_match()`/`levenshtein_distance()`/`payee_similarity()` — used only by `sync/pending_match.py`'s PENDING-transaction correlation (see below), never by `clean_bank_text` itself. `normalize_payee_for_fuzzy_match` deliberately does NOT also truncate to the segment before the first comma even though that's the part confirmed stable across a PENDING→BOOKED drift — doing so would erase the location/branch text `pending_match.py`'s Levenshtein-based disambiguation needs to rank two otherwise-plausible candidates against each other; the coarser `payees_plausibly_match` prefix check already tolerates the drift case on its own.
- `src/ynab_auto_sync/sync/money.py` — owns the Decimal↔milliunits boundary, the ONLY place amount unit conversion happens: `to_milliunits(amount: Decimal) -> int` (exact, `ROUND_HALF_EVEN` matching Python's builtin `round()` — a deliberate behavioral match for the `round(float(amount) * 1000)` it replaced, proven equivalent against 499 real historical amounts, see "Currency amounts: Decimal, not float" below), `from_milliunits(int) -> Decimal` (always exact, 1000 is a power of ten), `parse_provider_amount(raw: str | float, decimal_places: int) -> Decimal` (converts a raw provider value to an exact Decimal — goes through `Decimal(str(raw))` for a float input, NEVER `Decimal(raw)` directly, which would inherit the float's binary representation noise). Internal canonical precision is always 3 decimal places (matching milliunits' own granularity), independent of `config.sync.currency_decimal_places` (which only governs how a raw provider value is parsed/quantized, e.g. NOK's 2 øre digits).
- `src/ynab_auto_sync/sync/ynab_payload.py` — bank-agnostic construction of the YNAB create-transaction dict (`{"account_id", "date", "amount", "payee_name" or "payee_id", "memo", "cleared", "approved", "import_id"}`) via `build_create_payload()`, plus the two YNAB field-length caps `YNAB_PAYEE_NAME_MAX_LEN`/`YNAB_MEMO_MAX_LEN` (moved out of `transform.py`, which re-exports both for backward compatibility). Extracted specifically so `engine.py`'s file-import path no longer had to reach into the SpareBank1-specific `transform.py` just to get YNAB's own length caps — that was an open/closed violation blocking a multi-provider refactor. `build_create_payload()` takes only already-normalized values (a `date`, int milliunits, plain strings) and never a raw source dict — **its `amount_milliunits: int` parameter is deliberately NOT `Decimal`**, even though every other domain type in this codebase now is (see `sync/money.py` above): this is the literal YNAB API payload boundary, which requires int milliunits regardless of internal representation, so every caller converts via `money.to_milliunits()` right before calling this function, never earlier. Its `import_id` parameter is a pure passthrough — it must never derive, hash, or re-prefix it (see invariant 6, YNAB permanently burns an import_id). Its optional `payee_id` parameter, when given, is emitted INSTEAD of `payee_name` (YNAB treats them as mutually exclusive on create — see invariant 12). Used by both `transform.transform_transaction()` (live-poll path) and `engine.import_file_rows()` (file-import path); `sync/file_import/transformers/norwegian_bank.py` still has its own separate copy of the two length constants, not yet consolidated onto this module.
- `src/ynab_auto_sync/providers/` — **the input seam** (mirrors the older `sync/file_import/` registry pattern). `base.py`: `TransactionProvider` ABC (`type_name()`/`list_accounts(force_refresh=False)`/`fetch(since_by_account, on_skip=None)`), `NormalizedTransaction` (`amount: Decimal` — major-unit currency, e.g. `Decimal("158.48")` kr, not milliunits; exact to 3 decimal places, converted to int milliunits only at the YNAB-payload boundary via `sync/money.py::to_milliunits()` — see "Currency amounts: Decimal, not float" below), `ProviderAccount` (`account_type` has no fixed vocabulary across providers — SpareBank1 confirmed live to send `"USER"`/`"SAVING"`/`"CREDITCARD"`, not the `"checking"`/`"credit_card"` an earlier, never-verified version of this docstring guessed), `BookingStatus`, `ProviderAuthRequiredError`. Its docstrings carry the load-bearing knowledge a new provider's author needs — read them before adding one. `fetch()` takes a **per-account** window map and may over-fetch (a provider batching several accounts into one upstream call uses `min(...)`); the ENGINE applies the authoritative per-account cutoff, and a provider must never drop a row for being too old. Per-row robustness is the provider's job: one malformed row is logged and skipped, never raised. `SkipCallback` + `report_skip()` (mirrors `engine.py`'s `ProgressCallback`/`_report()` shape exactly) is the optional, default-`None`, best-effort hook a provider calls once per genuinely malformed row it drops — backs the GUI's Audit Log "skipped" category (see `state_db.py`'s `audit_events` entry below); a provider must NOT call it for routine, expected per-cycle skips (e.g. SpareBank1's PENDING-row skip), only for structurally-malformed data — see `fetch()`'s docstring for the exact line. `registry.py`: `REGISTRY`/`register`/`get_provider_class`. `sparebank1/provider.py`: `SpareBank1Provider`, which owns what used to be inline in `run_cycle()` — the batched fetch, `accountKey` bucketing, and the three per-row `MissingFieldError` skip-and-log branches, each of which also calls `report_skip()` alongside its existing `logger.error()`. `fetch()` also skips every `PENDING` row outright (logged at debug level, `report_skip()` deliberately NOT called) rather than normalizing and returning it — SpareBank1's `amount` is not reliable until a transaction books, confirmed against real data; see "Resolved: SpareBank1 PENDING transactions are no longer imported at all" below. `list_accounts()` is TTL-cached (`_ACCOUNTS_CACHE_TTL`, 5 minutes; instance-level, no lock needed — long-lived per-process singleton on one event loop, same reasoning as `StateDB`'s own concurrency notes) so a Mappings-tab visit doesn't re-hit the live `/accounts` endpoint every time; `force_refresh=True` (wired from the GUI's "Refresh" button through `GET /api/providers?force_refresh=true`) bypasses it. It also runs each account's raw `name` through `_friendly_account_name()` — confirmed live (`GET /personal/banking/accounts?includeCreditCardAccounts=true`) that a regular checking/savings account's `name` is already a real personal nickname (never touched), but a credit card's `name` is a masked card number (e.g. `"**** **** **** 3431"`) while its `description` holds the real product name (e.g. `"Mastercard Ung"`) — the masked case is replaced with `f"{description or type_label} •{last4}"`. A name that doesn't match the masked-number regex is returned completely untouched, so this can only improve on today's floor, never regress it. This is separate from — and doesn't touch — `account_mappings.display_name`, which is set once at mapping-creation time and only reflects the fix for accounts mapped *after* it shipped; `Mappings.tsx`'s existing-mappings table has its own click-to-edit rename (`doRename`/`updateMapping(id, {display_name})`, no backend change needed since `display_name` was already in `StateDB._MAPPING_UPDATABLE_FIELDS`) for anything mapped before.

The `"SpareBank1 transaction"` fallback payee string is bank-specific and deliberately stays here rather than in `ynab_payload.py`. `get_transaction_date()` and `transform_transaction()` both take a required `timezone` parameter (no default — see invariant 5 and "Resolved: SpareBank1 transaction dates were a day early" below), threaded from `config.sync.timezone` through `SpareBank1Provider.__init__`/`__main__.py`'s `_build_providers()`. `get_account_number()`/`get_remote_account_number()` extract the transfer-matching cross-reference fields (see invariant 8) — neither raises `MissingFieldError` like the other getters here do, since a transaction with no recognizable account number should just never participate in transfer-matching, not be skipped/logged as malformed. `PAYEE_NAME_CANDIDATES` (payee) vs. `MEMO_FIELD_CANDIDATES` (memo) are deliberately DIFFERENT tuples, not the same list reused — confirmed live against 25 real booked transactions that memo never once carried information payee didn't already say (either byte-identical, or differing only by a payment-processor prefix like `"Vipps*"`/`"Zettle_*"` that `cleanedDescription` already strips for payee). `MEMO_FIELD_CANDIDATES` prefers `cleanedDescription` too (fixing that prefix case) but deliberately EXCLUDES `remoteAccountName` — including it would make memo mathematically guaranteed to always equal payee whenever a named counterparty exists (same field, same first-hit), permanently defeating the suppress-when-identical check below instead of just correctly applying it. Both `provider.py`'s `_extract_memo(sb1_tx, payee_name)` and this file's `transform_transaction()` compute payee first, then suppress memo to `None` whenever it's identical to payee after cleaning (case-insensitive, whitespace-normalized) — `transform_transaction()` is confirmed dead in the live `fetch()` path (`provider.py` reimplements everything locally per its own docstring) but is kept behaviourally in sync since its own tests still exercise it.
- `src/ynab_auto_sync/sync/file_import/` — the analogous dedup/transform layer for the *file-import* path (a different source, same no-duplicates guarantee, deliberately generic naming since xlsx is only today's first format — see invariant 7): `base.py` (`TransformerBase` OCP contract: `can_handle(headers)`/`name()`/`transform(rows)`, `ImportedTransactionRow` (`amount: Decimal`, formerly `amount_milliunits: int`), `RowTransformError`), `registry.py` (`REGISTRY`/`register`/`detect_transformer`), `parsing.py` (`parse_file(filename, data)` — dispatches on extension, `.xlsx` today via openpyxl, a future `.csv` branch slots in without touching transformers), `dedup.py` (`compute_dedup_key`/`get_tracking_key`/`derive_import_id`, prefix `"FILE:"` — **`compute_dedup_key`'s signature and hash-input shape are deliberately UNCHANGED by the Decimal refactor**: it still hashes an `int` milliunits value, now computed via `money.to_milliunits(row.amount)` at each call site rather than being handed a raw int field — any change to the hash input shape itself would silently re-import a user's whole file-import history as duplicates, see invariant 7 and "Currency amounts: Decimal, not float" below), `transformers/norwegian_bank.py` (the one registered transformer so far, payee/memo also run through `sanitize.clean_bank_text`; parses its `Amount` column via `money.parse_provider_amount(amount, decimal_places=2)` — hardcoded `2`, not threaded from config, since this transformer is already Norwegian-bank-specific by name/column-layout; memo is `None` always as of a later change, not derived from Merchant Category).
- `src/ynab_auto_sync/sync/transfers.py` — pure-function matching only (`TransferCandidate`, `find_transfer_pairs`), no I/O, deliberately decoupled from `engine.py`'s internal types so it's independently testable. `TransferCandidate.amount: Decimal` (major-unit currency, not milliunits) — the pairing check (`other.amount == -c.amount`) is exact equality, identical semantics whether backed by int or Decimal. `TransferCandidate.account_number`/`remote_account_number` (both `str | None`) carry SpareBank1's real account-number cross-reference — see invariant 8 for the full matching rule, why it's OR not AND between the two directions, and the false positive that motivated it. `find_transfer_pairs`' date-window check goes through `sync/date_window.py`'s `days_between()` (a new `unit` parameter, default `"calendar_days"` so no existing call site's behavior changes) rather than a raw `abs((...).days)` — see "Manual-transaction matching (opt-in)" below for why this became shared, configurable behavior instead of transfer-matching-only.
- `src/ynab_auto_sync/sync/pending_match.py` — the fuzzy PENDING↔BOOKED and PENDING↔manual-transaction correlation used by `engine.py`'s `"transitioned_fuzzy"` outcome, opt-in via `config.sync.pending_import_enabled` (see "PENDING-transaction import (opt-in, credit-card only)" below for the full write-up). Pure-function matching only (`PendingCandidate`/`BookedCandidate` (`amount: Decimal`)/`PendingMatch` (`amount_diff: Decimal`, formerly `amount_diff_milliunits: int`), `find_pending_match`, `find_manual_match_tolerant`), same no-I/O, engine-decoupled shape as `sync/transfers.py`. `_amount_within_tolerance(a: Decimal, b: Decimal, tolerance: Decimal) -> bool` is now a plain `abs(a - b) <= tolerance` — the Decimal refactor removed the "convert tolerance_kroner to milliunits inside the comparison" step this used to need, a genuine simplification. `find_manual_match_tolerant`'s `candidates` param is still `list[dict]` with a raw YNAB API `"amount"` int field (from `ynab_client.list_unimported_transactions()`) — converted to Decimal via `money.from_milliunits()` only at the comparison, since this dict shape is a YNAB API boundary type, not internal domain state. Adds a Levenshtein-edit-distance-based ranking step (`sanitize.py`'s `payee_similarity`) as a tie-breaker when more than one candidate survives the coarser account/amount/date filters, accepting a winner only if it clears both a similarity floor and a minimum margin over the runner-up — otherwise still refuses to guess, same stance as `find_transfer_pairs`/`_find_manual_match`.
- `src/ynab_auto_sync/sync/date_window.py` — `days_between(d1, d2, unit)`, shared by `transfers.py`'s transfer-matching (invariant 8) and `engine.py`'s manual-transaction-matching (below). `unit="working_days"` counts business days via `workalendar.europe.Norway()` (a module-level, stateless, reusable instance) — confirmed live that `get_working_days_delta()` is already order-independent and correctly excludes both weekends and Norwegian public holidays (e.g. Good Friday → the following Tuesday is 1 working day, not 4 calendar days).
- `src/ynab_auto_sync/sync/engine.py` — **provider-agnostic**: it knows only the `TransactionProvider` contract and consumes `NormalizedTransaction`s (`ntx.amount: Decimal`, converted to int milliunits via `money.to_milliunits()` only at the point a YNAB payload/PATCH dict is actually built — see "Currency amounts: Decimal, not float" below; `_PendingUpdate.new_amount`/`_PendingFuzzyUpdate.new_amount` are `Decimal` too, same "bare domain amount, not yet a payload" reasoning, while every literal `ynab_tx`/YNAB-response `dict`'s `"amount"` key stays `int` unchanged, since those ARE the payload). It has zero code references to SpareBank1 (keep it that way). Constructed as `SyncEngine(config, http_client, db, providers)`. `run_cycle()` is a convenience composition of two phases now exposed separately so `scheduler.py` can retry just one of them (see "Cycle-failure retry with backoff" below): `fetch_and_classify()` — read enabled mappings from the DB → `_compute_fetch_windows()` (cursor + overlap, widened by any still-pending transaction — generic, stays in the engine) → `provider.fetch()` per provider → `_classify()` → **match transfer pairs** (`_match_transfers`, invariant 8) → returns a `ClassifiedCycle` — then `submit(classified)`: batch create/update per YNAB budget → persist tracking. `submit()` is safe to call more than once with the same `ClassifiedCycle`, including after a prior partial failure — every write it makes is naturally idempotent on retry (YNAB's `import_id` dedup, invariant 1, and `update_transactions`' idempotent PATCH payloads), which is exactly what makes the retry design below safe without extra bookkeeping. Both phases take an optional `on_progress: Callable[[str, dict], Awaitable[None]] | None = None` (default `None` everywhere, so every existing caller is unaffected) — called once per provider before `fetch()` and once per budget before each YNAB write, wrapped in a best-effort `_report()` helper that swallows and logs any callback exception so a broadcast bug can never affect the cycle itself (see "Live GUI push updates" below). `SyncEngine` still has no `NotificationSink` import of its own — the callback is a plain function, not the sink interface, so the engine stays notification-agnostic. `import_file_rows()` normalizes each parsed row into the SAME `NormalizedTransaction` shape and runs it through the SAME `_classify()`, which is what makes "a file import can't double-book what a live poll already imported" structural rather than two code paths agreeing by convention. A mapping naming an unconfigured provider is logged and skipped, never fatal. `readd_deleted_transaction(tracking_key)` is source-agnostic and re-derives the new `import_id` inside the ORIGINAL row's dedup domain via `import_ids.prefix_of` (invariant 7). Has no MQTT side effects of its own (see docstring in the file). `_classify()`'s "new" branch also looks up `db.get_payee_id(ynab_budget_id, ntx.payee_name)` and threads it through to `build_create_payload` (invariant 12); `_record_created()` writes the mapping back from the create response's `payee_id`, but only when the submitted payload had no `payee_id` of its own — a transfer primary's rewritten `payee_id` (see `_match_transfers`, invariant 8) must never be cached under a raw merchant name. `_record_created()` also checks `created.get("matched_transaction_id")` for every non-transfer row (YNAB's native transaction-matching, invariant 8's own note below, can fire on ANY create, not just the deliberate manual-match feature's) and, when set, delegates to `_track_native_match()` — a shared helper also called by `_record_matched()`'s own `_finish_native_match()`, extracted after both call sites had independently grown the same "track the pre-existing visible transaction instead of the shadow, log as `updated`" logic (see "Resolved: an ordinary create's native transaction-match tracked the invisible shadow" below). `reconcile_payee_mappings()` is the separate maintenance-pass half of the same invariant — see "Payee-mapping reconcile pass" below. **Audit trail**: every `created`/`updated`/`duplicate`/`skipped` outcome writes a row to `db.audit_events` (see `state_db.py` below) immediately alongside the corresponding `tracked_transactions` write, stamped with the provider's own `account_key` (`_PendingCreate.provider_account_id`/`_PendingUpdate.account_key`, or `ntx.provider_account_id` at the two `fetch_and_classify()` skip sites — `_PendingUpdate` gained this field alongside `provider_type` specifically to make this possible, populated in `_classify()`'s `"transitioned"` branch from the same `ntx` already in scope) — `_record_created()`/`_record_transfer_secondary()` write `created` (the latter tagged `"transfer secondary leg..."` in `detail`; the primary leg is tagged `"transfer primary leg"`), `submit()`'s update loop writes `updated` right after `mark_booked()`, all three `_backfill_duplicates()` sub-cases write `duplicate` (distinguished only via `detail`, not a finer `event_type`), and `fetch_and_classify()`'s two defensive skip branches (unmapped account, stale/out-of-window) write `skipped` directly. A malformed-row skip's `account_key` instead flows up through the `on_skip` callback's `context` dict (see `providers/` below) — the provider still knows which account it was fetching for even when the row itself is too broken to become a `NormalizedTransaction`. `import_file_rows()` shares the same `created`/duplicate machinery via `_record_created()`/`_backfill_duplicates()`, plus its own small hook for the file-only "already tracked" duplicate case (`_classify()`'s `"unchanged"` outcome never reaches `_backfill_duplicates()` on this path, since it's filtered out before `pending_creates` is built) — fired only when `not dry_run`, since a preview never actually writes anything. Deliberately NOT audit-logged, to avoid flooding: `_classify()`'s plain `"unchanged"` outcome on the live-poll path, and the provider's routine PENDING-row skip — both are expected, high-frequency, non-diagnostic events, not "something went wrong." **Manual-transaction matching** (opt-in, see the dedicated section below): `_classify()`'s "new" branch, given a per-account `manual_candidates` list, may instead return a `"matched_manual"` outcome (`_PendingManualMatch`); `fetch_and_classify()` populates that list lazily per `ynab_account_id` (only when `manual_match_window_days > 0`, so the disabled case costs zero extra API calls) and routes the outcome into `ClassifiedCycle.matches_by_budget`; `submit()`'s `_record_matched()` creates the replacement transaction FIRST and only deletes the original manual transaction after that succeeds — never the other order — and never indexes the create response positionally (YNAB's own native transaction-matching can echo the still-live original back in the same response; the replacement is found by its own submitted `import_id`, same pattern `_record_created()` already uses for the unrelated transfer-response quirk). `import_file_rows()` deliberately never wires this in (omits `manual_candidates`, defaulting to `None`) — a bulk historical file import isn't the scenario this was built for. **`submit()`'s pending→booked update loops (`_PendingUpdate`/`_PendingFuzzyUpdate`) bulk pre-check every target's current existence in YNAB, once per budget, before attempting any PATCH** (`ynab_client.list_transactions_including_deleted()`), then PATCH confirmed-alive rows individually, never batched — see "Resolved: update PATCH could permanently wedge the sync cycle" below for why (a blind batched PATCH used to 400 the WHOLE batch, including otherwise-fine rows, the moment one target had been deleted directly in YNAB, and since `submit()` raising aborts the whole cycle, one stale row could wedge every budget's sync forever). A confirmed-deleted row (or one whose individual PATCH still 400s despite the pre-check saying alive — `_patch_single_update()`'s own defensive catch) goes through `_recover_missing_pending_update()`: reevaluate for a live manually-typed replacement (same account, exact amount, within `pending_import_date_window_days`, via `list_unimported_transactions()` + the *same* create/native-match-or-replace flow `_record_matched()` already implements for `_classify()`'s `"matched_manual"` outcome — no second mechanism) before falling back to marking the row `booking_status='DELETED'` for GUI re-add. A match found counts toward `CycleResult.created` (same accounting as `matches_by_budget`); no match found counts toward `resolved_deleted` (same accounting as `_backfill_duplicates`'s identical "resolved, nothing created or updated" event) — neither is folded into `updated`, since neither is an ordinary update. The two single-row PATCH sites (stale-`payee_id` self-heal on a just-created transaction; a matched transfer's secondary-leg cleared/amount correction) get a narrower catch-and-log-only treatment on a 400, not the full reevaluate flow — neither semantically fits (no `new_amount` concept for the payee-only correction; a transfer leg isn't a manual-match candidate), and both are vanishingly rare since their target was created moments earlier in the same `submit()` call.
- `src/ynab_auto_sync/sync/state_db.py` — SQLite state: `account_cursors`, `run_metadata`, `tracked_transactions`, `account_mappings`, `payee_mappings`, `audit_events`. Disposable/recoverable by design (see invariants). **`tracked_transactions`/`audit_events` carry BOTH `amount_milliunits INTEGER` and `amount_decimal TEXT` columns, deliberately never just one** — every mutating method (`upsert_tracked`/`mark_booked`/`rekey_pending_to_booked`/`insert_audit_event`) now takes `amount: Decimal` and derives both column values from that single in-memory value at write time (`money.to_milliunits(amount)` and `str(amount)`), so the two can never drift from each other by construction. `amount_milliunits` is kept as the numeric source `list_audit_events`'s `sort_by="amount_milliunits"` `ORDER BY` needs — a TEXT-stored Decimal string sorts lexicographically wrong for negative/mixed-magnitude values, confirmed a real correctness risk before deciding to keep both columns rather than migrate to TEXT-only. `_backfill_amount_decimal(table, pk_column)` (called from `_migrate()` only when `amount_decimal` is newly added to an existing DB) is the first migration in this file that backfills a *value* rather than just adding a column with a static default — derives each row's exact Decimal from its existing `amount_milliunits` via `money.from_milliunits()` (always exact, no precision invented or lost). See "Currency amounts: Decimal, not float" below for the full design. `audit_events` is a genuinely **append-only** log (autoincrement PK, never mutated once written) — the one table here that's NOT a current-state upsert; it backs the GUI's Audit Log tab and is purely observational, never read by any dedup/classify/submit logic. `insert_audit_event(...)` is one generic write method (mirrors `upsert_tracked`'s single-signature-many-call-sites style) with `event_type` one of `created`/`updated`/`duplicate`/`skipped`, an `account_key` (the provider's own account identifier, same value `tracked_transactions.account_key` uses — mirrors `DeletedTransactions.tsx`'s existing "Account" column convention), and a free-text `detail` for the specific reason — see `engine.py`'s entry above for exactly which outcome writes which event/detail/account_key. `list_audit_events(event_type=None, account_key=None, include_skipped=False, sort_by="occurred_at", sort_dir="desc", limit=50, offset=0)` returns `(rows, total)`; an explicit `event_type` always wins over `include_skipped` (so `?event_type=skipped` works regardless). `sort_by` is checked against `AUDIT_EVENT_SORT_COLUMNS`, a fixed allowlist — never interpolate a caller-supplied column name into the `ORDER BY` clause directly, even though the only caller (`routes/audit.py`) already constrains it via a `Literal` type; `sort_dir` is checked against `("asc", "desc")`. Both raise `ValueError` on an invalid value rather than silently falling back. `count_audit_events_by_type()` is a cheap zero-filled `GROUP BY`, backing the GUI's summary strip — deliberately unaffected by the current `event_type`/`account_key`/`include_skipped` filter, so the strip always shows true totals as a nudge toward categories the current filter is hiding. `prune_audit_events(cutoff_date)` reuses `config.sync.retention_days` (no new config knob) and compares on `date(occurred_at)` rather than the raw datetime string, so "today" is never pruned regardless of what time it currently is. `run_metadata`'s `*_last_run` counters (`fetched_last_run`, `imported_last_run`, `updated_last_run`, `duplicates_last_run`, `resolved_deleted_last_run`) are all set together in `record_success()` and zeroed together in `record_failure()` — `fetched_last_run` is the raw pre-dedup/classification count (`CycleResult.fetched`, sourced from `ClassifiedCycle.fetched_count`), added via the same migration mechanism as `resolved_deleted_last_run` before it (see "Discrete event notifications" below). `run_metadata.log_level` (`set_log_level(level)`) is a fourth kind of thing this table holds alongside cursors/counters/`paused`: a GUI-settable runtime override for the process's log level, `NULL` until ever set (meaning "no override, fall back to `config.logging.level`") — see "Runtime-configurable log level" below. `delete_all_mappings()` is the bulk "clear all" the Mappings tab's clear-all button calls — a single `DELETE FROM account_mappings` with no `WHERE`, returning the row count deleted; only removes the mapping rows, `tracked_transactions`/burned `import_id`s are untouched (invariant 11 still applies — nothing is re-imported on remap). `payee_mappings` (`get_payee_id`/`upsert_payee_mapping`) caches, per `(ynab_budget_id, raw_payee_name)`, the YNAB `payee_id` first assigned to that raw text — see invariant 12; `upsert_payee_mapping` is `INSERT OR IGNORE`, deliberately first-write-wins. `delete_payee_mappings_for_ids(ynab_budget_id, ynab_payee_ids)` is the healing half of invariant 12's reconcile pass (see `SyncEngine.reconcile_payee_mappings()` and "Payee-mapping reconcile pass" below) — deletes cached rows whose `ynab_payee_id` was individually confirmed gone via a targeted per-id lookup (404, or `deleted: true`), never merely from being absent in a bulk-list scan — see that method's own docstring for the two live-caught mistakes/refinements that motivated the current hybrid design (a pure bulk-list design was tried first and proven permanently inert against real deletions; a pure per-id design fixed that but cost one API call per ever-cached payee every sweep). `list_payee_ids(ynab_budget_id)` returns every DISTINCT cached `ynab_payee_id` for a budget — the full candidate pool the reconcile pass starts from, most of which the hybrid design's cheap bulk-list first pass resolves without ever reaching a per-id call. `is_payee_reconcile_due(min_interval_days)` / `mark_payee_reconcile_done()` (new `run_metadata.last_payee_reconcile_at` column) rate-limit the whole sweep, mirroring `maybe_vacuum`'s own pattern — kept as burst insurance even after the hybrid design restored a cheap common case, since a large one-cycle candidate set is still possible. `tracked_transactions` also persists full reconstruction data (`payee_name`, `memo`, `transaction_date`, `ynab_account_id`, `cleared`, `readd_count`) on every row, not just deleted ones. Every mutating method is `async` and guarded by an internal `asyncio.Lock` (see invariant 9); the connection is opened with `PRAGMA journal_mode=WAL`, `PRAGMA busy_timeout=5000`, and `check_same_thread=False`. `prune_booked_transactions(cutoff_date)` / `maybe_vacuum(min_interval_days)` implement the retention policy (see below — no longer just "recommended"). `account_mappings` (`list_mappings`/`get_mapping`/`create_mapping`/`update_mapping`/`delete_mapping`/`seed_mappings_from_config`/`count_tracked_for_account`) is now **authoritative** for which accounts sync where: `engine.run_cycle()` reads `list_mappings(enabled_only=True)`, and `webapp/routes/mappings.py` lets the GUI edit them. A disabled mapping is skipped at fetch time entirely, and its existing PENDING tracked rows are left untouched rather than pruned, so re-enabling resumes reconciliation instead of orphaning them. `create_mapping`/`update_mapping` re-implement `config.py`'s startup dedup checks as write-time validation (raising `MappingValidationError`) since a mutable table can no longer rely on a one-time fail-fast load-time check; budget-alias validity is still the caller's concern, not validated here. `seed_mappings_from_config(rows)` is seed-once-only (no-op if the table already has any row) and its `provider_account_id` must be copied byte-for-byte from the old `sparebank1_account_key` — see invariant 2/7, a single character of drift breaks every existing `tracked_transactions` match and the burned YNAB `import_id`s that depend on it.

- `frontend/` — a React + Vite + Tailwind SPA (TypeScript) served by the FastAPI backend above. Five tabs, no router. See `frontend/CLAUDE.md` for the per-component breakdown and the build gotcha (no hot reload — must run `npm run build`).

## Core invariants — do not violate these without re-deriving why they exist

1. **YNAB's `import_id` is the authoritative no-duplicates guarantee, always.** Local SQLite state (`tracked_transactions`) is a performance/tracking layer only — it may be lost or reset without ever causing a real duplicate in YNAB, because `engine.py`'s `_backfill_duplicates` resilience path recovers via `find_transaction_by_import_id()` whenever YNAB reports a submission as a pre-existing duplicate. Never build a design that relies on local state being the source of truth for dedup.

2. **Never derive the tracking/dedup key from SpareBank1's own `id` field.** This was a real, live production bug: `id` was proven to change on *every single poll* of a still-pending credit-card transaction (two fetches of the same real charge, hours apart, returned completely different `id` strings — same `nonUniqueId`, same everything else). The correct key comes from `transform.get_tracking_key(sb1_tx, account_key)`:
   - Prefers `creditCardIdentifiers.nonUniqueId` when present (booked credit-card transactions — a structured, specific field).
   - Falls back to the raw top-level `nonUniqueId` (pending credit-card transactions, and all regular bank-transfer transactions, which never have `creditCardIdentifiers`).
   - Scoped by `account_key` (SpareBank1's own field is literally named "nonUniqueId" — it warns you it isn't globally unique).
   - `get_transaction_id()` (reading `id`) still exists for logging/display only — it must never feed `derive_import_id()` or any `tracked_transactions` key again.
   - **`creditCardIdentifiers.nonUniqueId` itself was separately confirmed live to be format-unstable**, not just a safe structured alternative to `id`: for the identical already-booked transaction, SpareBank1 re-served it bare (e.g. `"708046574"`) when freshly observed (`source: "RECENT"`) and `partitionKey`-prefixed (e.g. `"2926243-708046574"`, matching the top-level `nonUniqueId` field) once the same transaction aged into `source: "HISTORIC"`. `get_tracking_key()` now unconditionally strips a `f"{partitionKey}-"` prefix when present, always normalizing to the bare form — never the reverse — since years of already-tracked credit-card `import_id`s were derived from the bare form (see "Resolved: `creditCardIdentifiers.nonUniqueId` format drift across RECENT→HISTORIC" below).

   **Generalized for the provider seam:** every provider must derive `NormalizedTransaction.tracking_key` from a field *proven stable across polls of the same real-world transaction*, verified live against that provider's own API — never from something that might be a per-response id. The warning is restated in `providers/base.py`'s docstring so a future provider's author meets it there rather than rediscovering this bug with a different bank. Also note **`provider_account_id` is load-bearing, not cosmetic**: it prefixes every SpareBank1 tracking key, so it must survive any migration or rename byte-for-byte (see the `account_mappings` seed).

3. **`tracked_transactions` rows are written immediately as each YNAB call succeeds — not deferred to end-of-cycle** — while `account_cursors`/`run_metadata` are only persisted by the *caller* (`scheduler.py`) after the whole cycle succeeds. This split is deliberate: cursor advancement is all-or-nothing per cycle (a failure means next cycle's overlap window retries everything), but transaction tracking reflects real external state the moment it's true, so a later-budget's failure in the same cycle can't cause a retry to re-attempt creating an already-created transaction.

4. **Amounts are NOK from SpareBank1 (not a minor-units API, confirmed live), parsed into an exact `Decimal` via `sync/money.py::parse_provider_amount()` and converted to YNAB milliunits via `sync/money.py::to_milliunits()`.** `Decimal` (not `float`) is the canonical internal amount type everywhere — see "Currency amounts: Decimal, not float" below for the full design and why this changed. `parse_provider_amount()` goes through `Decimal(str(raw))` for a float input, never `Decimal(raw)` directly, to avoid inheriting float's binary representation noise. `to_milliunits()`/`from_milliunits()` are the only two places milliunits conversion happens, and both are exact (1000 is a power of ten).

5. **Dates from SpareBank1 are Unix epoch milliseconds** (`get_transaction_date()` handles this) — a real bug (`ValueError`, not caught) before it was found and fixed. Occasionally an ISO string appears too; both are handled. **The epoch-ms value encodes LOCAL (`config.sync.timezone`) midnight, not UTC midnight** — `get_transaction_date()` takes a required `timezone` parameter and converts via `ZoneInfo(timezone)` before truncating to a date; converting via UTC instead (the bug, live until 2026-08-25) rolls every transaction back onto the previous calendar day, every season, since Oslo is always ahead of UTC. See "Resolved: SpareBank1 transaction dates were a day early" below.

6. **YNAB permanently reserves an `import_id` once used, even after the transaction using it is deleted — and its plain (non-delta) transaction list silently excludes deleted transactions.** Confirmed live: a transaction resolved as a "duplicate" that can't be found via `find_transaction_by_import_id()` (account-scoped, plain list) may still exist, just deleted — check with `find_transaction_including_deleted()` (budget-wide, `last_knowledge_of_server=0`) before concluding local state is genuinely broken. When a deletion is confirmed, `_backfill_duplicates` marks the row `booking_status='DELETED'` **permanently** — never retried automatically, by design (an intentional deletion, e.g. a real duplicate cleaned up by hand, must not be silently resurrected). If a deletion turns out to have been a mistake, `SyncEngine.readd_deleted_transaction()` (invoked via `scripts/readd_deleted_transaction.py` or the GUI's DeletedTransactions tab) re-creates it from the persisted payee/memo/date/amount/cleared data with a fresh, derived import_id (the original stays burned forever). **Related, separately confirmed live**: `PATCH .../transactions` silently IGNORES an `import_id` key in an update payload — 200 response, but the field reads back `null` immediately after (`scripts/verify_ynab_import_id_patch.py`). There is no API-level way to retroactively grant an existing transaction real import_id-dedup protection; the only way is to delete it and create a fresh transaction with the import_id set from the start — see "Manual-transaction matching (opt-in)" below for where this mattered.

7. **File-import dedup keys are derived from stable *content* fields (date + amount + casefolded payee + casefolded memo), hashed — never from any row-assigned or file-provided id.** A bank export file has no equivalent of SpareBank1's `nonUniqueId` at all, so this isn't just the safer option, it's the only one — same underlying invariant as #2, applied to a source that never had a candidate id to misuse in the first place. `sync/file_import/dedup.py`'s `IMPORT_ID_PREFIX = "FILE:"` is deliberately distinct from `transform.py`'s `"SB1:"`: the two dedup domains (live-poll vs. file-import) must never collide even if the same real-world transaction is later observed by both paths, since `derive_import_id` hashes only the raw pre-prefix string as its entropy source — a shared prefix would silently and permanently merge two unrelated dedup domains in YNAB. `tracked_transactions.sb1_transaction_id` (the PK column) now holds either a live-poll tracking key (`{account_key}:{raw_id}`) or a file-import one (`file:{ynab_account_id}:{dedup_hash}`) — the column name is a pre-existing misnomer, not a bug; it was already "just the tracking key string" before file-import existed.

   **Prefix rules, now that there can be many sources:** a source's prefix is a **frozen literal** it owns — `"SB1:"` must never be computed from `provider.type_name()` or anything else that could change, because YNAB permanently burns every `import_id` it has seen (invariant 6) and a changed prefix would silently re-import that source's whole history as duplicates. Two sources must never share a prefix. `sync/import_ids.py` centralizes only the hashing/truncation; the prefix stays with the source deliberately. `readd_deleted_transaction` re-derives inside the ORIGINAL row's domain (via `import_ids.prefix_of`) — it used to always mint an `SB1:` id even for file-imported rows, which was a real (if benign, since the id was always fresh) domain crossing.

8. **Account-to-account transfers use YNAB's real, native linked-transfer mechanism — never both sides as independent transactions once matched.** Confirmed live via `scripts/verify_ynab_transfer.py` before this was designed (per the standing rule below), not assumed: creating a transaction with `payee_id` set to the destination account's auto-generated `"Transfer : <name>"` payee (found via `ynab_client.get_payees()`/`find_transfer_payee_id()`) makes YNAB **auto-create the paired transaction on the other account itself** — the caller must never submit both sides. Two load-bearing facts this depends on, both confirmed the same way:
   - **The auto-created side gets `import_id: null`** — YNAB assigns it none. `engine.py`'s `_record_transfer_secondary()` therefore writes a locally-synthesized, clearly-marked `"LOCAL:XFER:..."` import_id for that row's `tracked_transactions` entry — this value was never sent to or recognized by YNAB and must never be reused to attempt a real API call against it.
   - **Transfers only work within one YNAB budget.** `engine.py`'s `_match_transfers()` therefore only ever looks for pairs within one budget's own newly-classified transactions (`creates_by_budget`'s existing per-budget grouping already provides this scoping for free) — a transfer where the two accounts map to different budgets always imports as two ordinary, independent transactions, unchanged from before this feature existed.

   Matching itself (`sync/transfers.py::find_transfer_pairs`) requires opposite-sign, equal-amount, different-account, within `config.sync.transfer_match_window_days` (default 4 — credit-card payments can take until the "next working day" to become visible, confirmed by the user to sometimes exceed 1 calendar day) of each other, **AND** at least one leg's real account-number cross-references the other (see below) — among **only transactions being freshly created this same cycle** — an already-tracked transaction is never retroactively converted into a transfer leg. Ambiguous matches (more than one plausible partner, checked symmetrically on both sides) are skipped entirely, never guessed, matching `_backfill_duplicates`' existing "don't guess" stance elsewhere.

   **Account-number cross-reference, added after a real false positive found via live data**: the sign/amount/account/window rule alone linked a real 158.48 kr salary deposit to an unrelated 158.48 kr grocery purchase on a different account, 4 days later — same amount, opposite sign, nothing else in common, right at the edge of the window. Fetching real transaction data (`GET .../transactions`) turned up two more fields, `accountNumber.value` (the owning account's own real account number, nested, present on every transaction including credit cards) and `remoteAccountNumber` (the counterparty's real account number when known, with `"-1"` as SpareBank1's own sentinel for "not applicable" — confirmed on every card purchase seen). `NormalizedTransaction.account_number`/`remote_account_number` (`providers/base.py`, both `str | None = None`, populated by `providers/sparebank1/transform.py`'s `get_account_number()`/`get_remote_account_number()`) carry these through `_PendingCreate` into `TransferCandidate` (`sync/transfers.py`), which now requires `c.remote_account_number == other.account_number` **or** `other.remote_account_number == c.account_number` — deliberately OR, not AND. A genuine bank-to-bank transfer (confirmed live, 39722.10 kr) has **both** directions resolve correctly. A genuine credit-card bill payment (confirmed live, 18289.30 kr) only has **one** direction resolve: the checking-account leg's `remoteAccountNumber` names the card issuer's own internal clearing account (e.g. "Sparebank 1 Kreditt AS"), not the card itself, but the card's own transaction feed (`typeCode: "K_0047"`, description "Innbetaling") correctly names the checking account back — so requiring both directions would have silently broken all credit-card-payment linking, which is exactly why a hand-curated `typeCode` allowlist (the first design tried) was abandoned in favor of this direct identity check: no SpareBank1 `typeCode` reliably identifies a credit-card payment as "transfer-shaped." A provider/test that never populates `account_number`/`remote_account_number` simply never participates in transfer-matching at all (safe default — two ordinary transactions, not a crash), so this is additive for SpareBank1 only, not a behavior change for a future provider that doesn't implement it.

   **Known residual risk, documented rather than silently accepted**: if the process crashes in the narrow window between `_record_created` writing the primary leg's `tracked_transactions` row and writing the secondary's (two back-to-back local SQLite writes, no network call between them), the secondary could be left permanently untracked. A later cycle would then see it as a fresh "new" transaction from its own account's own fetch and submit it independently — and since YNAB's auto-created secondary has no import_id for that submission to collide with, this specific narrow case would create a genuine duplicate. Not fully solved (would need wrapping both upserts in one atomic DB transaction, a larger `StateDB` change) — deliberately left as a known gap rather than pretending it can't happen.

   Also confirmed live and worth knowing: a transfer-creating submission's `create_transactions` response lists the **same transaction id twice** in `transaction_ids` — `total_created`/`CycleResult.created` is therefore computed from `_record_created`'s own return value (rows actually written locally), never from `len(response["transaction_ids"])`. And YNAB defaults the auto-created secondary's `cleared` to `"uncleared"` regardless of what the primary was created with — if SpareBank1's own data says that leg is already `BOOKED`, `_record_transfer_secondary` immediately issues a follow-up `update_transactions` PATCH to correct it, rather than waiting for a future poll's normal pending→booked transition.

9. **`StateDB` is safe under the concurrency the GUI introduces (a webapp route and a scheduler cycle now routinely overlap on one process, not just rarely via a manual script), via three mechanisms together, not one:** `PRAGMA journal_mode=WAL` (readers don't block on a writer), `PRAGMA busy_timeout=5000` (a writer that finds the DB locked by another *process* waits and retries instead of raising immediately — this is what replaces `scripts/readd_deleted_transaction.py`'s old "if locked, just retry" folklore with an actual mechanism), and an `asyncio.Lock` around every mutating method (serializes writes *within* this process, since the scheduler and the webapp share one event loop per `__main__.py`'s `asyncio.gather`, not separate OS threads). All three matter: WAL/busy_timeout alone wouldn't stop two of this process's own coroutines interleaving mid-transaction (see `_backfill_duplicates`'s awaited network call between a read and a write on the same key); the lock alone wouldn't help a genuinely separate process (e.g. the CLI script run manually) or make concurrent reads fast. `check_same_thread=False` is also required on the connection — not for real concurrency safety (the lock/WAL provide that), but because some ASGI test/runtime paths (confirmed with Starlette's `TestClient`) dispatch into a different OS thread than the one `StateDB` was constructed on even for a fully `async` app.

10. **Mapping invariants are enforced on every WRITE, not at startup — because mappings are now mutable at runtime.** `config.py`'s `model_validator` used to guarantee, once and fail-fast, that no two accounts shared a key and no two shared an `import_source_name`. Moving mappings into the GUI-editable `account_mappings` table destroys that guarantee unless it is re-derived, so `StateDB.create_mapping`/`update_mapping` raise `MappingValidationError` (surfaced as HTTP 422) for a duplicate `(provider, provider_account_id)` — backstopped by a real `UNIQUE` constraint, with `sqlite3.IntegrityError` caught and re-raised rather than leaking a raw sqlite error to an API caller — and for a duplicate non-empty `import_source_name` (checked explicitly; no UNIQUE index is possible since blanks must repeat freely). `webapp/routes/mappings.py` additionally validates `ynab_budget_id` against `config.ynab.budgets.values()` on every write, the third thing the old startup validator covered. If you add a new mapping invariant, it goes in the write path — a startup-only check is now decorative.

11. **Re-pointing an already-synced account at a different YNAB account does NOT move or re-import its history**, because `tracking_key` is scoped by `provider_account_id`, not by the mapping row, and the old `import_id`s are permanently burned in YNAB (invariant 6). This is a genuine, irreversible user-facing consequence, not an implementation detail: `StateDB.count_tracked_for_account()` exists so the GUI can warn before it happens, and `Mappings.tsx` blocks such a change behind a confirmation that says so concretely. Don't "fix" this by re-keying tracked rows on remap — that would re-import everything as duplicates.

12. **A transaction's `payee_name` is only ever an exact-match lookup in YNAB — creating with the same raw text after the user renames/merges that payee in YNAB does NOT reuse the rename, it creates a brand-new payee under the old name.** This was a real reported bug, root-caused by reading the code (every create path always sent `payee_name`, never `payee_id`) and then confirmed live via `scripts/verify_ynab_payee_id.py`: after renaming a payee via the API, resubmitting the original `payee_name` created a second, separate payee, while submitting the same `payee_id` correctly attached to the renamed one. The fix: `StateDB.payee_mappings` (see architecture map) caches the `payee_id` YNAB assigns the FIRST time a given raw `(ynab_budget_id, raw_payee_name)` pair is created; `engine.py`'s `_classify()` looks it up before every create and passes it to `build_create_payload(payee_id=...)`, which then omits `payee_name` entirely (YNAB rejects/ignores neither being informative — the two are mutually exclusive on create, confirmed the same way). `_record_created()` populates the cache from the create response's own `payee_id`, but only for a create that used `payee_name` (i.e. `payee_id` wasn't already set on the outgoing payload) — this excludes a transfer primary leg, whose `payee_id` is YNAB's own transfer payee (invariant 8) and must never be cached under a merchant name. First-write-wins (`INSERT OR IGNORE`) is deliberate: the cached id is a permanent anchor to whatever the user has renamed the payee to, so a later create must never silently overwrite it. **Gap closed**: `SyncEngine.reconcile_payee_mappings()`, called non-fatally from `scheduler.py`'s `_reconcile_payee_mappings()` at the end of every `_do_cycle()` (rate-limited internally to once per day — see below), hybrid-checks each configured budget's cached `payee_id`s — a cheap bulk-list first pass trusts any id still present, and only the (typically few) ids absent from that list get a targeted per-payee GET to confirm before anything is healed (`StateDB.delete_payee_mappings_for_ids`). Deliberately does NOT guess what the deleted payee was merged into (YNAB's payee list gives no such linkage, confirmed against sibling project `../ynab-auto-bank`'s identical stance); the next create for that raw payee text simply re-learns a fresh `payee_id` through the normal `_classify()`/`_record_created()` path. See "Payee-mapping reconcile pass" below for the full design, including two real design mistakes/refinements caught via live verification along the way (a pure bulk-list scan was tried first and proven to never detect a real deletion; a pure per-id design fixed that but cost far more API calls than needed). **Newly-confirmed live gap, worse than the reconcile pass alone can prevent (found via real production data, 2026-08-25)**: the reconcile pass only protects the *next* create after its once-a-day sweep — a payee deleted/merged in YNAB *during* that window is still used by any create that happens before the next sweep. Confirmed live from the raw request/response logs that submitting a create with such a now-stale `payee_id` is NOT rejected: YNAB returns 200 but silently drops it, coming back with `payee_id` **and** `payee_name` both `null` — worse than "doesn't reuse the rename," this loses the payee entirely with no automatic recovery. `_record_created()` now detects this directly (submitted `payee_id` truthy, response's `payee_id` falsy, and not a transfer primary leg — see invariant 8, whose `payee_id` is YNAB's own transfer payee and should never legitimately hit this): it heals the stale `payee_mappings` row immediately via the same `delete_payee_mappings_for_ids` the reconcile pass uses, uses `_PendingCreate.payee_name` (the raw text, carried separately from `ynab_tx` for exactly this kind of correction — see its own docstring) for the local `tracked_transactions`/`audit_events` write instead of persisting `NULL`, and issues one corrective `update_transactions` PATCH so the transaction gets a real payee in YNAB too. Confirmed live (`scripts/verify_ynab_payee_name_patch.py`) that PATCHing `payee_name` genuinely takes effect — unlike `import_id`, which `update_transactions` is separately confirmed to silently ignore (see invariant 6's addendum), so this could not be assumed to behave the same way without checking.

## Cycle-failure retry with backoff

Added after a real SpareBank1 500 error was observed to just sit as a single recorded failure until the next cron fire, hours later, with no attempt to recover sooner. `scheduler.py` now retries a failed cycle with exponential backoff, entirely on its own (the engine has no retry logic beyond the pre-existing per-GET `http_retry.retry_get`):

- **Backoff schedule**: `sync.retry_backoff_base_seconds * 2**attempt`, capped at `sync.retry_backoff_max_seconds` (defaults 60s / 1800s). Tunable in `config.yaml` without a code change.
- **Bounded by the next cron fire, not open-ended**: before scheduling a retry, `_schedule_retry()` checks whether `now + delay` would land before the next scheduled cron fire (`_next_cron_fire_at()`). If yes, an earlier wake-up is scheduled (`_retry_deadline`, folded into `_run_loop`'s existing wait via `_seconds_until_next_wake()` — the same `asyncio.wait(timeout=...)` that already listens for `stop`/`sync_now`, so a retry wait is interruptible exactly like the normal cron wait). If the delay would land at or after that fire, retrying is pointless — that fire will attempt a fresh cycle anyway — so `_schedule_retry()` gives up instead: clears all retry state and lets the normal cron-triggered attempt happen.
- **Two failure categories, handled differently** (`_attempt_cycle()`): a failure during `engine.fetch_and_classify()` (the provider-hitting phase) has nothing worth caching — the next retry re-fetches from scratch. A failure during `engine.submit()` (the YNAB-writing phase) is different: the already-classified data (a `ClassifiedCycle`) is cached on the scheduler (`_cached_classified`) and reused on the next retry, so a YNAB outage is retried by re-hitting *only YNAB*, never re-polling the provider — this was an explicit requirement, not an incidental optimization. Safe to do because `submit()` is idempotent on retry (see the engine.py architecture-map entry above) — resubmitting an already-created budget's transactions alongside a still-failing budget's is harmless, just reported back as `duplicate_import_ids` YNAB-side.
- **`ProviderAuthRequiredError` is explicitly excluded from backoff retry** — a revoked/expired OAuth token needs a human BankID re-login; retrying against the same broken credentials on a timer achieves nothing and just adds noise. This is unchanged from pre-retry behavior: `auth_required` failures still just wait for the next natural cron fire.
- **Any successful cycle clears all retry state** (`_clear_retry_state()`) — attempt count, retry deadline, and any cached `ClassifiedCycle` — regardless of whether that success came from the normal cron fire, a scheduled backoff retry, or a manually-triggered "sync now" (`POST /api/sync-now` / MQTT `sync_now`). A user manually forcing a sync is exactly how someone breaks out of an ongoing backoff loop after fixing whatever was wrong.
- **Known, accepted tradeoff**: cached classified data can be resubmitted for as long as the retry loop keeps going before the next cron fire (up to several hours with large cron gaps and the 30-minute backoff cap) — meaning any *new* bank transactions that occurred during an extended YNAB outage won't be picked up until the next cron-fired fetch. This matches the explicit request behind this feature (avoid hitting the provider's API repeatedly during a YNAB-side outage) and is judged an acceptable staleness window, not a bug.
- **File import (`POST /api/import`) deliberately has NO retry/backoff at all** — see `routes/file_import.py`'s architecture-map entry above. It's a single user-initiated request, not a background loop; a YNAB failure during the commit is reported straight back as a 503 with a clear message, and the user re-uploads to retry manually.

## Live GUI push updates

The dashboard used to only poll `GET /api/status` every 15s. It now also gets pushed updates over `GET /api/ws` (a new websocket route), with polling kept as an automatic fallback rather than removed:

- **Message envelope**: `{"type": "...", "data": {...}}`. `status_snapshot` (the full `GET /api/status` shape, sent once immediately after a client connects, via a `build_status_payload(config, db)` helper factored out of `routes/status.py` so the REST route and the websocket route can never drift apart), `status` (partial — just `{"run_metadata": {...}}`, mirroring `publish_status`'s existing call sites 1:1), `sync_state` (`{"value": "running" | "idle"}` — `"idle"` is new, see below), `cycle_progress` (`{"phase": "fetching" | "submitting", ...context}`, e.g. `{"phase": "fetching", "provider": "sparebank1", "accounts": 3}`).
- **In-cycle progress is opt-in instrumentation, not a new correctness dependency**: `engine.py`'s `fetch_and_classify()`/`submit()` take an optional `on_progress` callback (default `None`), called once per provider (before `provider.fetch()`) and once per budget (before each YNAB write) — coarse phase boundaries "for free" from where the engine already loops, no new state. Every call is wrapped in `_report()`, which catches and logs any callback exception rather than letting it propagate — a broadcast bug must never turn into a failed (or worse, half-completed) sync cycle. `scheduler.py`'s `_attempt_cycle()` passes a `_report_progress` adapter into both engine calls; `SyncEngine` itself still has zero knowledge of `NotificationSink` or websockets.
- **`sync_state="idle"`** is a new value `_do_cycle()` publishes (after `publish_status`, in the same `finally` block) once an attempt — success or failure — is over. Previously only `"running"` was ever published; MQTT/Home Assistant didn't need the opposite signal, but the dashboard's progress panel does (to know when to hide itself), so this is additive rather than a behavior change for existing MQTT consumers.
- **`CompositeSink` exists because MQTT and the GUI websocket are two independent, both-optional broadcast concerns** (`config.mqtt.enabled` vs `config.gui.enabled`) and `Scheduler` only ever holds one `sink`. `__main__.py`'s `_build_sink()` returns `NullSink()` if neither is active, the single sink directly if exactly one is, or a `CompositeSink` fanning out to both — see the `notifications/` architecture-map entry above for the isolation guarantees. This is the same reason `ConnectionManager` is built once in `main()` and threaded into both `_build_sink()` and `create_app()`: one shared instance, not two.
- **No new auth surface**: `/api/ws` inherits the GUI's existing no-app-level-auth trust model, same as every REST route — the reverse proxy in front of this app is the only boundary.
- **Real bug found and fixed while building this**: FastAPI does not resolve `Depends(...)` functions typed for an HTTP `Request` when used on a `@router.websocket(...)` route — it raises a `TypeError: missing 1 required positional argument: 'request'` at connection time (confirmed live, not from docs). `routes/ws.py` reads `websocket.app.state.*` directly instead of reusing `deps.py`'s `get_config`/`get_db`/`get_ws_manager`.
- **Reverse-proxy dependency, not verifiable from this repo alone**: a websocket connection needs `Upgrade`/`Connection` headers forwarded by the reverse proxy, which `deploy/swag/ynab.subdomain.conf` now sets — but `$connection_upgrade` needs a `map $http_upgrade $connection_upgrade {...}` directive in nginx's `http{}` scope (SWAG's own `nginx.conf`, outside this repo). If missing, the websocket handshake fails **silently from the user's point of view** — the frontend's automatic polling fallback (below) means the dashboard keeps working, just without live updates, so there's nothing that visibly breaks to prompt someone to go check the proxy config.
- **Frontend resilience** (`frontend/src/contexts/SyncStatusContext.tsx`): reconnect with exponential backoff (1s → doubling → capped at 15s, same ceiling `notifications/mqtt_sink.py` uses server-side, reset on a successful connect), and the dashboard's old 15s poll moved into this provider as an automatic fallback — running whenever `connectionState !== "open"`, starting immediately on mount/disconnect and stopping the instant the socket opens, so there's never a gap with no data flowing and never double-fetching once the socket is live. The connection-state indicator (`Dashboard.tsx`'s footer) is a deliberately visible amber badge ("Reconnecting… showing data every 15s") when disconnected, not a quiet footer note — precisely because the proxy-misconfiguration failure mode above is otherwise silent.
- **Server-side heartbeat, not a reverse-proxy timeout override**: `routes/ws.py` sends a `ping` message every 20s of inbound silence (`HEARTBEAT_INTERVAL_SECONDS`), keeping the connection non-idle from the proxy's point of view without requiring the user to also raise a `proxy_read_timeout`-style setting — more portable across whatever reverse-proxy product someone actually has in front of this app, not just SWAG.
- **Cloudflare Access + WebSocket incompatibility, confirmed live (2026-08-25)**: Cloudflare Access authenticates by injecting an HTTP 302 redirect to its login page. A raw WebSocket handshake cannot follow a redirect, so the connection hangs with no response at all instead of failing cleanly. Fix: create a **separate, path-specific** Access Application (not just a new policy in the existing one) with path `/api/ws` and set its action to `Bypass` instead of `Allow` or `Deny` — "Bypass" skips Access's auth entirely, while "Allow" still runs the redirect flow. When testing with `curl` or raw sockets, remember to include the `Host` header matching the reverse-proxy's expected `server_name` (e.g., `-H "Host: ynab.bergee.net"`), otherwise the proxy routes to the wrong backend. If you're using SWAG behind cloudflared, verify two more things: (1) your reverse-proxy config (e.g. `ynab.subdomain.conf`) does NOT duplicate the WebSocket headers (`Upgrade` / `Connection`) — SWAG's default `proxy.conf` already sets them, and duplicating causes nginx to send malformed headers; (2) verify the `map $http_upgrade $connection_upgrade {...}` directive exists in nginx's `http{}` scope (SWAG's `nginx.conf`, not the subdomain config), not just in the proxy.conf include.

## Discrete event notifications (`alerts/`) vs continuous state (`notifications/`)

Two separate output-side seams exist on purpose, both optional, neither aware of the other:

- **`notifications/`** pushes continuous **state** — `sync_state`, `run_metadata` counters, in-cycle progress — to a dashboard (GUI websocket) or Home Assistant (MQTT). This is what existed before this feature and is **unchanged** by it.
- **`alerts/`** pushes discrete **events** — one message per finished cycle, categorized as plain success / success-with-changes / error — to something like a phone (ntfy.sh today). Each of the three is independently toggleable via `NtfyConfig.notify_on_success`/`notify_on_success_with_changes`/`notify_on_error`.

`Scheduler` holds both (`self._sink: NotificationSink`, `self._notifier: EventNotifier`) and calls into each independently from `_attempt_cycle()`; neither seam imports or references the other.

- **Success classification**: `result.created > 0 or result.updated > 0` → `notify_success_with_changes`, else `notify_success`. `duplicates`/`resolved_deleted` alone do NOT count as "changes" — they're not new financial data worth a push notification, unlike a created/updated transaction.
- **Error-notification dedup, an explicit requirement**: the pre-existing retry/backoff mechanism (see above) can retry a failing cycle every 60s–30min for hours during a real outage — without dedup, that would push a notification on every single retry. `Scheduler._maybe_notify_error()` tracks the exact message string of the last error actually pushed (`_last_notified_error`); a repeat of the same message is silently skipped, a different message (or the first failure of a fresh outage) pushes again. Deliberately **not** folded into `_clear_retry_state()`/`_schedule_retry()` — this dedup state must survive "give up retrying, wait for next cron fire" the same way the underlying unresolved error does, and only resets to `None` on an actual success. **Known, accepted limitation**: dedup is by exact message text, so a message that varies slightly between retries (e.g. embeds a timestamp) would defeat it and notify every time — not solved, call it out if ever observed in practice.
- **`fetched_last_run` metric**: added alongside this feature (not strictly part of it) — the raw pre-dedup/classification fetch count already existed as `ClassifiedCycle.fetched_count`/`CycleResult.fetched` but was previously only ever logged. Now persisted (`run_metadata.fetched_last_run`, via the same migration mechanism as `resolved_deleted_last_run` before it), published (new MQTT discovery sensor, forwarded automatically over the GUI websocket/`GET /api/status` since both already forward `read_run_metadata()`'s dict verbatim), shown on the dashboard, and included in ntfy message bodies.
- **Why a new package instead of extending `NotificationSink`**: the two concerns have genuinely different shapes (continuous state with a connection lifecycle + command stream, vs. discrete fire-and-forget events with none) and different failure/config independence requirements (MQTT/GUI vs. ntfy/future providers) — forcing them through one interface would mean either sinks growing unrelated methods or the abstraction leaking one concern's assumptions into the other. Follows the same seam pattern already established twice in this codebase (`providers/`, `notifications/`): an ABC, a `Null*` no-op, a `Composite*` fan-out with per-child isolation, a `_build_*()` constructor in `__main__.py`.

## Don't sync at startup unless a cron fire was missed

`scheduler.py::_run_loop()` used to unconditionally run a sync cycle the moment it entered the loop — meaning every process restart (a deploy, a config change, a crash-and-restart) triggered an extra, redundant sync even when the last cycle had run moments ago. Fixed via `cron.py::previous_fire_at()` (the `get_prev()` mirror of the existing `next_fire_at()`) and `Scheduler._missed_scheduled_fire()`, which compares `run_metadata.last_run_at` against the most recently scheduled fire time:

- **Only checked on `_run_loop()`'s very first iteration** (`skip_startup_sync = startup and not self._missed_scheduled_fire()` — Python's `and` short-circuits, so the check is never even evaluated past the first pass). Every later wake — a natural cron fire, `sync_now`, a backoff retry — cycles unconditionally, exactly as before this change.
- **Uses `last_run_at`, not `last_success_at`**: both success and failure paths stamp `last_run_at` (`StateDB.record_success()`/`record_failure()`), and a *failed* attempt still means that scheduled slot was handled — retrying a recent failure sooner than the next natural fire is the pre-existing backoff mechanism's job (see "Cycle-failure retry with backoff" below), not startup's.
- **A fresh install/state DB (`last_run_at` still `NULL`) is always treated as missed** — preserves the original "first-ever start syncs immediately" behavior rather than requiring a full cron interval to pass before the very first sync.
- **Paused takes priority**: if `run_metadata.paused` is set, the startup check is never even reached — no cycle runs regardless of whether a fire was missed, matching pre-existing pause semantics everywhere else in the scheduler.

## GUI pause toggle

`run_metadata.paused` already existed (settable only via MQTT's `pause` command, e.g. from Home Assistant) and was already displayed read-only on the Dashboard (see the `paused` state in `OverallState`/`STATE_META`), but had no GUI control to actually change it. Added `Scheduler.set_paused(paused)` — the one shared implementation of "write `db.set_paused()` then republish `sink.publish_state_value("paused", ...)`" — called by both the pre-existing MQTT command handler and the new `POST /api/pause` route (`webapp/routes/pause.py`), so a GUI-triggered pause still republishes to MQTT/HA exactly like an MQTT-triggered one always did; a route that instead called `db.set_paused()` directly would have silently skipped that republish. `Dashboard.tsx` gained a "Pause syncing"/"Resume syncing" button next to "Sync now", reading `run_metadata.paused` straight off the shared `useSyncStatus()` object rather than a locally-tracked mirror, so it reflects pauses triggered from MQTT or another browser tab too, not just its own clicks.

**Real bug, found 2026-08-26 (user report: "pausing/resuming doesn't update over WS")**: `set_paused()` only ever called `publish_state_value`, which the websocket frontend's message handler (`SyncStatusContext.tsx`) explicitly ignores — its `default:` case comments that `state_value` is an "MQTT/Home Assistant concern." The only message type the frontend applies to `run_metadata.paused` is `"status"` (`{"type": "status", "data": {"run_metadata": {...}}}`), and nothing published that on a pause toggle. Net effect: clicking the button wrote the DB and updated MQTT/HA correctly, but had zero visible effect on any connected browser tab — including the one that clicked it, since `handleTogglePaused` never optimistically updates local state — until the next full sync cycle's own `publish_status` call happened to refresh it, or the page was reloaded. Fixed by also calling `sink.publish_status(db.read_run_metadata())` at the end of `set_paused()`, reusing the exact plumbing `_do_cycle()` already relies on rather than teaching the frontend a new message type.

## Runtime-configurable log level

`config.logging.level` used to be the only way to change the log level — hand-edit `config.yaml`, restart the process. The GUI's Dashboard now has a "Log level" dropdown that changes it live, no restart:

- **State, not config — same shape as the account-mappings exception**: `run_metadata.log_level` (`StateDB.set_log_level()`/`read_run_metadata()["log_level"]`) is `NULL` until the GUI control is ever touched, meaning "no override — use `config.logging.level`." `config.yaml`'s value is the seed/fallback a fresh process (or a fresh `state/sync_state.db`) starts with, exactly the same relationship `accounts:` has to `account_mappings` — see the amended non-goals entry above.
- **Applies immediately, not just on next restart**: `webapp/routes/settings.py`'s `PATCH /api/settings` both persists (`db.set_log_level()`) AND calls `logging_setup.configure_logging()` again on the spot. `configure_logging()` was already idempotent (clears and re-adds the one stdout handler, resets the root logger's level) so this needed zero changes to that function — reusing it here is what makes "live" trivial rather than needing a separate "just call `setLevel()`" code path.
- **`__main__.py` reordered on purpose**: `StateDB` is now constructed BEFORE `configure_logging()` is called at startup (previously the reverse), so startup can read any persisted override before deciding what level to configure. Confirmed safe by inspection — `StateDB.__init__` performs no logging of its own, so nothing is lost by delaying `configure_logging()` a few lines.
- **No MQTT/HA integration for this** — deliberately out of scope. Home Assistant's MQTT discovery only has entity types for numeric/binary/switch state (see `mqtt/discovery.py`'s `EntityDescriptor`), not a `select` with an enum of options; adding that machinery for one config knob wasn't judged worth it. The GUI is the only surface for this.

## Manual-transaction matching (opt-in)

Investigated a real report: a Telia bill showed as two independent transactions in YNAB — one manually typed in by the user (no `import_id`) and one from this sync (a real `import_id`). Root cause, confirmed by reading the code: this project's whole no-duplicates guarantee (invariant 1) is scoped to *this tool's own* `import_id`s; `_classify()` never looked at anything a human typed into YNAB by hand. Also confirmed live that the budget had zero YNAB Scheduled Transactions, so YNAB's own native matching (which only fires for a scheduled transaction's own firing, or a Direct-Import-linked account) had nothing to hook into either.

**Two live-verification detours, both worth knowing before touching this code again:**

- **PATCH-ing `import_id` onto an existing transaction is a silent no-op.** Confirmed live (`scripts/verify_ynab_import_id_patch.py`): 200 response, but the field reads back `null` right after. See invariant 6's addendum. This ruled out the obvious first design (attach `import_id` to the pre-existing manual transaction in place).
- **`create_transactions` has its own native, undocumented transaction-matching.** Submitting a transaction with an `import_id` near an existing same-account/same-amount transaction can make YNAB echo that pre-existing transaction back in the SAME response (its `approved` flipped to `false`, `matched_transaction_id` set on both sides) alongside the genuinely new row — confirmed via `scripts/verify_ynab_delete_recreate.py`, fires regardless of payee text similarity. Its exact triggering window is NOT reliably characterized (tested gaps of 5/10/20/40 days: 20 failed to match while 40 succeeded, non-monotonic) — do not depend on it for correctness. Its concrete implication for this codebase: **never index a `create_transactions` response positionally** (`transactions[0]`/`transaction_ids[0]`) whenever a pre-existing similar transaction might still be live at submission time — it can be the OTHER transaction. Always look up by your own submitted `import_id`, the same defense `_record_created()` already needed for the unrelated transfer-response quirk (see invariant 8).
  **Two more facts confirmed live later (2026-08-26, `scripts/verify_ynab_native_match_amount_sensitivity.py`), now load-bearing for the design below**: (1) this native matching requires the submitted amount to be an EXACT match to the existing transaction's — even a 0.42 kr difference suppresses it entirely, reproduced 3 independent ways. (2) The newly-created (`import_id`-bearing) side of a fired match becomes **permanently excluded from `GET .../accounts/{id}/transactions`** (the plain list, almost certainly what the YNAB app's own register renders) regardless of whether its matched partner is later deleted — confirmed via the budget-wide `last_knowledge_of_server=0` listing that it's genuinely NOT deleted (`deleted: false`), just excluded from the normal view. `matched_transaction_id` is read-only (PATCHing it, including to `null`, has no effect) — there is no way to reverse this once triggered.

**Design, redesigned (2026-08-26) around YNAB's native transaction-matching rather than fighting it.** The original design (delete-and-recreate, since patch-in-place doesn't work at all — see above) worked but had a real usability gap: a PENDING match's replacement used the bank's rounded preauth amount, which showed a transiently-wrong amount and never got the "linked" look the exact/BOOKED case did. Investigated live (`scripts/verify_ynab_native_match_amount_sensitivity.py` and follow-ups against the real test budget) rather than guessed, and found two things that reshaped the design:

- **Native matching (see the bullet above) requires the submitted amount to be an EXACT match** to the existing transaction's amount — even a 0.42 kr difference suppresses it entirely. This is *why* the exact/BOOKED matcher always triggered it and the tolerant/PENDING one (submitting the bank's rounded preauth amount) never did.
- **What native matching actually does is not "nice visible linking"** — the newly-created (`import_id`-bearing) side becomes **permanently excluded from `GET .../accounts/{id}/transactions`** (the plain list almost certainly backing the YNAB app's own register) whether or not its matched partner is later deleted, confirmed via the budget-wide `last_knowledge_of_server=0` listing showing `deleted: false` for the "invisible" transaction. `matched_transaction_id` is also confirmed read-only (PATCHing it, including to `null`, has no effect) — there is no way to reverse this. The pre-existing (original) side is untouched by the match itself — its own payee/category/memo survive exactly as the user set them.

Given that, the design now **embraces** native matching instead of avoiding or fighting it:

- `SyncConfig.manual_match_window_days: int = 0` — opt-in, disabled by default, and (since the PENDING-side decoupling below) governs a **BOOKED** ntx's exact-amount matching only. `0` means "no behavior/API-call change from before this feature existed" for BOOKED transactions.
- `engine.py::_classify()`'s "new" branch (only reached when nothing is locally tracked for this transaction) checks a per-account, lazily-fetched candidate list (`ynab_client.list_unimported_transactions()` — no `import_id`, not deleted, never a split/`subtransactions`) for exactly one same-amount, in-window (`manual_match_window_days`, counted via `match_window_unit` — see `sync/date_window.py` above) candidate. Zero or more-than-one candidates are NOT guessed — both fall through to an ordinary create, same "don't guess" stance as `_match_transfers`' ambiguous-pair handling (invariant 8).
- **PENDING-transaction manual-matching is decoupled from `manual_match_window_days`, gated on `pending_import_enabled` alone instead.** Added after a real production incident (2026-08-25): with `pending_import_enabled` on and `manual_match_window_days` at its default `0`, 3 of 9 PENDING imports on a real credit card duplicated transactions the user had already typed into YNAB by hand, because the candidate fetch (`_get_manual_candidates`) and the match attempt were both gated behind the single BOOKED-oriented toggle. A PENDING import colliding with a manually-typed entry is expected, first-class behavior for pending-import specifically (the whole point of importing before the real transaction settles is that a human might beat the sync to it) — not the same "no strong signal, opt-in only" risk `manual_match_window_days` exists to gate for BOOKED transactions (see the "Known, accepted risk" bullet below, which still applies to the BOOKED case only). `_get_manual_candidates`'s fetch gate is now `manual_match_window_days > 0 OR pending_import_enabled`; `_classify()` then gates the actual match attempt per-status independently — a PENDING ntx tries `find_manual_match_tolerant()` whenever `pending_import_enabled`, a BOOKED ntx tries the exact matcher only when `manual_match_window_days > 0`, unchanged from before. Net effect: turning on `pending_import_enabled` alone now costs one extra `list_unimported_transactions()` call per touched account per cycle (even if that account turns out to have no PENDING transactions this cycle), but BOOKED-transaction matching's default-off risk profile is completely unaffected.
- `_classify()`'s manual-match branch builds `_PendingManualMatch.ynab_tx` using the **matched candidate's own exact amount** (`match["amount"]`), not the ntx's — for the exact/BOOKED matcher these were already identical, but for the tolerant/PENDING matcher this is the one deliberate change that makes native matching fire. Every other copied field (category_id/memo/approved/flag_color/payee_id-or-name, fresh import_id) is unchanged — the same fully-formed payload works for either outcome below, so there's no extra API call to handle whichever one happens.
- `submit()`'s `_record_matched()` branches per row on whether the just-created transaction's response shows `matched_transaction_id` set:
  - **Fired**: leave BOTH transactions alone — never delete the original. `tracked_transactions.ynab_transaction_id` is set to the *original's* id (not the new shadow's), so every existing consumer of that column (audit UI, readd-deleted-transaction, the pending→booked fuzzy-transition PATCH target below) keeps its "this id is fetchable" assumption true; the shadow's `import_id` still anchors the dedup guarantee. Also learns `payee_mappings` (invariant 12) from the matched candidate's own `payee_id` — already in hand, no extra API call — so a *future* bank transaction for the same raw merchant text resolves to the same payee automatically, which is the concrete fix for "correctly update payee preferences" going forward.
  - **Didn't fire** (native matching's date-gap sensitivity is confirmed non-monotonic/undocumented, so this can't be guaranteed): fall back to the original create-then-delete behavior — create the replacement FIRST, delete the original only after that succeeds, never the other order (a failed create leaves the original untouched; a failed delete after a successful create leaves both visible, a manually-resolvable duplicate, not lost data). Confirmed live that deleting an already-deleted transaction returns 404, not idempotent success — the retry path catches that specifically as "already done," not an error.
  - A resubmitted match (retry after a prior partial failure) comes back in `duplicate_import_ids`, which carries no transaction body — the shadow's current `matched_transaction_id` state is re-derived via `ynab_client.find_transaction_by_import_id()` before applying whichever branch above it implies.
- **The tracked row's `payee_name` is the BANK's own description (`ntx.payee_name`, passed as `_PendingManualMatch.raw_payee_name`), NOT YNAB's resolved payee from the create response** (`shadow["payee_name"]`, which for a manual match is the user's short custom name). Both `_finish_native_match` and `_finish_fallback` write it this way. This is load-bearing for a PENDING manual match: when the charge later books, `find_pending_match`'s `payees_plausibly_match` hard filter compares that stored payee against SpareBank1's raw BOOKED description — storing "Parkering" instead of "EasyPark AS, …" made that filter fail and the booked charge get created fresh (a real production duplicate on Felleskort, 2026-08-31 — see "Resolved: manual-matched PENDING placeholder stored the user's payee, breaking pending→booked correlation" below). It stays consistent with the `payee_mappings` key `learn_payee` already learns from the same `raw_payee_name`, and the user still sees their custom payee in YNAB (that transaction is never re-PATCHed; a re-add re-resolves `payee_id` via `payee_mappings`).
- **The pending→booked amount/cleared correction, once the real transaction later books, needed ZERO new code.** Tracking the row with `booking_status = ntx.booking_status` (typically `PENDING`) and `ynab_transaction_id` = the visible original means it flows straight into the existing fuzzy pending→booked pipeline (`find_pending_match`/`_PendingFuzzyUpdate`/`rekey_pending_to_booked`, see the section below) — that pipeline already just PATCHes `{id, cleared, amount}` onto whatever `ynab_transaction_id` it's given, and never cared whether that id was self-created or matched-into-existence.
- **No new database column** — traced every read site of `ynab_transaction_id` first (state_db.py's own methods, the audit UI fallback, readd-deleted-transaction, frontend's audit modal); all of them already assume "this id is the one, currently-fetchable YNAB transaction for this row," which pointing it at the original satisfies without any schema change.
- Folded into `CycleResult.created` rather than a new field — a matched transaction is, from `run_metadata`/MQTT discovery/the dashboard/ntfy's point of view, indistinguishable from an ordinary new transaction (both endings result in exactly one net-new tracked row with a real `import_id`, same as an ordinary create — this counting is unaffected by the audit-log distinction below). Distinguished in the audit log instead: `detail="matched & replaced pre-existing manual transaction {id}"` for the fallback ending is logged as `event_type="created"` (a genuinely new visible transaction did appear, replacing the deleted original). **The native-match ending is logged as `event_type="updated"`, not `"created"`** (`detail="natively linked to pre-existing manual transaction {id} (import_id anchored on hidden transaction {shadow_id})"`) — fixed 2026-08-26 after a user report; nothing new appears in the user's register for this ending, the pre-existing original just gets a real `import_id` anchored onto it via the permanently-hidden shadow, so `"created"` miscategorized it in the GUI's Audit Log tab. Confirmed against 3 real production rows (via the `bobk-production-debug` skill) that the raw YNAB create response's `matched_transaction_id` really was mutually set on both sides before recategorizing — both call sites in `_record_matched()` already gate on that field being truthy before ever calling `_finish_native_match()`, so no new verification logic was needed, only the label.
- **Known, accepted risk**: unlike transfer-matching (invariant 8's account-number cross-check), there's no equivalent strong signal for a manual entry — a genuinely unrelated transaction sharing the same amount within the window on the same account would be wrongly claimed. Mitigated by defaulting the feature off, not by trying to eliminate the risk.
- **Deliberately not wired into `import_file_rows()`** — a bulk historical file import isn't the scenario this was built for, and would need its own candidate-cache plumbing for a case that hasn't come up.

## PENDING-transaction import (opt-in, credit-card only)

`config.sync.pending_import_enabled` (default `False` — identical behavior to before this feature existed) lets a PENDING SpareBank1 transaction import immediately (uncleared, at its preauth amount) instead of being skipped entirely, correcting itself once the real transaction books. Investigated by pulling real fetch logs from a live deployment (`state/api_logs/`) rather than assuming — the existing `_classify()` "transitioned" branch (which matches PENDING→BOOKED via exact `tracking_key` equality) turned out to be unusable for this, for reasons that are durable knowledge about SpareBank1's API regardless of this feature:

- **A credit-card transaction's tracking key is NOT stable across its own PENDING→BOOKED transition.** A PENDING row's raw `nonUniqueId` (e.g. `"575213387"`) bears no relation to the same real purchase's `creditCardIdentifiers.nonUniqueId` once BOOKED (e.g. `"708150808"`) — confirmed on 4 separate real transactions, completely different numbers, not a formatting quirk. Distinct from the already-documented RECENT/HISTORIC prefix-drift issue (both fields are present and self-consistent within one booking state; they simply don't correlate to each other across the two states at all).
- **PENDING bank-transfer rows are worse**: `nonUniqueId` is hardcoded to a dummy sentinel `"000000000000000000"`, identical across every pending transfer observed — unusable as any kind of key, not just unstable. This is why the feature is scoped to `CREDITCARD` accounts only, as an **allowlist**, not a blocklist that merely rejects the known sentinel — the same lesson invariant 8 already learned the hard way for transfer-matching (a hand-curated `typeCode` blocklist was tried first there and abandoned, since it silently trusts anything not yet observed). `providers/sparebank1/provider.py::fetch()` checks the sentinel unconditionally (regardless of the toggle) as defense-in-depth on top of the allowlist, not instead of it.
- **A PENDING row's `date` field floats** — it reflects "today"/processing date and moves forward on every poll while still pending, only fixing to the real purchase date once BOOKED. Can differ from the eventual booked date by several days — absorbed by `pending_import_date_window_days`' tolerance (default 5).
- **PENDING amounts are always whole kroner** (no fractional-kroner component — a preauth/hold value), while the BOOKED amount has decimals: sometimes exact, sometimes off by up to ~1.1 kr observed live — absorbed by `pending_import_amount_tolerance_kroner`'s tolerance (default 2.0 kr).
- **Payee text drifts** between a PENDING and BOOKED observation of the same purchase (casing, a trailing country-code suffix appears once booked, and once the location token changed entirely while the merchant-name prefix stayed stable) and **cannot disambiguate two different real transactions alone** — two separate same-day purchases at the same merchant chain produced byte-identical booked descriptions with different amounts, confirmed live.

**Design**: `src/ynab_auto_sync/sync/pending_match.py` (see its own architecture-map entry above) is a multi-signal fuzzy matcher — account + amount tolerance + date window + payee similarity, Levenshtein-edit-distance-based ranking as a tie-breaker when more than one candidate survives the coarser filters, never guessing when even that can't separate two candidates by a clear margin (accepted, documented residual risk: an ambiguous case falls through to an ordinary new create, leaving the stale PENDING placeholder(s) stuck uncleared forever — a visually obvious state in YNAB, not a silent duplicate, same "safe failure mode" reasoning `_find_manual_match`'s own ambiguity handling already uses).

- **Provider layer** (`providers/sparebank1/provider.py`): `SpareBank1Provider.__init__` takes `pending_import_enabled: bool`, threaded from `config.sync.pending_import_enabled` exactly like `timezone` already is — this keeps "should this provider even emit a PENDING row" a provider-owned decision, as it already was structurally before this feature (`fetch()`'s prior unconditional skip). Deliberately **not** a wholesale move of `pending_match.py` into `providers/sparebank1/`: the matcher itself is provider-agnostic (plain `PendingCandidate`/`BookedCandidate` values, no SpareBank1 types), same reasoning `sync/transfers.py`/`sync/date_window.py` already establish for living in `sync/` despite only SpareBank1 populating the fields they need today. When enabled, `fetch()` also calls `list_accounts()` once (already TTL-cached, so normally a cache hit) to resolve each PENDING row's `account_type` for the CREDITCARD allowlist check — zero extra calls when the toggle is off.
- **Engine layer** (`sync/engine.py`): reading `_classify()`'s existing "new" branch shows it **already** handled a PENDING `ntx` correctly before this feature (`cleared="uncleared"`, `booking_status` flows through to `upsert_tracked` unchanged) — so the provider toggle alone is sufficient for the plain create-as-pending path, zero `_classify()` changes needed there. What *is* new: `_classify()` gains a `pending_candidates: list[PendingCandidate] | None` param, tried (for a `BOOKED` `ntx` with nothing tracked under its own key) via `pending_match.find_pending_match()` *before* the manual-match check — a match returns the new `"transitioned_fuzzy"` outcome (`_PendingFuzzyUpdate`). Separately, when `ntx.booking_status == PENDING` (only possible once the toggle is on), the manual-match branch swaps in `pending_match.find_manual_match_tolerant()` instead of the exact `_find_manual_match` — which stays byte-for-byte unchanged for the `BOOKED` case. `_record_matched()` needed **zero changes**: it already persists whatever `booking_status` `_classify()` computed, so a tolerant manual match on a PENDING `ntx` is automatically tracked as `PENDING` and becomes eligible for the exact same fuzzy pending→booked resolution as a self-created placeholder — both converge through `StateDB.list_pending_candidates()`'s single `WHERE booking_status = 'PENDING'` query with no special-casing.
- **State layer, the correctness-critical part** (`sync/state_db.py`): `StateDB.rekey_pending_to_booked(old_tracking_key, new_tracking_key, new_amount_milliunits)` changes a tracked row's **primary key** (`sb1_transaction_id`), not just its status/amount in place like `mark_booked()` — necessary, not merely convenient: a fuzzy-matched booked observation's tracking key is a *different string* from its pending placeholder's, so `mark_booked()`'s same-key `UPDATE...WHERE` can't reach it, and leaving the row parked under the old key would mean every future poll of that real transaction computes the new key, finds nothing tracked, and eventually creates a genuine duplicate once it's no longer a pending-candidate match either. No FK constraints reference `sb1_transaction_id` (this project doesn't use SQLite foreign keys), so a PK-value `UPDATE` is schema-safe. Retry-safe the same way the rest of `submit()` is: returns `None` (not an error) when `old_tracking_key` is already gone but `new_tracking_key` already reflects the completed transition — a resubmitted `ClassifiedCycle` after a prior partial failure.
- **One real bug this surfaced**: this is the *first* case in the codebase where a `tracked_transactions` row's primary key changes mid-lifecycle. An older `audit_events` row written before the rekey still references the pre-rekey `tracking_key`, so `webapp/routes/audit.py`'s `db.get_tracked(event["tracking_key"])` lookup would wrongly report "not currently tracked" for a transaction that's actually fine, just rekeyed. Fixed with `StateDB.get_tracked_by_ynab_transaction_id()` as a fallback — `ynab_transaction_id` never changes across the rekey (same already-created YNAB transaction, just getting an amount PATCH), so it's the stable key to fall back to.
- **Known, accepted crash-window gap**, same class of risk invariant 8 already documents for transfer secondaries: if the process crashes between the PATCH succeeding on YNAB and `rekey_pending_to_booked`'s local write landing, a later cycle resubmits the same PATCH (idempotent) and completes the rekey then — safe, just not instantaneous. Not solved (would need one atomic DB transaction spanning the whole retry), deliberately left as a known gap rather than pretended away.

## Operational gotchas

- **The running service does not hot-reload — restart it after any code change.** Python loads `engine.py`/`transform.py`/etc. once at process start; editing them on disk has zero effect on an already-running process until it's restarted. This caused real, time-consuming confusion during the tracking-key bug investigation (the fix was correctly on disk but the live process was still running pre-fix code) — always check `ps aux | grep ynab_auto_sync` and compare its start time against the relevant file's mtime before concluding a fix "isn't working." The frontend has the same problem via a different mechanism: editing `frontend/src/*` has zero effect until `npm run build` regenerates `frontend/dist`, which the backend serves as static files — a stale `dist/` looks identical to a real bug.
- **Running tests/scripts from a git worktree can silently execute the MAIN REPO's code instead of the worktree's own, if you invoke `python`/`pytest` directly.** Confirmed live (2026-08-26) while building the native-transaction-matching redesign: `which python` inside a worktree resolved to the *main repo's* `.venv` (its editable install's `.pth` file points at the main repo's `src/`), so `python -m pytest` ran against unmodified main-repo code the whole time — every test appeared to pass or fail identically regardless of in-worktree edits, which looked like "my change had no effect" and cost real debugging time before `python -c "import ynab_auto_sync.sync.engine as e; print(e.__file__)"` exposed it. Each worktree actually has its OWN `.venv` (created by `uv`) — the fix is to always invoke via `uv run pytest` / `uv run python ...` from inside the worktree, which correctly resolves to that worktree's own environment and source, never the main checkout's. Verify with the same `e.__file__` trick if in doubt.
- **Be precise, not just directionally correct, when advising manual cleanup of financial data.** Advising "check budget X for duplicates from the migration window and clean them up" (without exact identifying criteria — specific import_ids, dates, amounts) led to a legitimate still-pending transaction being deleted by mistake alongside real duplicates. When recommending the user manually delete YNAB transactions based on a hypothesis about what's stale vs. current, give the exact distinguishing fields, not a general heuristic.
- **`ruff`'s default rule set (this repo pins no explicit `select`) includes `B008` (no function calls in argument defaults), which is a false positive for FastAPI's own idiomatic dependency-injection pattern** (`Depends(...)`/`File(...)`/`Form(...)` as a parameter default). `pyproject.toml`'s `[tool.ruff.lint] ignore = ["B008"]` is a deliberate, project-wide exception for this, not an oversight — don't "fix" webapp route signatures to avoid it.
- **The Docker image runs as a fixed, non-root `99:100`** (confirmed via search: Unraid's own default for Docker containers is `nobody:users`, uid 99 / gid 100 — this project deliberately targets that rather than an arbitrary uid, since Unraid/appdata deployments are the primary real-world target). Set via `USER 99:100` in the `Dockerfile`'s runtime stage, numerically rather than via `useradd`/`groupadd` — `python:3.12-slim`'s base Debian image already reserves gid 100 for its own `users` group, so creating a *named* account at that gid would collide; Docker's `USER`/`--chown` accept a raw uid:gid with no `/etc/passwd` entry required, and this app has no home-directory-dependent behavior, so there was no reason to fight that collision instead of just sidestepping it. **Real bug this caused, found via a live Unraid deployment**: the image used to hardcode `uid 1000` (`appuser`), which doesn't match Unraid's default appdata directory ownership — `sqlite3.OperationalError: unable to open database file` at startup (`StateDB.__init__`'s `sqlite3.connect()`) because the mounted `state/` directory wasn't writable by that uid, even though `state/tokens/<name>.json` inside it was already readable (readable-but-not-writable is the tell: `mkdir(parents=True, exist_ok=True)` had already succeeded, so the failure was specifically at creating the new `sync_state.db` file, not at reaching the directory at all). Fixed by switching to `99:100` and documented in README's "Deploying to your docker host" section — a host directory still needs to actually be `chown`ed to `99:100` (or already is, if created by a prior Unraid docker container using the same default) for this to work; the image can't fix host-side ownership itself.

## Standing rules for future work

- **Live-verify any new or changed assumption about SpareBank1/YNAB API behavior before trusting it in the real sync path.** This project's single most effective practice: every non-obvious API detail here (SpareBank1's OAuth host, the transactions endpoint's real field names, YNAB's `/budgets` vs `/plans` resource path, the bulk PATCH update shape, whether a "get by import_id" endpoint exists) got confirmed or refuted by writing a small throwaway script under `scripts/verify_*.py` and running it against a real account/test budget — never by trusting docs or trained-knowledge guesses alone. Docs have been directly wrong or misleading more than once (SpareBank1's own portal has an internal `expires_in` inconsistency; a guessed YNAB lookup endpoint returned a real 404). Keep doing this for anything new.
- **Quality gate**: `pytest -q` (all passing) and `ruff check src scripts tests` (clean) before considering any change done. No type checker, no coverage threshold — deliberately kept simple.
- **Financially-sensitive logic** (anything touching `sync/engine.py`'s classify/create/update logic, `transform.py`'s key derivation, or the dedup guarantee) deserves direct, careful attention rather than autonomous delegation — independent, well-isolated modules (a new client function, a config schema change, a self-contained store) are good candidates for parallel subagent dispatch; the cross-cutting correctness-critical wiring is not.
- **Git: `commit`, `tag`, and `push` are always-ask operations** — never run any of the three without the user explicitly requesting that specific action in that turn (a prior approval doesn't carry forward to the next one). This repo has version control but no automated commit policy.
- **Do housekeeping proactively, as part of finishing the work — don't wait to be asked.** Whenever something happens that a future session would need to know (a bug root-caused, a design decision made, a new invariant discovered, a risk resolved or newly identified, an assumption confirmed or refuted), update `CLAUDE.md` and `CHANGELOG.md` in the same turn as the change itself, and write/update cross-session memory when the fact is durable enough to matter outside this one conversation (a lesson about how to work with this user, a standing project fact). This is an explicit, standing instruction from the user — not optional politeness. `CHANGELOG.md` doubles as an incident/decision log for future sessions, not just a feature list; keep entries focused on *why* and *root cause*, not a diff summary.
- **Config and state are separate for a reason**: `config/config.yaml` (mostly-static secrets, hand-managed) vs. `state/tokens/<provider>.json` (rotating OAuth tokens, written every ~9 min, one file per provider) vs. `state/sync_state.db` (SQLite, disposable). Never merge these concerns.

## Resolved: SpareBank1 transaction dates were a day early

The user suspected the batch/list transactions endpoint reported the wrong date (booking date instead of "when the money was used") and prepared real sample data (`responses-dev/`: a batch response, a details response, and CSV exports with separate `Kjøpsdato`/`Posteringsdato` columns) to investigate. That premise turned out to be wrong in a useful way: cross-referencing the batch JSON against the CSVs showed the batch endpoint's `date` field, once interpreted in the correct timezone, **already equals `Kjøpsdato`** (the purchase date) — no per-transaction details-endpoint call is needed at all.

**Root cause, found by running the real code against the real sample data, not just reading it**: `get_transaction_date()` did `datetime.fromtimestamp(value / 1000, tz=UTC).date()`. SpareBank1's epoch-ms timestamps encode **local (Europe/Oslo) midnight** for the transaction's real calendar date, not UTC midnight — truncating in UTC rolls every transaction back onto the *previous* calendar day, in every season (Oslo is always ahead of UTC), for every transaction sourced from the epoch-ms field (both credit-card and checking-account transactions). Confirmed on a real transaction: "KANELSNURREN MA, Sandnes, NOR" (-79 kr, `nonUniqueId: "2926243-708150808"`, raw `date: 1787522400000`) has CSV-confirmed `Kjøpsdato = 2026-08-24`; the pre-fix code returned `2026-08-23`. Independently reconfirmed by the project's own pre-existing test `test_get_transaction_date_accepts_epoch_milliseconds`, whose fixture value was itself Oslo-local midnight `2026-08-20` but asserted the buggy `2026-08-19` — the test was locking in the bug.

**Fix**: `get_transaction_date()`/`transform_transaction()` now take a required `timezone` parameter and convert via `ZoneInfo(timezone)` instead of `UTC`, mirroring `cron.py::next_fire_at()`'s existing pattern; `config.sync.timezone` (already `"Europe/Oslo"` by default, already IANA-validated) is threaded through `SpareBank1Provider.__init__` → `__main__.py`'s `_build_providers()`.

**Deliberately forward-only, per explicit user decision**: already-imported YNAB transactions are NOT bulk-corrected — that's real, potentially-already-reconciled financial data, out of scope for this fix. Every transaction imported before 2026-08-25 keeps whatever (one-day-early) date it was created with; only newly-fetched transactions get the corrected date going forward. Not a dedup-key-drift risk — `get_tracking_key()`/`derive_import_id()` derive from `nonUniqueId`, never from date — and not a fetch-window risk — `engine.py::_compute_fetch_windows()`'s cursors are `datetime`-based with an hours-level overlap buffer, independent of this bug.

## Resolved: update PATCH could permanently wedge the sync cycle

Production (`bobk`) got stuck in a retry-backoff loop for hours after a PATCH to YNAB's bulk update endpoint started 400ing on every attempt: `"transaction does not exist in this budget (index: 0), ... (index: 1), ... (index: 2)"`. Since a submit()-phase failure caches the whole `ClassifiedCycle` and resubmits it unchanged on every backoff retry (see "Cycle-failure retry with backoff"), the entire sync — every budget, every new transaction — was completely stuck until manually paused.

**Investigated live** via a new read-only, per-session-permission-gated SSH skill (`.claude/skills/bobk-production-debug/SKILL.md`, formalizing the standing "production data is read-only for debugging" rule for this specific host). The failing PATCH batch actually had 5 rows, not 3 — only indices 0/1/2 were rejected. A budget-wide `last_knowledge_of_server=0` GET confirmed those 3 were `deleted: true, matched_transaction_id: null` — genuinely gone, not merely hidden by YNAB's own native transaction-matching (which the other 2, still-succeeding rows *had* triggered — a separate, already-documented and accepted risk, unrelated to this bug).

**Root cause**: all 5 rows were SpareBank1 PENDING-import credit-card placeholders (see "PENDING-transaction import" above) mid pending→booked correction. `submit()`'s update loops batched every row into one PATCH with zero per-row error isolation - invariant 6's existing "transaction was deleted" detection only ever fired on the *create* dedup path (`duplicate_import_ids`), never on this *update* path. One bad id 400s the whole batch (including otherwise-fine rows), `submit()` raises, cycle stuck.

**A second live check nearly led to the wrong fix.** The user, seeing the "deleted" purchases still visible in their own YNAB app, asked to check for a live replacement under a different id before assuming they were simply gone — searching the account's current transaction list by content (date/amount/payee), not the dead id. It found exactly that: all 3 had a live, manually-typed replacement (`import_id: null`, exact matching amount) already in the register — the user had deleted the confusing uncleared preauth placeholders and typed the correct final amounts in by hand. Blindly marking these `DELETED` for GUI-based manual re-add (the plan before this check) would have created 3 genuine duplicates.

**Fix**, see `engine.py`'s architecture-map entry above for the mechanism (`submit()`'s bulk pre-check + `_recover_missing_pending_update()`'s reevaluate-for-a-manual-match-before-DELETED design) and `ynab/client.py`'s entry for the new `list_transactions_including_deleted()`. `scripts/verify_ynab_update_deleted_transaction.py` verifies the load-bearing assumptions this depends on (a PATCH on a deleted id returns 400; a *mixed* batch of one valid + one deleted id rejects the whole batch, not just the bad row; the budget-wide listing reports `deleted: true` immediately, no propagation delay) — not yet run against the real test budget, since this worktree has no config with real credentials.

## Resolved: an ordinary create's native transaction-match tracked the invisible shadow, leaving real transactions permanently stuck uncleared

User report: two real transactions stayed uncleared in the YNAB GUI despite `tracked_transactions`/`audit_events` both showing a successful "pending → booked (fuzzy-matched, tracking key changed)" PATCH the day before, and `state/api_logs/` confirming YNAB accepted it (200, correct `{"cleared": "cleared", ...}` payload).

**Investigated live on `bobk`.** The PATCH really was accepted — but this morning's full account-transaction GET log (1363 rows) didn't contain either tracked `ynab_transaction_id` at all. Tracing back to the original creation POST showed why: both PENDING-import placeholder creates had `matched_transaction_id` set in the response — YNAB's own undocumented native transaction-matching (see "Manual-transaction matching (opt-in)") had fired, exact-amount-matching them against two pre-existing transactions the user had already manually entered and categorized.

**Root cause**: `_record_matched()` (the deliberate manual-transaction-matching feature's own code) already checks `matched_transaction_id` and tracks the pre-existing *visible* transaction instead of the shadow when it's set (`_finish_native_match`). `_record_created()` — the plain create path used for every ordinary "new" transaction, including opt-in PENDING-import placeholders — had no equivalent check, because native matching had only ever been observed and designed for through that feature's own deliberate candidate search. It turns out to be a property of the create endpoint itself, not of which code path calls it: **any** create with a coincidental exact-amount match against an existing transaction can trigger it. `_record_created()` blindly tracked the shadow's id in this case, and a shadow that fires a native match becomes permanently excluded from the plain account transaction list — so every later pending→booked correction PATCHed a transaction the user's YNAB app can never show, with zero visible effect on the real transaction they were actually looking at.

**Fix**: `_record_created()` now mirrors `_finish_native_match` — when a non-transfer create's response has `matched_transaction_id` set, it tracks that id (the visible original) instead of the shadow's, and logs `event_type="updated"` (not `"created"`), same reasoning as the audit-log fix in "Fixed: native-match manual-transaction linking was audit-logged as 'created' instead of 'updated'" above. Gated on `transfer_secondary is None` so the unrelated linked-transfer mechanism is untouched; the stale-`payee_id` self-heal and `payee_mappings` learning are skipped for this branch (both would operate on the now-irrelevant shadow). **Deliberately not extended** to `_backfill_duplicates`'s own `duplicate_import_ids` retry path for ordinary creates — `_record_matched()` has the identical, already-accepted gap on its own retry path (its `find_transaction_by_import_id` lookup can't find a natively-matched shadow either, same plain-listing exclusion), so this stays consistent with the existing risk-acceptance model. Two already-affected transactions needed manual "cleared" toggling by hand in the YNAB app — no code path can reach them automatically, since their `tracked_transactions` rows point at now-orphaned shadow ids.

**Follow-up, same day, prompted by the user asking "since this needed to be fixed two places, should it be centralized?"**: yes — the fact that `_record_created()`'s copy of this logic was missing for weeks while `_record_matched()`'s existed is exactly the kind of drift a shared helper closes off. Extracted `_track_native_match()` (just above `_record_created()`) covering the `upsert_tracked`/optional `upsert_payee_mapping`/`insert_audit_event` triple both sites need; each call site now differs only in its keyword arguments (`_record_created()` has no pre-known candidate so never passes `learn_payee`; `_record_matched()`'s `_finish_native_match` does, from the manual-match candidate's own `payee_id`) rather than in duplicated logic. Pure refactor — all 458 tests passed unchanged, including both call sites' existing regression tests, confirming no behavior moved.

**Later discovery (2026-08-28): the same bug pattern was silently re-introduced in two more places** — a pending-update recovery case that also calls `_record_matched()` but collapses its `(created, updated)` tuple, and a manual re-add path that never checks `matched_transaction_id` at all. Both are now fixed with regression tests added: `_recover_missing_pending_update()` now returns a 3-tuple `(created, updated, resolved_deleted)` and the caller correctly splits the created/updated counts into separate accumulators; `readd_deleted_transaction()` now finds created rows by import_id lookup instead of positional indexing, and correctly tracks the matched original when native matching fires. Root cause: three independent code paths each grew their own copy of "handle a create response," and only two of the three paths got audited when this bug was first discovered — nothing prevents it from happening again elsewhere, but regression tests now catch it if it spreads.

## Currency amounts: `Decimal`, not `float`

Prompted by a user question ("what is milliunits, can we use `Decimal` internally?"). Full narrative in CHANGELOG.md — this section is the durable, current-state summary.

`Decimal` is now the canonical internal amount type everywhere — `NormalizedTransaction.amount`, `TransferCandidate.amount`, `PendingCandidate`/`BookedCandidate.amount`, `ImportedTransactionRow.amount`, `StateDB`'s mutating methods' `amount` parameter — always major-unit currency (e.g. `Decimal("158.48")` kr), never milliunits, always exact to 3 decimal places. `sync/money.py` owns the ONLY conversion points (`to_milliunits`/`from_milliunits`/`parse_provider_amount`) — see its own architecture-map entry above.

**What deliberately stayed `int` milliunits, and why**: the YNAB API payload boundary (`sync/ynab_payload.py::build_create_payload()`'s `amount_milliunits` parameter, and every literal `ynab_tx`/YNAB-response `dict`'s `"amount"` key throughout `engine.py`) — YNAB's own API requires int milliunits regardless of internal representation, so there's nothing to gain converting it, only an extra conversion at the one point that actually talks to YNAB. The webapp's JSON API responses (`amount_milliunits: int`, still computed via `to_milliunits()` at the route layer) and the frontend (`formatNok`, `number`-typed TS interfaces) — this refactor changes internal representation only, never the wire contract, so the frontend needed zero changes. SQLite's `amount_milliunits INTEGER` columns — kept alongside the new `amount_decimal TEXT` columns rather than replaced, since `list_audit_events`'s `ORDER BY` needs a genuinely numeric column (see `state_db.py`'s own entry above for why a TEXT-stored Decimal string would sort wrong).

**The one non-negotiable constraint**: `sync/file_import/dedup.py::compute_dedup_key()`'s hash input had to stay byte-identical to what it hashed before this refactor, for every already-imported file-import transaction — any drift would silently re-import a user's entire file-import history as duplicates (invariant 7). Proven safe, not assumed: `money.to_milliunits(money.parse_provider_amount(...))` was checked against **499 real historical amounts** (every raw SpareBank1 GET-transactions response amount and every already-tracked `amount_milliunits` value in production's `sync_state.db`, pulled read-only via SSH per the project's standing rule on production data access) against the old `round(float(amount) * 1000)` path — zero mismatches. The verification script itself wasn't kept in the repo (a one-off check against a snapshot of production data, not a reusable asset), but the technique is now documented in the `verify-dedup-key-refactor` skill for reuse next time key-derivation code is touched.

**Investigated and deliberately rejected**: wiring `parse_float=Decimal` into `providers/sparebank1/client.py`'s `response.json()` calls to eliminate float parsing at the true source, rather than downstream in `transform.py`. Confirmed live that httpx forwards `parse_float` correctly to `json.loads()` with zero precision loss (the raw JSON number *text* is handed straight to the callable, no float intermediate at all) — but `transform.py::get_transaction_date()` checks `isinstance(value, (int, float))` on the epoch-ms date field (see invariant 5), and a blanket `parse_float=Decimal` on the whole response would silently retype that field to `Decimal` too if SpareBank1 ever returns it with a literal decimal point, breaking date parsing for a reason entirely unrelated to the amount-precision goal. `money.parse_provider_amount()`'s `Decimal(str(raw))` approach already closes the amount-precision gap without this collateral risk, so `client.py` itself was left untouched.

## `tracked_transactions` retention policy (implemented)

Was a low-urgency hygiene concern with nothing pruning the table; now implemented via `StateDB.prune_booked_transactions(cutoff_date)` + `StateDB.maybe_vacuum(min_interval_days)`, called from `Scheduler._prune_tracked_transactions()` at the end of every `_do_cycle()` (non-fatal — a pruning failure is logged and never affects the cycle's own recorded success/failure).

- **Only `BOOKED` rows are pruned**, and only once past `config.sync.retention_days` (default 270 days) — enforced at config-load time to stay past the fetch horizon (`initial_backfill_days` + `lookback_overlap_hours`) via a `model_validator` in `config.py`, so a normal cycle's overlap window can never re-fetch a transaction that's already been pruned and misclassify it as new.
- **`PENDING` rows are never pruned by age**, regardless of `transaction_date` — their whole purpose is to be found again later so a pending→booked transition can be detected; pruning one would recreate the "one duplicate at the transition" risk described above, self-inflicted. `prune_booked_transactions`'s `WHERE` clause hard-codes `booking_status = 'BOOKED'` for exactly this reason.
- `maybe_vacuum` rate-limits `VACUUM` (tracked via a migrated `run_metadata.last_vacuum_at` column) since `DELETE`s alone don't shrink the on-disk file and `VACUUM` is too expensive to run every cycle.

## Payee-mapping reconcile pass (implemented)

Closes invariant 12's gap: what happens when a cached `payee_mappings` row's `ynab_payee_id` is later deleted/merged away in YNAB. Deliberately does NOT port sibling project `../ynab-auto-bank`'s heavier `PayeeAlias` learned-alias system — this project already anchors on `payee_id` synchronously at create time (invariant 12), so it doesn't have that problem to solve.

Current design (`SyncEngine.reconcile_payee_mappings()`) is a hybrid, chosen after two earlier designs were live-disproven: a pure bulk-list scan for `deleted: true` never actually detects a deletion (`scripts/verify_ynab_payee_deletion.py`, run three ways against real data — YNAB omits a gone payee from `get_payees()` entirely rather than flagging it); a pure per-id `GET .../payees/{id}` design fixed that (confirmed reliably 404s via `scripts/verify_ynab_payee_get_by_id.py`) but costs one API call per cached payee every sweep. Full narrative in CHANGELOG.md.

1. Fetch each budget's bulk `get_payees()` list once (skip the whole budget with zero calls if nothing's cached). Any cached id present there is trusted active — confirmed live that YNAB never lists a gone payee here.
2. Any cached id absent becomes a *candidate only*, never healed on absence alone (could be a transient/incomplete response) — confirmed individually via `get_payee()` (404 or `deleted: true`) before `StateDB.delete_payee_mappings_for_ids` heals it.

Rate-limited to once/day (`is_payee_reconcile_due`) as burst insurance, not because the common case is expensive. Never guesses what a deleted payee merged into — a later create just re-learns a fresh `payee_id` normally. Not written to `audit_events` (no transaction outcome to attach to; log-only, like `prune_booked_transactions`). Failure isolation at two levels: a bulk-fetch failure skips that budget's whole sweep; a per-id lookup failure is isolated to that one candidate.

**Also confirmed and closed**: YNAB payees have no `hidden` concept distinct from `deleted` — checked three ways live (raw JSON of an ordinary payee, a `PATCH` hide attempt got a 400, a manual UI-hide left the payee unchanged); see `scripts/verify_ynab_payee_hidden.py`. Don't re-investigate without new cause. (YNAB *categories* do have `hidden` — payees don't.)

## Deliberate non-goals (don't reintroduce this scope without discussing first)

- **No general web UI beyond the four admin tasks MQTT/HA genuinely can't do.** MQTT/Home Assistant remains the primary operational surface (status, sync-now, pause). The `frontend/` SPA (see architecture map) exists specifically for status visibility, deleted-transaction re-add, spreadsheet import, and account mapping — tasks needing a file upload, a tabular preview, or drag-and-drop, which HA's dashboard can't provide. Still no OAuth connection management and no general manual reconciliation UI — don't expand it without discussing first.
- **"No config editing" was deliberately overturned twice now — account mappings, and `logging.level`.** Mappings moved from `config.yaml` into the `account_mappings` SQLite table so the GUI can edit them by drag-and-drop; that was the explicit goal of the multi-provider work. `logging.level` got the same treatment for the same underlying reason (see "Runtime-configurable log level" below): `run_metadata.log_level` is state, not config, `config.logging.level` remains the fallback/default a fresh process starts with, and nothing about it is a secret or safety-sensitive. Both exceptions follow the exact same shape: state-DB-backed override, config value as the seed/fallback, never the other way around. Everything else in `config.yaml` — credentials, budgets, cron, retention, GUI/MQTT/notifications settings — remains hand-edited, static, and never written by the app. Don't extend GUI editing to those without discussing first (as happened for both of these); secrets in particular stay in the file.
- **No config export/import, no DB backup tooling.** Both solve problems specific to a fully DB-backed *mutable* config model (the sibling project's). This project's config is still a static YAML file — portable and backup-able by being a plain file. Note the mappings table is now the one exception, and it is *state*, not config: it lives in `state/sync_state.db`, which the invariants already treat as disposable and reconstructible.
- **No currency-mismatch handling.** SpareBank1's data so far shows domestic transactions' `amount`/`currencyAmount` matching exactly, suggesting pre-conversion rather than pass-through — revisit only if a real foreign-currency transaction is observed to behave differently.
